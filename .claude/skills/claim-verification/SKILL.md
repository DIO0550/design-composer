# 主張を書く前に確かめる

`implementation-flow` フェーズ3(計画)・フェーズ5(実装)で、コメント・doc・Issue/PR 本文に
**事実の主張**を書いたとき、**構造を変更したとき**、**列挙・表を書いた / 列挙の対象になって
いる項目を増減させたとき**は、それぞれ次の検証エージェントへ渡す前にこの手順で確かめる。

- フェーズ3(計画)で書いた分 → フェーズ4(`plan-reviewer`)へ渡す前
- フェーズ5(実装)で書いた分 → フェーズ6(`implementation-reviewer`)へ渡す前

**このスキルの管轄は、書いたものを実物と突き合わせるところだけ。** 確かめ方の対応表は
`.claude/agents/implementation-reviewer.md`「コメントや却下理由が...事実を主張していたら」に
既にあるので、ここでは複製せず参照する(同じ対応表を2箇所に持つと片方だけ古くなる。
`rules/coding.md`「規約の適用範囲」)。

## 手順

1. **書いた1文が、コード・外部ドキュメント・実行結果について何かを主張しているか確認する。**
   選択の理由の説明に留まり、確かめられる事実を主張していないなら対象外
2. 主張しているなら、`.claude/agents/implementation-reviewer.md` の
   「主張の形 / 確かめ方 / 分類」表からいちばん近い行を選ぶ(表に無い形の主張も、
   最も近い行の確かめ方に倣う)
3. **その「確かめ方」列に書かれた操作を実際に行う**(参照先を開く・grep する・数え直す・
   動かして見る・テストを壊す、等)。「読んで確認できるはず」で済ませない
4. 確かめた結果が主張と食い違っていたら、**主張の側を実物に合わせて直す**(実装の意図が
   違っていた場合の実装側の修正判断は、このスキルの対象外)
5. 同じ事実を説明する記述が差分の複数箇所にあるなら、**すべての箇所を同じタイミングで
   開いて確かめる**(1箇所だけ直すと `comment-referent-drift` 等の食い違いが残る)
6. **差分内で条件・仕組み・置き場所などの構造を変更したら、その構造を前提にしている
   Why / Why not が差分の他の箇所(新規・既存問わず)に残っていないか確認する**
   (`分類: comment-premise-drift`)。手順1〜5が「今書いた1文が正しいか」を確かめるのに対し、
   これは向きが逆で「今の変更が、前に書いた文の前提を崩していないか」を確かめる。
   変更前の条件・呼び出し順・置き場所を指す語で差分全体を `grep` し、ヒットした
   Why / Why not について `.claude/agents/implementation-reviewer.md`「記述の組」表の
   `comment-premise-drift` 行の確かめ方(差分の最終形を読み、前提がまだ成立しているか
   付き合わせる)で確かめる。崩れていたら前提の記述を新しい構造に合わせて書き直す
   (消すだけで済ませない)
7. **書いた列挙が実体を網羅しているかを、2 つの入口から確かめる**
   (`分類: comment-enumeration-drift`)。「この件数は◯◯だ」と数そのものを主張した文は
   手順1〜4 が扱う。ここが拾うのは次の 2 つ

   - **列挙・件数の対象を増減させたとき** — 手順6 と同じ向きで、増減させた側から
     「それを数えている文」を探す。**増減させた項目の名前・列挙の見出し語**で
     `src` / `docs` / `rules` / `.claude` を `grep` し、**差分の外も引く**(数えている文が
     差分に入っていないことがある)。数を指す語(「この◯つ」「◯個」)から引くと候補が桁違いに
     増えて絞り込みにならないので、項目名でヒットしたファイルと差分の中だけに当てる
   - **数を書いていない列挙を書いた・触ったとき** — 手順1 で「事実を主張していない」と
     落としやすいが、この形が繰り返し出ている。数える前に、**その列挙が説明している対象**
     (関数の失敗分岐・union の定義・呼び出し箇所のどれか)を先に決める。決まらないなら、
     その列挙が何を網羅すると言っているのかが決まっていない

   確かめ方は `.claude/agents/implementation-reviewer.md`「記述の組」表の
   `comment-enumeration-drift` 行による。食い違ったら記述の側を今の実体に合わせて直す

## 観点への追記のままにしない

`comment-structure-claim` / `comment-behavior-claim` は pr-294 で
`implementation-reviewer` の観点(層=観点)として対応済みだったが、その後も
26 件・10 件が再発した(`harness/records/pr-294.md`「対策済」)。**いずれもレビュー時点では
100% 捕まっており(すり抜け0)**、観点自体が読まれていないわけではない。しかし捕まる位置が
「実装済みの差分をレビューに出したあと」のままだと、直すたびに差分を出し直す手戻りが
繰り返される。観点への追記を繰り返しても再発は止まらなかった(2b「前回と同じ層への追記は
選択肢に入れない」)ため、実装時点で確かめる層(スキル)へ上げた。

同じ形が計画側にもあった。`plan-scope-premise-verification`(想定した接続先・前提・検証手段が
実例で成立するかの主張)は pr-352 で `implementation-flow` フェーズ3の手順(層=観点)として
分割されたが、その後も pr-359〜pr-394 の間に 7 件再発した(`harness/records/pr-352.md`
「対策済」)。**こちらもすり抜け0**で、`plan-reviewer` が毎回捕まえているのに計画の書き直しが
繰り返された。捕まる位置が「計画を `plan-reviewer` に渡したあと」のままだったことが原因なので、
comment 側と同じ理由でこのスキルへ寄せた(フェーズ3の呼び出しを追加)。

`comment-premise-drift`(Why / Why not が前提にした構造が同じ差分内の別の変更で崩れる形)も
同じ形だった。`comment-stale-edit` の4語彙分割(pr-305)で `implementation-reviewer` の観点
(層=観点)として対応済みだったが、締めの `対策済` 行が積み残しになっており「未介入」に
見えていた(`harness/records/pr-305.md`「対策済」に機械可読な再掲として追記済み)。積み残しを
解消すると、観点まで介入済みのまま 13 件再発しておりすり抜けは 0 件。comment-structure-claim /
comment-behavior-claim・plan-scope-premise-verification と同じく、レビュー時点でしか捕まらず
差分を出し直す手戻りが続いていたため、このスキルへ寄せた(手順6)。

`comment-enumeration-drift`(書いた列挙が実体を網羅していない形)も同じ形だった。
同じ pr-305 の4語彙分割で `implementation-reviewer` の観点(層=観点)として対応済みだったが、
`comment-premise-drift` と同じく締めの `対策済` 行が積み残しになっているため、`count.sh` 上は
「未介入」と出る。観点まで介入済みとして数え直すと pr-313〜pr-530 で 19 件再発しており、
すり抜けは 0 件。19 件は「実体を増減させて列挙が追随しなかった」向きと「書いた列挙が実体を
網羅していなかった」向きの2つに割れていたので、手順7 は入口を2つ持たせた(片方だけだと、
もう一方の向きが起動しない)。
