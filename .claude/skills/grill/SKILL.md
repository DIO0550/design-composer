# 起票前に仕様と判断を詰める

後で実装する人が同じ判断を聞き直さずに済むよう、依頼・会話で決まったことを下書きに移し、残りを対話で決める。

## 1. 本文に要る答えを拾う

[Issue フォーム](../../../.github/ISSUE_TEMPLATE/)を拠り所に、共通の 4 節にそれぞれ答えを入れる。既に会話や資料で答えが分かるものは聞き直さない。

| 節 | 確かめる問い |
| --- | --- |
| ゴール | 何ができるようになれば終わりか |
| 完了の確かめ方 | 何をどう確かめ、どんな結果なら完了か |
| 拠り所 | どの仕様書の節・UI 案の画面・既存テストなどに従うか。従うものがなければ、何を決める必要があるか |
| 決めてよい範囲 | 何を聞かずに決めてよく、何を必ず人に聞くか |

種類は根拠と推奨を用意し、未確定なら人に決めてもらう。選んだフォームの種類固有の必須欄（`required: true`）も埋める。
Epic では、何を軸に子へ分けるかと、各子が独立してマージできる理由まで決めて「分割の判断」に書く。親の起票だけを頼まれたら子の候補を本文に残す。子の起票も頼まれた場合は、各子の内容と種類を確定してから起票し、親に sub-issue として紐づける。

## 2. 止まりそうな分岐を調べてから尋ねる

1. UI 案で決まっていない見せ方、層をまたぐ移動、複数の実装案など、後で判断が割れそうな分岐を洗い出す。
2. 調べれば決まることは、質問の前に `grep` で既存の仕様・コード・テストを探すか、既存テストを実行するか、捨てられる小さな試作で確かめる。本実装に手を付けず、何を試して何が分かったかを残す。事実だけで答えが出たら質問から外し、結果と根拠を示す。実装できると分かっても採用の可否まで決まるわけではない。UI 案にない見せ方や UI 案から変える方針が未承認なら、調べた結果を比較材料にして人に尋ねる。
3. 人の判断がまだ要る分岐ごとに、選択肢・推奨・その理由を示す。先の回答で選択肢が変わるかを見て、今まとめて答えられる未決事項を 1 回にまとめる。
   - `AskUserQuestion` は 1 回 4 問まで。4 問以内なら 1 回、独立した 5 問なら 4 問と残り 1 問に分ける。別の対話ツールの上限が 4 問より少なければ、その上限に従う。
   - ゴールや種類などの回答で後続の問いが変わる場合は、先にその判断と同時に答えられる問いを聞く。回答を取り込んでから、残った問いと選択肢を組み直して次のまとまりで聞く。既に答えたことは聞き直さない。

## 3. 決めたことを本文にして渡す

- 共通 4 節と種類固有の必須欄に具体的な回答を入れる。未決のままの人の判断、空欄、仮置きが残っていれば起票しない。人が委ねた判断は「決めてよい範囲」に明記する。
- `## 決めた判断` に、分岐ごとに採用した方針と理由、却下した案と理由、調査や試作で確かめた事実と根拠を書く。分岐がなければ「追加の判断なし」と明記する。
- 作成時の本文と種類の書式は [`implementation-flow` の「種類の確定」手順 4](../implementation-flow/SKILL.md#種類の確定)を参照する。`implementation-flow` に通す Issue は人が選んだ種類を (a) に、Epic は (c) に当てる。書式の参照であり、`implementation-flow` を起動し直す手順ではない。
- 直接起票を頼まれた場合は `grill` が 1 件につき 1 回起票する。`implementation-flow` から呼ばれた場合は確定した本文と種類を返すだけにして、呼び出し元が起票する。下書きだけを頼まれた場合は投稿せず、下書きを返す。
