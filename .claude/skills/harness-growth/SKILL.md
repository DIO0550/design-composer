# ハーネスの育て方

マージされた PR 1 本につき、記録を 1 ファイル残す。記録は「今回何に躓いたか」を
分類タグ付きで書いたもの。溜まると `AGENTS.md`「ルールに書かれていない指摘が 2 回以上
出たら規約の抜けとして扱う」を機械的に数えられるようになる。

**記録は実装者への評点ではない。** 「良い / 悪い」ではなく「何が起きて、次にどう防ぐか」を書く。

---

## Step 1: 材料を集める

対象 PR について次を集める。

| 材料 | 取り方 |
| --- | --- |
| レビュー指摘 | `pull_request_read`(`get_review_comments` / `get_reviews` / `get_comments`) |
| CI の失敗 | `pull_request_read`(`get_check_runs`)、詳細は `get_job_logs` |
| 差分の規模 | `pull_request_read`(`get_files`) |
| 関連 Issue | PR 本文のリンク。Issue のコメント履歴に計画と却下案がある |
| 実装中の手戻り | このセッションの履歴。計画から外れた箇所、書き直した箇所 |
| フックの発火 | セッション中に hooks が止めた操作(lint 抑制・push ブロックなど) |

**手戻りとフックの発火は記憶からしか取れない。** 別セッションで実行する場合は
Issue と PR に残っている記録から復元し、復元できない分は「不明」と書く。
**推測で埋めない**(埋めると記録が推測混じりになり、回数の根拠として使えなくなる)。

## Step 2: 記録を書く

`harness/records/pr-<番号>.md` に
[templates/record.md](templates/record.md) の形式で書く。
**`.claude/` の下には置かない**(書き込みのたびに承認が要るため /
[`harness/records/README.md`](../../../harness/records/README.md))。

- **指摘 1 件 = 1 ブロック。** まとめて 1 件にしない(分類が混ざって数えられなくなる)
- `分類` は [templates/record.md](templates/record.md)「分類の語彙」から選ぶ。**語彙を勝手に増やさない**
  (増やしてよいのは Step 4 の 4c と `なし` の逃し弁だけ)
- どれにも当てはまらないなら `分類: なし` と書き、内容に何の話かを書く。
  これが「規約の抜け」の候補になる
- **指摘が 0 件の回も記録を残す。** 0 件は「順調だった」というデータ

## Step 3: 回数を数える

```bash
bash harness/records/count.sh
```

| 列 | 意味 |
| --- | --- |
| 再発 | **最後の介入より後**の記録に出た件数。Step 4 の分岐はこれで決める |
| 通算 | 全記録での件数。語彙が飽和していないかを見るときの参考 |
| 以降 | 最後の介入より後の記録の本数(「介入後 N 本再発ゼロ」の N) |
| 最終介入 | 前回置いた層と、その回の PR 番号。無ければ「未介入」 |

**通算ではなく再発で分岐する。** 通算は単調増加するので介入が効いたかを表さない
(10 回目の後の 11 回目が、介入の前と後のどちらなのかが読めない)。

`分類: なし` の中身は数えられないので、目視で似た話が過去に無いかを確認する。

## Step 4: 数えた結果で分岐する

`count.sh` の出力を上から見て、**該当する最初の規則**に従う。1 件しか出ていない分類は
記録するだけにして改善はしない(1 件で規約を足すと、その回限りの事情がルールとして固定される)。

### 4a. 未介入で 2 回以上 → 介入する

置き場所は強制力の強い順に検討する。**上から順に「これで防げるか」を確かめ、採らなかった
ものは理由を記録に書く。** 理由を書かずに下へ降りない。降りた記録が残らないと、毎回
いちばん弱い「`rules/` に一文足す」へ落ち着き、次の回も同じ分類が出る。

| # | 層 | 置き場所 | 選ぶ条件 |
| --- | --- | --- | --- |
| 1 | `hook` | git hooks(`harness/githooks/`)または CI。同じ検査を `.claude/hooks/` にも置き、即時フィードバック版として共有する | **機械的に判定できる**(文字列・AST・コマンドの成否で白黒が付く) |
| 2 | `skill` | `.claude/skills/` に新しいスキルを作る | **毎回同じ段取りを踏む作業**があり、順番を間違えると結果が変わる |
| 3 | `観点` | 既存スキルの手順・観点に足す(`implementation-flow` の各フェーズと `references/`) | 実装前・検証時に気づける観点 |
| 4 | `rules` | `rules/` に追記する、または表現を直す | 判断基準がどこにも書かれていない / 書いてあるが読まれていない |

**`rules` は読み手の記憶に頼るのでいちばん弱い。** ここへ落とすのは 1〜3 が使えないと
確かめたときだけにする。**Claude Code のフックだけを 1 段目として数えない**
(発火しない実行環境がある / [`.claude/hooks/README.md`](../../hooks/README.md))。

介入したら、記録の「規約への反映」の末尾へ次を足す。**この行が次回の起点になる。**

```markdown
**この回の介入（`count.sh` が数える行）:**

- 対策済: `naming` 層=rules at pr-168
```

**上の層に置けたら、下の層の記述は参照 1 行に縮める。** フックにしたのに `rules/` の
該当節をそのまま残すと、総量が増える一方になる。縮めた分も同じ PR の差分に含める。

### 4b. 介入済みで、介入後に 2 回再発 → 層を 1 つ上げる

**前回と同じ層への追記は選択肢に入れない。** 「`rules/` に書いたのに再発した」は
「読み手の記憶に頼る層は弱い」の実測データであり、同じ層で表現を変えても同じ結果になる。

上の層で表現できない(機械判定できず、毎回の段取りでもない)ときだけ、**その理由を書いて
据え置きにできる**。据え置きも判断なので `対策済` の行は書く(次の 2 回をそこから数える)。

### 4c. 介入後 5 回以上 → 分類が飽和している。語彙を割る

同じ分類が対策後も 5 回出るのは、その語彙が**別種の問題を 1 つのタグに畳んでいる**サイン。
「N 回目」にもう情報が無い。

- 直近の同分類の指摘を並べ、亜種ごとに新しい語彙を切って
  [templates/record.md](templates/record.md) の語彙表へ足す
- **過去の記録は書き換えない。** 新しい語彙の数えは、足したあとの記録から始まる
- 割った結果、片方の亜種が機械判定できるなら、その場で 4a に戻ってフック化を検討する

### `なし` の逃し弁

`なし` が 10 件溜まったら、目視でグルーピングして語彙へ昇格する。
「語彙を勝手に増やさない」は各記録を書く時点での規則であって、**語彙表そのものの更新を
ここで行うのは正常な手順**。昇格させたら `なし` の `対策済` の行(層は昇格先の層)を書き、
`なし` の数えをそこから始め直す。

### フックにする / しない

- **機械的に判定できるものだけをフックにする。** 「帰属先が正しいか」「この正規化は過剰か」
  のような判断はフックにできない(文字列一致では偽陽性しか出ない)
- フックが誤って止めると実装者はエスケープハッチを探すようになり、**フック全体が信用
  されなくなる**(経緯は [`.claude/hooks/README.md`](../../hooks/README.md)「例外」)
- 迷ったら**既存のフックが何を見ているか**を読む。`check-test-rules.sh` のように
  「`test()` ブロックの中だけ」と対象を絞れるなら成立する。絞れないなら成立しない
- **弱める(報告に留める / 追加行だけに絞る)前に、`--all` 相当で件数を数えて、埋められる
  なら埋める。** 埋めれば絞る理由そのものが消え、いちばん強い形がそのまま成立する。
  弱めるなら、その理由といつ強められるかを `.claude/hooks/README.md` へ書く
  (数えて埋めた実例: `harness/records/pr-159.md`)
- 足したら配線も更新する。git hooks は `harness/githooks/`、Claude Code のフックは
  `.claude/settings.json` と `.claude/hooks/README.md` の表

### 新しいスキルを作る / 作らない

- **作る**: 同じ段取りを毎回踏んでいて、**順番を間違えると結果が変わる**もの
- **作らない**: 判断基準が 1 つ増えただけ(→ `rules/`)。1 回しか通らない手順。
  既存スキルの 1 フェーズに収まるもの(→ そのスキルへ足す)
- **既存スキルへ足せるなら足す。** スキルが増えるほど「どれを読むか」の判断が要るので、
  数が増えること自体がコストになる

## Step 5: 棚卸し(条件を満たしたときだけ)

Step 3 の集計時に次のいずれかが真なら、**その回の PR に棚卸しを含める**。
真でなければこの Step は飛ばす(カレンダーでは発火させない)。

| 条件 | やること |
| --- | --- |
| 4b / 4c / `なし` 10 件に該当がある | Step 4 の該当規則を実行する |
| `wc -l AGENTS.md rules/*.md` の合計が 1500 行を超えた | フック / CI で強制済みの節を参照 1 行へ縮める。無ければ、いちばん再発していない分類の節を要約する |
| このファイル(`SKILL.md`)が 200 行を超えた | 判例(件数・経緯)を `harness/records/` への参照 1 行に置き換える |
| 「以降」が 10 本以上で「再発」が 0 の分類がある | **その対策より下の層に残る同内容の記述を削る**(効いている証拠が出たので二重に持つ理由が無い) |

最後の 1 行が eviction の本体。「発火しない = 効いている / 見られていない」は区別できないので、
**上の層(フック / CI)が実在する場合に限って下の層の文章だけを削る**。ガード自体は消さない。

## Step 6: PR にする

記録(と Step 4・5 の改善があればそれ)を 1 本の PR にする。

- **記録対象の PR とは別のブランチを切る**(記録対象はすでにマージ済み)
- PR 本文には、記録した分類の一覧と、介入したものがあればその対応を書く。
  **対応には「どこへ置いたか」だけでなく「なぜ上の層にしなかったか」も書く**
- **改善が無い回でも PR は出す。** 記録が残ること自体が目的
- フックを足した回は配線が揃っていることを確かめる(片方だけだと動かない / 誰も知らない)

---

## 注意事項

- **過去の記録を書き換えない。** 判断が変わったら新しい記録に書く。
  書き換えると履歴が消えて回数を数えられなくなる
  (例外は `対策済` の行の追加。判断ではなく、その記録が既に結論したことの機械可読な再掲)
- 記録は PR ごとに 1 ファイル。1 つのファイルへ追記する形にしない
  (並行する PR が必ず衝突する)
- 記録を書くために実装を蒸し返さない。集めるのは**すでに出ている**指摘・失敗・手戻りだけ
