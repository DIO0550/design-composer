# ハーネスの育て方

記録を数え、**人・bot・CI まで届いた指摘が再発している分類**にだけ手を入れる。

**評価を決めるのは人。** サブエージェントの指摘と自己修正は `内部` 列に出るが、分岐には
使わない(理由は [`harness-record/templates/record.md`](../harness-record/templates/record.md)
「なぜ外部だけで分岐するのか」)。数えるのは成果であって饒舌さではない。

**入力は既にある記録の集計。記録の新規作成はしない**(→ `harness-record`)。

---

## Step 1: 数える

**`harness-counter` サブエージェントへ投げる。** 記録は増え続けるので、本文をこのコンテキストへ
入れない。返るのは `count.sh` の出力・対象 1 件・その根拠だけ。自分で数えるのは、エージェントが
使えない環境のときだけ。

```bash
bash harness/records/count.sh            # 分類ごとの再発（増やす側）
bash harness/records/count.sh --shrink   # 縮める側（Step 5 で使う）
```

| 列 | 意味 |
| --- | --- |
| 再発 | 起点より後の記録で、**人・bot・CI に届いた**件数。**分岐はこれだけで決める** |
| 内部 | 同じ区間で、サブエージェント・自己修正・フックが捕まえた件数。**分岐に使わない** |
| 通算 | 全記録での件数 |
| 以降 | 起点より後の記録の本数 |
| 起点 | その分類でいちばん古い、まだ開いている介入 |

## Step 2: 対象を 1 つだけ選ぶ

**再発が 2 以上の分類のうち、再発が最も多いもの 1 つ**を今回の対象にする。同数なら**起点が
古いほう**(未介入を最優先)を採る。通算・内部は分岐に使わない性質なので、同数の割り方にも
使わない。

- **1 回の growth で介入は 1 つ。** 複数置くと、次に数えたときどれが効いたのかが分からなくなる
- 再発 1 以下の分類は何もしない。1 件で規範を動かすと、その回限りの事情が固定される
- 再発 2 以上が 1 つも無ければ、増やす側は**何もしない**。Step 5 の棚卸しだけを行う
- `なし` が選ばれたら、まず中身を読んで 13 個の語彙のどれかに入らないかを見る。入らない形が
  2 件以上まとまっているなら、**それは語彙ではなく判例に書く**(語彙は増やさない)

## Step 3: 介入先を決める（フックか判例の 2 択）

| 介入先 | 選ぶ条件 | 置き場所 |
| --- | --- | --- |
| `hook` | **機械的に判定できる**(文字列・AST・コマンドの成否で白黒が付く) | まず linter の設定(`.oxlintrc.json` / Biome)。書けなければ `.claude/hooks/lib/` に検査を置き、git hooks・CI・`.claude/hooks/` の 3 層へ配線する |
| `case-law` | 機械判定できない | `harness/case-law/<対応するファイル>.md` に、その回の実例(NG / OK・固有名・PR 番号)を足す |

**`rules/` は増やさない。** 規範は「別のリポジトリへ持っていって意味が通るか」で選ばれた少数
だけで、実例は判例に置く。**介入としては**スキル・検証エージェントの観点も増やさない
(足すこと自体を禁じるのではなく、再発への対処としてここを選ばない)。**規範そのものが足りて
いないと判断したときは、その場で `rules/` を書き換えず、規範の追加を提案する Issue を立てる**
(規範を動かすかどうかは人の判断。growth が自動で足す対象ではない)。

**linter の設定を最初に確かめる。** 1 つの設定変更が既存の配線(編集後 lint・push 前 lint・CI)に
そのまま乗るのに対し、自前スクリプトは 3 層それぞれに配線が要る。**「フック化は不成立」と書く
ときは、linter 設定・自前スクリプトのどちらも確かめてから書く**(確かめずに降りると判例へ偏る)。

## Step 4: フックは再生で確かめる

**採用の条件は再生**: その指摘が出た PR の**マージ前の木で発火し、いまの main で発火しない**こと。
片方でも外れたら入れない(発火しない＝見ていない / main で発火する＝既存を止める)。

```bash
git fetch origin pull/<PR番号>/head
git worktree add --detach /tmp/replay FETCH_HEAD
<新しい検査> /tmp/replay/src   # → 発火する（その回の欠陥を捕まえる）
<新しい検査> src               # → 発火しない（既存を止めない）
git worktree remove --force /tmp/replay
```

誤って止めるフックはエスケープハッチを探す運用を招き、フック全体が信用されなくなる。対象を
絞れないなら成立しないので判例へ回す。足したら配線も更新する(`harness/githooks/` /
`.claude/settings.json` / `.claude/hooks/README.md` の表)。**人が踏む手順も配線のうち**で、
CI だけが走らせる検査は `implementation-flow` フェーズ 7 の push 前コマンド一覧へも足す。

**判例には再生に当たる確認が無い。** 置いた実例が次に読まれるかは測れないので、判例で済ませた
回は「なぜ機械判定にできなかったか」を PR に書き、次に同じ分類が再発したらフック化を再検討する。

## Step 5: PR にする（棚卸しを含む）

- **Issue を立て、PR 本文に `Closes #<番号>` を書く。** 数えた結果と分岐の判断はその Issue に残す
- 介入した分類が最後に出た記録の「規約への反映」へ、次の 1 行を足す。**これが次回の起点になる**

  ```markdown
  - 対策済: `naming` 層=hook at pr-<この PR の番号>
  ```

- **`count.sh --shrink` に該当があれば、同じ PR に棚卸しを 1 つだけ含める**(増やす側と同じく、
  複数入れるとどれが効いたか分からなくなる)。該当が複数なら、以降がいちばん長いものを採る

  | 節 | 条件 | やること |
  | --- | --- | --- |
  | 1 | 以降 10 本以上で再発 0 | その分類に対応する `rules/` の記述を、フック・判例への参照 1 行へ縮める |
  | 2 | 実測が予算を下回っている | `count.sh` の予算を実測まで**下げる**(ラチェット。上げない) |
  | 2 | 実測が予算を超えている | 足した分と同量を削るか、判例・フックへ移す(**予算は上げない**) |
  | 3 | 発火 0 の装置 | 退役候補。消すか、呼ばれ損ね(description の文言)を直すかを選び、理由を書く |

- **該当したのに縮めなかった回は、理由を PR に書き、その分類が最後に出た記録へ
  ``- 見送り: `<分類>` at pr-<番号>`` を足す**(`--shrink` が見送り回数を出す)。見送りが 2 回
  続いた候補は、3 回目に理由の書き足しでは済ませない
- **改善が無い回は PR を出さない。** 出すものが無いのは正常な結果
- 記録ファイルに触るのは `対策済` と `見送り` の行の追加だけ。**新しい記録は作らない**

---

**過去の記録・判例を書き換えない。** 判断が変わったら新しく足し、古いほうに 1 行添える
(例外は `対策済` / `見送り` の行の追加。判断ではなく機械可読な再掲)。判例を書けるのはこの
スキルだけ。
