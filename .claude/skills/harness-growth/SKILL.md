# ハーネスの育て方

記録を数え、**人・bot・CI へ届いた指摘が再発している分類 1 つ**にだけ手を入れる。印象や
読み直しでは決めない。記録の新規作成はしない(→ `harness-record`)。

介入先は**フックか判例の 2 択**。読み手の記憶に頼る文章(`rules/`・スキルの手順・エージェントの
観点)を足すことは介入に数えない。機械判定できないものは判例に置き、検証エージェントがそこを読む。

## 1. 数える

`harness-counter` サブエージェントへ投げる(記録本文をこのコンテキストへ入れないため)。

```bash
bash harness/records/count.sh              # 分類ごとの再発
bash harness/records/count.sh --shrink     # 縮める側
bash harness/records/count.sh --list <分類> # その分類の、最後の介入より後の指摘
```

| 列 | 意味 |
| --- | --- |
| 再発 | 最後の介入より後に、人・bot・CI へ届いた件数。**分岐はこれだけで決める**(サブエージェントの指摘を混ぜると、観点を足すほど再発に見える) |
| 内部 | 同じ期間にサブエージェント・フック・自己修正が拾った件数。参考値 |
| 以降 | 最後の介入より後の記録の本数 |

## 2. 1 つ選ぶ

**再発が 2 以上の分類のうち最大の 1 つ**を選ぶ。同数なら内部が少ないほう(観点でも拾えて
いない側)。無ければ介入せず「5. 縮める」へ進む。

- 1 回の growth で介入は 1 つ。まとめて直すと、どれが効いたかを次回数えられない
- `なし` が最大なら、`--list なし` を並べて 2 件以上まとまる形を 1 つ切り出し、それを対象にする
  (語彙表へ足すのは、その形がフックか判例になったあと)
- 介入済みの分類が再発したなら、前回の置き場所は候補から外す(同じ層で言い換えても同じ結果になる)

## 3. フックにする

上から順に「これで捕まえられるか」を確かめる。

1. **linter の設定**(`.oxlintrc.json` / Biome)。既存の配線(編集後 lint・push 前 lint・CI)に
   そのまま乗る
2. **自前の検出器**(`.claude/hooks/lib/`)。リポジトリの構造を読まないと判定できないもの。
   配線は `.claude/hooks/`・`harness/githooks/`・`.github/` の 3 層(`.claude/hooks/README.md`「配線」)
3. **手順の中の検査**(`.claude/skills/` のコマンド、`harness/githooks/pre-push`)。実行の順序が
   決まっているときだけ

**機械的に判定できるものだけをフックにする**(文字列・AST・コマンドの成否で白黒が付く)。
判断をフックにすると偽陽性が出て、フック全体が信用されなくなる。

### 採用前の再生

フックは書いた時点では効くかどうか分からない。**過去の記録で再生してから採用する。**

```bash
bash harness/records/count.sh --list <分類>          # 捕まえるべき指摘と PR 番号
merge="$(git log --merges --format=%H --grep='pull request #<番号> ' origin/main | head -1)"
git worktree add /tmp/replay "${merge}^2"           # その PR のマージ前の木
(cd /tmp/replay && <検出器>)                          # ここで発火しなければ、そのフックは捕まえない
<検出器>                                             # main では発火しないこと(偽陽性)
```

再発の指摘を **1 件も捕まえないフックは採用しない**。捕まえた件数と偽陽性 0 を PR に書く。

## 4. フックにできなければ判例へ

`harness/case-law/<規範と同名>.md` に、その分類の見出しの下へ **NG / OK の形と判定の
分かれ目**を書く(書き方は `harness/case-law/README.md`)。`rules/` には足さない。

スキルの手順へ足してよいのは、**順番を間違えると結果が変わる段取り**だけ。判断基準が
1 つ増えただけなら判例。

## 5. 縮める

`--shrink` の数字で決める。目で確かめない。介入と同じく 1 回に 1 つで、**該当があるのに飛ばさない**
(削ることは足すことと同じ重さの介入。理由は `AGENTS.md`「常時ロードは増やさない」)。

| 節 | 条件 | やること |
| --- | --- | --- |
| 1 | 常時ロードが上限を超えている | 実例・固有名・件数・PR 番号を判例へ移す。無ければ、フックで強制済みの節を参照 1 行にする |
| 1 | 常時ロードが上限を下回った | `count.sh` の `always_loaded_cap` をその値まで下げる。**上げない** |
| 2 | 以降 10 本以上で再発 0 の分類 | その分類の `rules/` の節から実例・経緯を判例へ落とす(規範の 1 文は残す) |
| 4 | 発火 0 の装置 | 退役するか、description のトリガー文言を直す。どちらかを理由付きで選ぶ |

## 6. PR にする

- Issue を立て、数えた結果・選んだ分類・採らなかった置き場所とその理由を書く。PR 本文は
  `Closes #<番号>`
- **その分類が最後に出た記録**の「規約への反映」末尾に起点の行を足す(書けるのはこのスキルだけ)

  ```markdown
  - 対策済: `<分類>` 層=<hook|skill|case-law> at pr-<番号>
  ```

- `rules/` を触った回は `count.sh --shrink` の節 1 を PR 本文に貼る
- **介入も縮めるも無い回は PR を出さない。** 出すものが無いのは正常な結果
- 過去の記録・過去の判例は書き換えない(判断が変わったら新しく足す)
