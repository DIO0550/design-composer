# ハーネスの育て方

マージされた PR 1 本につき、記録を 1 ファイル残す。記録は「今回何に躓いたか」を
分類タグ付きで書いたもの。溜まると `AGENTS.md`「ルールに書かれていない指摘が 2 回以上
出たら規約の抜けとして扱う」を機械的に数えられるようになる。

**記録は実装者への評点ではない。** 「良い / 悪い」ではなく「何が起きて、次にどう防ぐか」を書く。

---

## Step 1: 材料を集める

対象 PR について次を集める。

| 材料 | 取り方 |
| --- | --- |
| レビュー指摘 | `pull_request_read`(`get_review_comments` / `get_reviews` / `get_comments`) |
| CI の失敗 | `pull_request_read`(`get_check_runs`)、詳細は `get_job_logs` |
| 差分の規模 | `pull_request_read`(`get_files`) |
| 関連 Issue | PR 本文のリンク。Issue のコメント履歴に計画と却下案がある |
| 実装中の手戻り | このセッションの履歴。計画から外れた箇所、書き直した箇所 |
| フックの発火 | セッション中に hooks が止めた操作(lint 抑制・push ブロックなど) |

**手戻りとフックの発火は記憶からしか取れない。** 別セッションで実行する場合は
Issue と PR に残っている記録から復元し、復元できない分は「不明」と書く。
**推測で埋めない**(埋めると記録が推測混じりになり、回数の根拠として使えなくなる)。

## Step 2: 記録を書く

`harness/records/pr-<番号>.md` に
[templates/record.md](templates/record.md) の形式で書く。
**`.claude/` の下には置かない**(書き込みのたびに承認が要るため /
[`harness/records/README.md`](../../../harness/records/README.md))。

- **指摘 1 件 = 1 ブロック。** まとめて 1 件にしない(分類が混ざって数えられなくなる)
- `分類` は [templates/record.md](templates/record.md)「分類の語彙」から選ぶ。**語彙を勝手に増やさない**
- どれにも当てはまらないなら `分類: なし` と書き、内容に何の話かを書く。
  これが「規約の抜け」の候補になる
- **指摘が 0 件の回も記録を残す。** 0 件は「順調だった」というデータ

## Step 3: 回数を数える

書いた記録の各分類について、過去の記録に同じ分類が何回出ているかを数える。

```bash
grep -rho '^- 分類: `[^`]*`' harness/records/ | sort | uniq -c | sort -rn
```

`分類: なし` の中身は数えられないので、目視で似た話が過去に無いかを確認する。

## Step 4: 2 回以上なら改善する

`AGENTS.md`「規約の更新」に従い、**2 回以上出ている分類**は規約 / スキル / フックの抜けとして扱う。

### 置き場所は強制力の強い順に検討する

**上から順に「これで防げるか」を確かめ、採らなかったものは理由を記録に書く。**
理由を書かずに下へ降りない。降りた記録が残らないと、毎回いちばん弱い
「`rules/` に一文足す」へ落ち着き、次の回も同じ分類が出る。

| # | 置き場所 | 選ぶ条件 | 強制力 |
| --- | --- | --- | --- |
| 1 | `.claude/hooks/` にフックを足す | **機械的に判定できる**(文字列・AST・コマンドの成否で白黒が付く) | 実行時に止まる |
| 2 | `.claude/skills/` に新しいスキルを作る | **毎回同じ段取りを踏む作業**があり、順番を間違えると結果が変わる | 呼ばれたら必ず読まれる |
| 3 | 既存スキルの手順・観点に足す | 実装前・検証時に気づける観点(`implementation-flow` の各フェーズと `references/`) | フェーズで必ず通る |
| 4 | `rules/` に追記する | 判断基準そのものがどこにも書かれていない | 読まれることが前提 |
| 5 | `rules/` の表現を直す | 書いてはあるが読まれていない(表・NG/OK の対比を足す) | 同上 |

4 / 5 は**読み手の記憶に頼る**ので、いちばん弱い。ここへ落とすのは 1〜3 が使えないと
確かめたときだけにする。

### フックにする / しない

- **機械的に判定できるものだけをフックにする。** 「帰属先が正しいか」「この正規化は
  過剰か」のような判断はフックにできない(文字列一致では偽陽性しか出ない)
- フックが誤って止めると実装者はエスケープハッチを探すようになり、**フック全体が
  信用されなくなる**。既存のフックが誤検知で信用を失った経緯は
  [`.claude/hooks/README.md`](../../hooks/README.md)「例外(エスケープハッチ)」にある
- 迷ったら**既存のフックが何を見ているか**を読む。`check-test-rules.sh` のように
  「`test()` ブロックの中だけ」と対象を絞れるなら成立する。絞れないなら成立しない
- 足したら `.claude/hooks/README.md` の表と `.claude/settings.json` の配線も更新する

### 新しいスキルを作る / 作らない

- **作る**: 同じ段取りを毎回踏んでいて、**順番を間違えると結果が変わる**もの
  (「先に既存テストの観点を数えてから書き換える」のように、手順そのものが品質を決める)
- **作らない**: 判断基準が 1 つ増えただけ(→ `rules/`)。1 回しか通らない手順。
  既存スキルの 1 フェーズに収まるもの(→ そのスキルへ足す)
- **既存スキルへ足せるなら足す。** スキルが増えるほど「どれを読むか」の判断が要るので、
  数が増えること自体がコストになる

### 記録に残すこと

2 回以上の分類ごとに、記録の「規約への反映」へ次の 2 つを書く。

- 選んだ置き場所と、そこで何を足したか
- **それより上の番号を採らなかった理由**(「判断なので機械判定できない」
  「毎回の段取りではなく判断基準が 1 つ増えただけ」など)

### 1 回目は記録だけ

**1 回目の分類は記録するだけにして、改善はしない。** 1 件で規約を足すと、
その回限りの事情がルールとして固定される。

## Step 5: PR にする

記録(と Step 4 の改善があればそれ)を 1 本の PR にする。

- **記録対象の PR とは別のブランチを切る**(記録対象はすでにマージ済み)
- PR 本文には、記録した分類の一覧と、2 回以上に達したものがあればその対応を書く。
  **対応には「どこへ置いたか」だけでなく「なぜフック / 新しいスキルにしなかったか」も書く**
  (Step 4 の検討をレビューできる形にするため)
- **改善が無い回(1 回目の分類だけ)でも PR は出す。** 記録が残ること自体が目的
- フックを足した回は `.claude/settings.json` の配線と `.claude/hooks/README.md` の表が
  揃っていることを確かめる(片方だけだと動かない / 動くが誰も知らない)

---

## 注意事項

- **過去の記録を書き換えない。** 判断が変わったら新しい記録に書く。
  書き換えると履歴が消えて回数を数えられなくなる
- 記録は PR ごとに 1 ファイル。1 つのファイルへ追記する形にしない
  (並行する PR が必ず衝突する)
- 記録を書くために実装を蒸し返さない。集めるのは**すでに出ている**指摘・失敗・手戻りだけ
