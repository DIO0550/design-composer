# 実装レビューの観点(過剰なブロック / フォールバック / 重複)

サブエージェントに実装差分を検証させるときの観点。フェーズ 6 で使う。
狙いは「動くけれど失敗を隠している」コードと、「編集のついでに増えた重複」を
PR に出す前に見つけること。

## 過剰なフォールバックの観点

- **既定値での穴埋め。** 失敗したときに空配列 / `0` / 空文字 / 「とりあえずの値」を
  返していないか。呼び出し側が失敗を知れなくなるので、`Result.err` / `Option.none` の
  まま返す
- **握りつぶし。** `Result` / `Option` を受け取って失敗側を捨てている箇所
  (`?? defaultValue`、`err` を無視した早期 return、`some` を見ずに `value` を読む)が無いか
- **二重の失敗表現。** `Result` を返す関数の内側で、さらに防御的な分岐を重ねていないか
- **到達しない分岐。** 型で既に排除されている状態に対する実行時チェックが残っていないか
  (直和で列挙したあとに「どれでもない場合」を書いている、など)
- **握りつぶした結果の隠蔽。** 失敗を握りつぶしたうえで UI に「何も起きなかった」ように
  見せていないか
- **仕様の規則を、仕様が決めていない対象へ類推で広げていないか。** 「A についてこう
  決まっているから、似ている B もそうする」は仕様ではなく実装者の推測。**docs が明文で
  決めているのはどこまでか**を引用して確かめる。既定値の解決規則(「省略時は 0」)を
  表記の規則(「0 は省略で書く」)として読み替えるのが典型で、正規化・省略・補完の形で出る
  - 見分け方: **その処理をやめると何が変わるか**を数える。画面もファイルの意味も変わらず
    「書き出しの綴りだけが変わる」なら、仕様が求めていない書き換え
  - 同じ仕組みを別の対象へ横展開するときは、**対象ごとに動機があるか**を確かめる。
    片方に効かせる理由(壊れるから)が、もう片方には無いことがある

## 過剰なブロックの観点

- **要らない存在チェック。** 必須の props / 引数に対する `if (!x) return` が「念のため」で
  入っていないか。必要なら型で必須にする
- **ガードの重複。** 呼び出し側と呼ばれる側の両方で同じ条件を弾いていないか。
  型で保証できる側に寄せる
- **フラグによる防御。** `useRef` で二重実行・連打を止めていないか(`rules/hooks.md`
  「ref をフラグにした『防御』」)。render に出る状態は `useState`、ボタンは `disabled`
- **ネストの深さ。** ブロックが 3 段を超えていないか。早期 return・関数分割で平らにする
- **無効化されたリント。** `biome-ignore` / `eslint-disable` が新たに入っていないか
- **範囲の固定窓による近似。** 宣言・ブロックの範囲を「ここから N 行」「N 文字」で
  切っていないか。窓は必ず外れるので、**窓の外に同種のものを置いた入力で確かめる**。
  構文で切れるなら(波括弧の対応など)そちらにする

| NG | OK |
|---|---|
| 関数の本体を `lines[index : index + 80]` で見て `throw` を探す。下に並ぶ別の関数の `throw` を拾う | 波括弧の対応で本体を切る(`missing-doc-comments.py` の `body_of`) |

## 重複の観点

計画では見えず、**編集しているファイルの中でついでに書き足した**ときに増える。
差分を見る段でしか捕まらないので、フェーズ 6 で必ず見る。

**`__tests__/` 内の本体が一字一句同じヘルパー**は `check-test-helper-duplication.sh`
(`分類: duplication-test`)が機械判定する。ただし対象は**編集したファイルが絡む・
同じ `__tests__/` フォルダ内・関数本体のみ**で、定数の重複と `__tests__/` を跨いだ重複は
見ていない(#179)。差分で複数のテストファイルを触ったなら、フックが拾わない範囲を
このチェックで補う。

以下は**判断が要る重複**(`分類: duplication-logic`)。テストヘルパーと違い機械判定できない。

- **同じ走査・同じ判定を書き足していないか。** 新しく足した関数が、同じファイルや
  同じ層の既存モジュールと同じことをしていないか(`find` と `findIndex` のように
  戻り値だけが違う形も含む)。片方をもう片方に乗せて、走査を 1 箇所にする
- **組み込み型への操作を直書きしていないか。** 先頭を取る・範囲を見る・集合を反転する
  といった操作は `src/utils/` の `<型名>Ex` にある。`array[0]` を書く前に読む
- **同じ値を 2 箇所で計算していないか。** 親と子の両方で同じ判定を求めているなら、
  求めるのは 1 箇所にして渡す
- **同じ事実を、別々のドメインオブジェクトや別々の道筋から独立に導いていないか。**
  「両者が食い違う組み合わせ」が型で作れてしまうなら、1 箇所で決めてそこから渡す形に畳む
  (例: 見出しのバッジ・ラベル・強調表示がそれぞれ別の値から同じ事実を導いていた → PR #162)
- **`switch` や対応表の分岐が、由来ごとに同じ構造(見出し・件数・行の組み立てなど)を
  繰り返していないか。** 分岐ごとに異なる部分だけを返す関数へ畳み、器や並びの組み立ては
  1 箇所にする(例: `switch (props.origin)` の 3 枝がそれぞれ器と行を組んでいた → PR #185)

## 命名の観点

新しく付けた識別子名(コンポーネント・ファイル・変数・定数)が、**このリポジトリの他の場所で
既に別の意味に使われていないか**を確認する(`分類: naming-precedent`)。`rules/naming.md`
「名前と実体を一致させる」「内容を表さない汎用語を使わない」は既に書かれているが、書いた
時点では気づかれず、実装検証のサブエージェントも捕まえられないまま**すべてレビューで
指摘されてから直っている**(`Document*` の接頭辞が指す対象からはみ出していた → PR #173、
他ツールの慣習名 `install` を借りたが何を install するか言えなかった → PR #205、
UI 案にも仕様書にも 0 回の比喩 `Legend` を使っていた → PR #211)。

- **接頭辞・語幹を grep で確認する。** `Document*` のように同じ接頭辞を持つ既存モジュールが
  あるなら、その接頭辞が指している対象と、新しく付けた名前の対象が一致しているか
- **借用した慣習名は、このリポジトリの文脈で何を指すかを言えるか確認する。** 他のツールの
  慣習(`husky` の `install` 等)をそのまま借りると、このリポジトリでの意味を言えない名前になる
- **比喩・抽象語を使うときは、`docs/06-ui.md` と `docs/Design Composer.html` に同じ語が
  出てくるかを `grep -i` で数える。** 0 回なら、その比喩がこのリポジトリの語彙に無い証拠
  (`rules/ui-verification.md`「数えるときは大文字小文字を無視する」と同じやり方)
- 上記の確認で既存の用法と衝突・不一致が見つかったら、`rules/naming.md` の該当節を示して
  改名を提案する

## UI 要素の意味の観点

差分やコメント・doc が UI 要素について**「これは◯◯を表す」「常に◯◯している」**のように
断定していたら、その主張を UI 案のマークアップで裏取りする(`分類: ui-fidelity-misread`)。
`rules/ui-verification.md`「見るのはスクリーンショットではなくマークアップ」を実行しても、
**マークアップを見たうえで意味を取り違える**形は防げない(PR #199)。計画検証で一度
確かめていても、実装(特に doc コメント)は typecheck・lint・テストのどれも落とさずに
書き換えられるため、実装検証でも独立に確認する。

- **主張の対象になっている要素を、UI 案の全画面・全状態で横に並べる。** 1 箇所だけを見て
  「状態表示」「ボタンではない」と判断せず、同じ要素が他の画面・他の状態でどう描かれているかを
  確認する。差が **1 属性(`background` 等)しか無い**ことがあり、その 1 属性を見落とすと
  「一時的な状態」と「常在する要素」を取り違える(PR #199 の `◆` はドラッグ画面だけ
  背景色が違う常在スロットだった)
- **「対象が全体か部分か」「追加か置換か」を、マークアップの実測値で確認する。** 「帯が
  3 つ」のような主張は、画面全体の帯の数なのか、ある帯の中の一部(倍率の並びなど)の数
  なのかで意味が変わる(PR #173)
- 取り違えたまま進むと、結論(実装の方針)自体は変わらなくても、**次に読む人が誤った根拠を
  裏付けとして参照する**ことになるため、結論が変わらない指摘でも直す

## テストが守っているかの観点

**「その assert は落ちうるか」を頭の中で判断しない。** 実際に壊して確かめる。

- **その差分の中心の判断を「1 つ選ぶ」で終えず、独立した判断ごとにすべて壊すミューテーションを
  入れて全テストを走らせる。** 配線・フラグ・別ブランチがそれぞれ別の主張を持つ差分では、
  1 つだけ確かめて終えると残りが素通りする(`分類: test-coverage-gap`。壊しても 1942 件
  すべて通る箇所が同時に 3 つあった → PR #185、分岐を丸ごと消しても 2014 件すべて通った →
  PR #211。どちらもそのブランチ・その判断を**参照するテストが 1 件も無かった**のが原因)。
  落ちるテストが 1 件も無ければ、その判断はテストで守られていない。確かめたら必ず元へ戻す
  (`git status --porcelain` が空であることまで見る)
- 選ぶのは「PR 本文やコミットメッセージが理由を繰り返し書いていること」。そこが
  いちばん守られていると思い込みやすく、実際に抜けやすい
- **ミューテーションを入れる前に、その判断を確かめている入力が既定値と一致していないか確認する。**
  一致していると、規則そのものを壊すミューテーションでも既定値のほうで結果が変わらず通って
  しまう(`分類: test-default-input`。「保存済みに戻る」の通しテストが開いた直後の既定状態
  だけを見ていた → PR #173、通しのテストがすべて時計の開始時刻(既定値)を起点にしていた →
  PR #192)。`rules/testing.md`「既定値・フォールバックがある処理では、既定値と違う答えに
  なる入力を選ぶ」の入力を、レビュー側でも同じ観点で確かめる
- UI の差分では、**次の 6 つを 1 つずつ消す**。どれも「出すと決めたのに、消しても落ちない」が
  実際に起きている
  | 消すもの | 例 |
  |---|---|
  | アイコン | `<TypeGlyph>` を消す(PR #149 / #152 で 2 回とも落ちなかった) |
  | 読み上げ名 | ボタンの `aria-label` を消す |
  | 器 | 領域の `aria-label` を消す(`region` でなくなるが、中のボタンは名前で引ける) |
  | 状態からの配線 | props を定数へ固定する(`isInsertEnabled={true}` など) |
  | **出し分け** | **その部品を出さない側でも出す**(行き先ごとの `switch` を全部 `some` にする / PR #164 で 1 件も落ちなかった) |
  | 位置・大きさ | `absolute` / `relative` を消す |
- **出し分けは「出る側」だけをテストしていることが多い。** 出る側は画面を組めば自然に通るので
  先に書くが、出ない側は書き忘れても誰も気づかない(`rules/testing.md`「『出さない』を
  確かめるときは、入力から自明にならない側を見る」)
- **最後の 1 つは happy-dom では落とせない**(Tailwind を解決しないため)。class 名を assert する
  のは実装詳細のテストになるので、テストで留めずに**気づく手段が Storybook の視覚差分だけである
  ことをコードのコメントに書く**
- 落ちなかったら、テストを足してからもう一度同じミューテーションを入れ、今度は落ちることを見る
- **コメントが「どのテストが守っているか」を名指ししていたら、その主張ごと壊して確かめる。**
  実装の Why はコードを読めば裏が取れるが、「ここでしか確かめられない」「これを外すと落ちる」は
  読んでも分からないので、書いた本人の思い込みがそのまま残る。守っているはずのテストが
  1 件も落ちないなら、直すのはコメントのほう(PR #141 の `DraftField` の `key`、
  PR #164 の通しテストの冒頭コメントが実際にこれで、どちらも壊して初めて嘘だと分かった)
- **コメントや却下理由が「◯◯だからこうしている」と事実を主張していたら、その事実を確かめる。**
  テストの名指しだけでなく、「この class がこれを防ぐ」「あの型は 1 つの値に畳めない」も同じ
  (`分類: comment-mismatch`)。**確かめ方は主張の種類で決まる**
  | 主張の形 | 確かめ方 |
  |---|---|
  | この class / 属性が◯◯を防ぐ | **外した状態を実際に作って見る**。happy-dom では落ちないので Storybook か DevTools で見る |
  | あの型は◯◯できない | **できると書いてあるコードを探す**(`grep` で同じ型を扱っている既存モジュールを読む) |
  | ここでしか確かめられない | 守っているはずのテストを壊す(上記) |
  | この API / フックはこう振る舞う | **公式ドキュメント・型定義を実際に読む**(「ref は render 中に読めない」と書いたが、読めてしまう。React が推奨しないだけ → PR #173) |
  | この経路はまれにしか通らない(通らない) | **その経路に実際に到達する入力でコードを追う**(「巻き戻る状況でしか負にならない」と書いたが、mount 時 1 度だけ初期化される `now` により通常経路で毎回踏んでいた → PR #192) |
  | コメントが手法・使用箇所を説明している(`switch` にする、この定数はここで揃える 等) | **差分の最終形を読み、コメントの説明どおりになっているか付き合わせる**。計画時点の手法のまま実装が変わっていることがある(`switch` と書いたまま対応表になっていた → PR #173) |
  PR #171 は 2 つとも外していた。`shrink-0` は**守る対象を取り違えた上に実質 no-op**
  (縮まないのは `min-width:auto` のため)で、「影・タイポは 1 つの値に畳めない」は
  `token-control` の `valueTextOf` が実際に畳んでいた。どちらも**書いた時点では
  もっともらしく読める**ので、確かめない限り残る
- **経緯を Issue の見出し番号(「決定 B」等)だけで指していないか。** 番号はコードだけを
  読む人には何も伝わらず、Issue を開いて探させることになる。理由そのものをその場に書く
  (`分類: comment-mismatch`。rules/coding.md「経緯・実行履歴」の対象は本文だけでなく
  見出し番号の引用も含む → PR #192)
- **却下しなかった非自明な選択に、Why が本当に書かれているか確認する。** 「なぜこれでは
  ないのか」を自分に問い、答えがコードのそばに無いなら書く(`分類: comment-missing`)。
  レビューで聞かれて初めて書いた実例がある(`pressPointer` 等に `userEvent` を使わない
  理由が無く、聞かれるまでコードに残っていなかった → PR #173)
- **中心の判断が「2 つの状態が同時に成り立つとき、どちらを選ぶか」の形なら、その入力を作ったテストがあるかを数える。** 優先順位を反転するミューテーションは、**入力が片側だけなら挙動が変わらない**ので落ちない。既存テストが「A だけ壊す」「B だけ壊す」で揃っていたら、**A と B が同時に成り立つ入力**が 1 件も無いというサイン(PR #157 は「ファイルとドキュメントの両方が不正」を作るテストが無く、反転しても 1737 件すべて通った)

過去に実際に見つかった例: 「選んでいないときも見出しの帯は残す」という差分の中心の判断を
壊しても 297 件すべて通った / 帯の型アイコンを消しても 69 件すべて通った(いずれも PR #149)。

## 過剰ではない場合

次は「過剰」ではないので指摘しない。

- 外部との境界(`libs/`)で、外部ライブラリの例外を `Result` へ変換する処理
- Provider の外で呼ばれたときに落とす Context アクセサフック(`rules/coding.md` の例外)
- 仕様として既定値が決まっている値の解決(スキーマの `default` など)。
  これは失敗の穴埋めではなく仕様
- ユーザー入力の検証(`create` が `Result` を返す形の検証)。
  不正な値を存在させないための境界であって、防御ではない

## 指摘の扱い

- 受け入れるなら差分を直してから PR に出す
- 受け入れないなら、**なぜそのブロック / フォールバックが必要かをコードのそばにコメントで書く**
  (PR 本文ではなくコードに書く。次に読む人が同じ疑いを持つため)
- 同じ指摘が過去にも出ていたら `harness/records/` の記録対象になる
  (`harness-record` スキル)
