# 実装レビューの観点(過剰なブロック / フォールバック / 重複)

サブエージェントに実装差分を検証させるときの観点。フェーズ 6 で使う。
狙いは「動くけれど失敗を隠している」コードと、「編集のついでに増えた重複」を
PR に出す前に見つけること。

## 過剰なフォールバックの観点

- **既定値での穴埋め。** 失敗したときに空配列 / `0` / 空文字 / 「とりあえずの値」を
  返していないか。呼び出し側が失敗を知れなくなるので、`Result.err` / `Option.none` の
  まま返す
- **握りつぶし。** `Result` / `Option` を受け取って失敗側を捨てている箇所
  (`?? defaultValue`、`err` を無視した早期 return、`some` を見ずに `value` を読む)が無いか
- **二重の失敗表現。** `Result` を返す関数の内側で、さらに防御的な分岐を重ねていないか
- **到達しない分岐。** 型で既に排除されている状態に対する実行時チェックが残っていないか
  (直和で列挙したあとに「どれでもない場合」を書いている、など)
- **握りつぶした結果の隠蔽。** 失敗を握りつぶしたうえで UI に「何も起きなかった」ように
  見せていないか

## 過剰なブロックの観点

- **要らない存在チェック。** 必須の props / 引数に対する `if (!x) return` が「念のため」で
  入っていないか。必要なら型で必須にする
- **ガードの重複。** 呼び出し側と呼ばれる側の両方で同じ条件を弾いていないか。
  型で保証できる側に寄せる
- **フラグによる防御。** `useRef` で二重実行・連打を止めていないか(`rules/hooks.md`
  「ref をフラグにした『防御』」)。render に出る状態は `useState`、ボタンは `disabled`
- **ネストの深さ。** ブロックが 3 段を超えていないか。早期 return・関数分割で平らにする
- **無効化されたリント。** `biome-ignore` / `eslint-disable` が新たに入っていないか

## 重複の観点

計画では見えず、**編集しているファイルの中でついでに書き足した**ときに増える。
差分を見る段でしか捕まらないので、フェーズ 6 で必ず見る。

- **同じ走査・同じ判定を書き足していないか。** 新しく足した関数が、同じファイルや
  同じ層の既存モジュールと同じことをしていないか(`find` と `findIndex` のように
  戻り値だけが違う形も含む)。片方をもう片方に乗せて、走査を 1 箇所にする
- **組み込み型への操作を直書きしていないか。** 先頭を取る・範囲を見る・集合を反転する
  といった操作は `src/utils/` の `<型名>Ex` にある。`array[0]` を書く前に読む
- **テストヘルパーを 2 つ以上のファイルへ書いていないか。** 差分で複数のテストファイルを
  触ったなら、同じアクセサ・同じ操作をそれぞれに書いていないかを見る。
  置き場所は `rules/testing.md`「テスト用ヘルパーの置き場所」
- **同じ値を 2 箇所で計算していないか。** 親と子の両方で同じ判定を求めているなら、
  求めるのは 1 箇所にして渡す

## 過剰ではない場合

次は「過剰」ではないので指摘しない。

- 外部との境界(`libs/`)で、外部ライブラリの例外を `Result` へ変換する処理
- Provider の外で呼ばれたときに落とす Context アクセサフック(`rules/coding.md` の例外)
- 仕様として既定値が決まっている値の解決(スキーマの `default` など)。
  これは失敗の穴埋めではなく仕様
- ユーザー入力の検証(`create` が `Result` を返す形の検証)。
  不正な値を存在させないための境界であって、防御ではない

## 指摘の扱い

- 受け入れるなら差分を直してから PR に出す
- 受け入れないなら、**なぜそのブロック / フォールバックが必要かをコードのそばにコメントで書く**
  (PR 本文ではなくコードに書く。次に読む人が同じ疑いを持つため)
- 同じ指摘が過去にも出ていたら `.claude/harness/records/` の記録対象になる
  (`harness-growth` スキル)
