# 計画レビューの観点

サブエージェントに実装計画を検証させるときの観点。フェーズ 4 で使う。

## Contents

- プロンプトの雛形
- 妥当性の観点
- テストケースの観点
- 指摘の扱い

---

## プロンプトの雛形

````text
以下の実装計画を検証してほしい。この計画で実装に入ってよいかを判断し、
問題があれば具体的に指摘すること。実装・ファイルの変更はしないこと。

## ゴール
<ゴール>

## 計画
<変更するファイルと置くもの / テストケースの一覧 / 却下した案とその理由 / 未決の判断>

## 判断の拠り所(読むこと)
- rules/architecture.md — ロジックの帰属先・依存方向・services の責務
- rules/coding.md — Result / Option・型による境界・イミュータブル
- rules/naming.md — 名前と実体の一致
- rules/testing.md — 振る舞いのテスト・配置と命名

## 見てほしい点
1. 計画の妥当性
2. テストケースの十分さ

## 返し方
- 指摘は「どの観点に反しているか」と「代わりにどうするか」をセットで書くこと
- 問題が無いと判断した観点も、何を見てそう判断したかを 1 行で書くこと
  (「問題ありません」だけの返答は検証になっていない)
````

## 妥当性の観点

- **ゴールと計画が対応しているか。** ゴールへ寄与しない変更が混ざっていないか。
  逆に、ゴールに必要な変更が計画から抜けていないか
- **ロジックの帰属先が正しいか。** 判定・計算・変換が `services/` や features 層や
  呼び出し側のヘルパー関数に置かれようとしていないか。第 1 引数に取る型の
  コンパニオンオブジェクトへ置けないか(`rules/architecture.md`「services はドメインを
  探してから使う」の 1〜6)
  - **書かれている帰属の理由が、その型に固有の性質を指しているか。** 「第 1 引数の型が
    ◯◯だから」とだけ書いて、他の型でも同じ理由が成り立ってしまわないかを確かめていない
    計画は理由になっていない。置き場所自体が合っていても、理由が誤っていると次に似た値が
    出たときに同じ場所へ置いてよいか判断できなくなる(`分類: ownership-reasoning`、
    PR #162 / #173 / #192)
  - **ドメインが受け取る値に、入力欄側の解釈が紛れていないか。** 「空欄なら未設定へ戻す」
    「ピッカーは 6 桁しか返さない」のような規則をドメイン側で読み替えていないか。
    解釈はコントロール側に残し、ドメインには解釈済みの値(`Option` 等)を渡す
    (`rules/architecture.md`「逆向きも見る」、`分類: domain-input-convention`、PR #168)
  - **ドメインオブジェクトの置き場所を、実際に消費する feature の数で判断しているか。**
    1 feature でしか使わないのに `src/domains/` へ置こうとしていないか。逆に 2 つ以上の
    feature が必要なのに `features/<x>/domains/` に留めていないか(`rules/architecture.md`
    「配置の判断基準」、`分類: domain-scope-promotion`、PR #192)
- **依存方向を壊していないか。** `app → features → services → domains`。
  `components/` `hooks/` `utils/` `types/` にドメイン知識が流れ込んでいないか。
  I/O が `libs/` の外に出ていないか
- **名前の付いていない型が隠れていないか。** 引数が 4 つ以上になる中間関数、
  常に対で渡る 2 値、タプルでの受け渡しは「型がまだ無い」サイン
- **同じ操作が既にどこかに無いかを探したか。** 新しく足す関数・モジュールについて、
  **書く前に探した場所を計画に挙げる**。組み込み型への操作(先頭を取る、範囲を見る、
  集合を反転する)なら `src/utils/` を読む。ドメインの走査・判定なら、
  同じファイルと同じ層の既存モジュールを読む。探さずに新設を決めると、
  中身まで同じものを 2 つ持つことになる(PR #122 / #144)
  - **触るドメインの `index.ts` は、公開 API の一覧を実際に開いて読む。** 名前も引数の形も
    違うので、grep では見つからない。PR #148 は「部品を引く → binding を引く → prop 定義まで
    辿る」の 3 段を自前に書いたが、`ComponentSet.publicPropTarget` が同じことをしていた
    (既存の呼び出し側が別の API を使っていたのは、**そちらは別の情報も要るから**であって、
    同じ答えを得る近道が無かったからではない)
- **不正な状態が型で表現できてしまわないか。** boolean や `Option` の組み合わせで
  矛盾した状態が作れるなら直和で列挙する。検証済みが前提の関数は、検証済みを表す型で受け取る。
  次は `harness/records/`(`illegal-state` 分類)に繰り返し出た形。計画に同じ形が
  無いかを 1 つずつ確認する
  - **辞書引きの「まだ無い」と「0」が同じ顔にならないか。** `Record<string, number>` を
    キーで引く計画は、定義の無いキーも型上 `number` になる(`noUncheckedIndexedAccess` が
    無いため)。区別したいなら `(名前, 値)` の並びにする(PR #124)
  - **出し分けの最後の枝がラベルの無い受け皿になっていないか。** `if` の連なり・
    nested ternary の最後の分岐は、行き先を足し忘れても黙って通る。`switch` を
    `default` 無しで書き、戻り値の型を `ReactNode` ではなく `ReactElement` にする
    (PR #139 / #157)
  - **`as const` から union を export する計画に `satisfies` と型テストが付いているか。**
    隣接する既存の語彙(`TypographyFields` 等)と縛り方を揃える(PR #141)
  - **本来届かないはずの `Option.none` / 分岐を計画で作っていないか。** `findX` → `findY`
    のような多段の参照は、途中の `none` が「起こり得ないのに UI が持つ枝」になる。
    1 段で引ける型・既存の公開 API を先に探す(PR #148)
  - **型エイリアスが構造を変えていないか。** `type A = B` のように別名を足すだけの新設は
    しない(`rules/coding.md`「構造が変わらない型エイリアスの新設は禁止」、PR #149)
  - **同じ位置づけの既存の型が `Option` で表しているものを、この計画だけ空配列 / 既定値へ
    潰していないか。** 隣の型と揃っているかを見る(PR #162)
  - **1 つの型に、本来直交する状態が同居していないか。** ある枝でしか意味を持たない
    フィールド(色トークンにしか無い swatch 等)を共通の親に持たせていないか(PR #168)
- **状態を持たず導出すると決めたなら、導出の入力が失われる操作を数えたか。**
  「持つと矛盾した状態が作れるから導出にする」は正しい判断だが、導出の入力
  (選択・入力値・直前の操作)が**無くなる操作**があると、そのたびに既定値へ落ちる。
  入力を消す操作(選択の解除、対象の削除、undo、外部変更の取り込み)を挙げ、
  そこで既定値へ落ちてよいかを確かめる。よくないなら、それは導出では表せない
  「見ている場所」なので、どこに持たせるかまで計画に書く
- **失敗と不在の表現。** 失敗が `throw`、不在が `undefined` / `null` になっていないか
- **語彙が `string` のまま残っていないか。** 仕様(`docs/`)が列挙している語彙は union にする
- **却下案の理由が理由になっているか。** 「複雑だから」「好みではない」は理由ではない。
  どの規約・どの制約に反するかまで降りているか
- **変更で壊れる既存の資産を洗い出しているか。** grep での数え上げ・一括置換の件数検算は
  SKILL.md フェーズ 3 の必須手順(呼び出し側を grep で数える・収集条件を実例に当てて検算する)
  で行っている前提なので、ここでは**ファイル表に挙がっているか**だけを見る。あわせて、
  新しく足すテストが既存のテストと同じ振る舞いを見ていないかも確認する(重複はテストにも効く)
- **消すものがある計画なら、それを最後に使っていたものを数えたか。** ボタン・props・
  メソッドを 1 つ消すと、その先が芋づるで死ぬ。**typecheck も lint も落ちない**(戻り値
  オブジェクトの未使用プロパティ・実装と食い違うコメント・公開したままの `export`)ので、
  計画の段階で数えないと死んだコードが残る。数えるのは次の 3 つ
  | 見るもの | 探し方 |
  |---|---|
  | 呼び出し元が 0 になる props / メソッド | `grep -rn "\.<名前>\b"` で残りの参照を数える |
  | 消したものに言及しているコメント | `grep -rn "<消す名前>"` を `src/` 全体にかける |
  | 画面から消える操作の代わりの入口 | ショートカット等が本当に届くかを、通しのテストで確かめる |
- **部品から位置・大きさを外す(別の器へ移す)計画なら、その部品の単体ストーリーが位置を与えているかを見る。** decorator が位置を持っていないと、実画面は変わっていないのに**ストーリーだけ**が変わり、VRT が赤くなる。**テストでは絶対に落ちない**(happy-dom は Tailwind を解決しない)ので、計画で `*.stories.tsx` を数えるときは「呼び出しがあるか」だけでなく「位置を与えているか」まで見る(PR #157)
- **表示の文言と「空のとき」と「並び順」が決まっているか。** UI を変える計画では、見出しや
  ラベルの**綴り**(既存の日本語を UI 案の英語に寄せるのか)と、**対象が 0 件のときに
  何を出すか**、**複数出るときの並び**が抜けやすい。UI 案(静止画)からは決まらないので、
  計画の時点で決めて Issue に残す(並びは、先頭の数件しか出さない一覧では見える差になる)
- **UI 案の行が何を指しているかを、他の画面と突き合わせて確かめたか。** 1 つの画面だけを見て
  読むと、行が指している実体を取り違える。**行に出ている名前を他の画面(`Assets` の一覧・
  `Layers` のツリー)で探し、どこに居るものかを確かめる。** 仕様(`docs/`)と突き合わせて
  「その行が成立しうるか」も見る。PR #148 は `Used by` の `◆ primary-button.background` を
  インスタンスの行と読んだが、`primary-button` は `Assets` の部品定義側にしか居らず、
  `background` はその部品の公開 prop でもないので、インスタンスの行としては成立しなかった
  (取り違えたまま進むと、集める対象そのものが変わる)
- **UI 案の要素が実際に何を表しているかを、単一の画面・単一の状態だけを見て断定していないか
  (`分類: ui-fidelity-misread`)。** 「強調して出す」のような書き方は、既存の要素を
  **追加**するのか**置換**するのかを決めていない(PR #162)。常在する要素と一時的な状態表示は
  見た目が近いことがあり、**同じ要素を全画面・全状態で並べて属性を比較する**まで裏を取る。
  差が 1 属性(`background` 等)しか無いこともある(PR #199)。実装検証でも同じ観点で
  コメント・doc の主張を確認する(`implementation-review.md`「UI 要素の意味の観点」)
- **未決の判断が残っていないか。** 残っているなら、実装中に決めてよいものか、
  先に決めるべきものかを判断する
- **既存のコードが前提にしている不変条件を、この計画が崩さないか。** doc / Why コメントが
  「常に◯◯である」と書いている前提(`分類: plan-integration-coverage`)は、その前提を
  崩す変更(単一選択 → 複数選択、単一 artboard → 複数 artboard 等)が来ると同時に嘘になる。
  前提を書いているコメントを grep で探し、崩れるなら計画に書き直しを含める(PR #227 は
  「選択は常に今見ている artboard の中にある」という Why コメントが複数選択の追加で崩れる
  ことを計画の時点で拾えていなかった)

## テストケースの観点

- **振る舞いを書いているか。** 「◯◯のとき□□になる」の形か。
  関数名・内部構造の語彙(「`calculateZIndex` が 2 を返す」)になっていないか
- **境界と異常系があるか。** 空 / 1 件 / 最大 / 循環 / 見つからない、など。
  正常系だけの一覧になっていないか
- **失敗の分岐を通っているか。** `Result.err` / `Option.none` を返す経路のテストがあるか
- **カテゴリの分け方。** `{対象}.{カテゴリ}.test.ts` のカテゴリが観点になっているか
  (`normal` / `edge` / 仕様領域)
- **仕様に根拠があるか。** `docs/` に無い振る舞いをテストで固定しようとしていないか
  (実装の偶然の挙動を仕様化しない。`分類: plan-integration-coverage`。PR #227 は
  「同じ名前 2 つは単一選択になる」というテストケースを計画に挙げたが、名前は単一名前空間で
  一意なためどの経路からも重複は来ず、根拠が無いまま計画に残っていた)
- **モックを前提にしていないか。** `domains/` `services/` は実物で検証できるはず。
  モックが要るなら設計側の問題
- **ゴールが「画面から届く経路を通すこと」なら、その経路を通すテストが一覧にあるか
  (`分類: plan-integration-coverage`)。** ドメインが既にあって配線だけを足す回で抜けやすい。
  単体(ドメイン / reducer / 単体 UI)だけを揃えると、**配線が切れていても全テストが緑になる**。
  通しは `opened-document-editor/__tests__/` が担当で、そこにしか無い前提(選択・行き先の
  切り替え・親が持つ `key`)は単体では通らない。**PR #164 で一度この観点を足したのに
  PR #227 で同じ形(`useNodeActions` → `PropertyPanel` の配線切れ)が再発している。**
  計画のテスト一覧に「ドメイン」「reducer」「単体 UI」しか無いなら、それだけで
  `opened-document-editor` 配下の通しテストが要らないと確定したのか、単に挙げ忘れて
  いないかを 1 行で書かせる

## 指摘の扱い

- 受け入れるなら**計画を直してから**実装に入る
- 受け入れないなら、**なぜ受け入れないかを Issue に書く**。書かずに実装へ進まない
- 指摘が計画の前提(ゴール)を揺らしている場合は、フェーズ 1 まで戻る
