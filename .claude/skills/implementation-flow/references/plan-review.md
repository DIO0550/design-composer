# 計画レビューの観点

サブエージェントに実装計画を検証させるときの観点。フェーズ 4 で使う。

## Contents

- プロンプトの雛形
- 妥当性の観点
- テストケースの観点
- 指摘の扱い

---

## プロンプトの雛形

````text
以下の実装計画を検証してほしい。この計画で実装に入ってよいかを判断し、
問題があれば具体的に指摘すること。実装・ファイルの変更はしないこと。

## ゴール
<ゴール>

## 計画
<変更するファイルと置くもの / テストケースの一覧 / 却下した案とその理由 / 未決の判断>

## 判断の拠り所(読むこと)
- rules/architecture.md — ロジックの帰属先・依存方向・services の責務
- rules/coding.md — Result / Option・型による境界・イミュータブル
- rules/naming.md — 名前と実体の一致
- rules/testing.md — 振る舞いのテスト・配置と命名

## 見てほしい点
1. 計画の妥当性
2. テストケースの十分さ

## 返し方
- 指摘は「どの観点に反しているか」と「代わりにどうするか」をセットで書くこと
- 問題が無いと判断した観点も、何を見てそう判断したかを 1 行で書くこと
  (「問題ありません」だけの返答は検証になっていない)
````

## 妥当性の観点

- **ゴールと計画が対応しているか。** ゴールへ寄与しない変更が混ざっていないか。
  逆に、ゴールに必要な変更が計画から抜けていないか
- **ロジックの帰属先が正しいか。** 判定・計算・変換が `services/` や features 層や
  呼び出し側のヘルパー関数に置かれようとしていないか。第 1 引数に取る型の
  コンパニオンオブジェクトへ置けないか(`rules/architecture.md`「services はドメインを
  探してから使う」の 1〜6)
- **依存方向を壊していないか。** `app → features → services → domains`。
  `components/` `hooks/` `utils/` `types/` にドメイン知識が流れ込んでいないか。
  I/O が `libs/` の外に出ていないか
- **名前の付いていない型が隠れていないか。** 引数が 4 つ以上になる中間関数、
  常に対で渡る 2 値、タプルでの受け渡しは「型がまだ無い」サイン
- **不正な状態が型で表現できてしまわないか。** boolean や `Option` の組み合わせで
  矛盾した状態が作れるなら直和で列挙する。検証済みが前提の関数は、検証済みを表す型で受け取る
- **失敗と不在の表現。** 失敗が `throw`、不在が `undefined` / `null` になっていないか
- **語彙が `string` のまま残っていないか。** 仕様(`docs/`)が列挙している語彙は union にする
- **却下案の理由が理由になっているか。** 「複雑だから」「好みではない」は理由ではない。
  どの規約・どの制約に反するかまで降りているか
- **未決の判断が残っていないか。** 残っているなら、実装中に決めてよいものか、
  先に決めるべきものかを判断する

## テストケースの観点

- **振る舞いを書いているか。** 「◯◯のとき□□になる」の形か。
  関数名・内部構造の語彙(「`calculateZIndex` が 2 を返す」)になっていないか
- **境界と異常系があるか。** 空 / 1 件 / 最大 / 循環 / 見つからない、など。
  正常系だけの一覧になっていないか
- **失敗の分岐を通っているか。** `Result.err` / `Option.none` を返す経路のテストがあるか
- **カテゴリの分け方。** `{対象}.{カテゴリ}.test.ts` のカテゴリが観点になっているか
  (`normal` / `edge` / 仕様領域)
- **仕様に根拠があるか。** `docs/` に無い振る舞いをテストで固定しようとしていないか
  (実装の偶然の挙動を仕様化しない)
- **モックを前提にしていないか。** `domains/` `services/` は実物で検証できるはず。
  モックが要るなら設計側の問題

---

## 指摘の扱い

- 受け入れるなら**計画を直してから**実装に入る
- 受け入れないなら、**なぜ受け入れないかを Issue に書く**。書かずに実装へ進まない
- 指摘が計画の前提(ゴール)を揺らしている場合は、フェーズ 1 まで戻る
