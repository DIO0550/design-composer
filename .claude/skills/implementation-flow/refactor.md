# `flow:refactor`: 振る舞いを変えず、既存のテストで確かめる

`flow:refactor` の Issue で、`SKILL.md` の各フェーズに**追加する**手順。記載のないフェーズは `SKILL.md` のままとする。

**振る舞いが変わっていない根拠は、書き換えていない既存のテストだけ。** テストを実装と一緒に書き換えると、緑のままでも振る舞いが変わっていないとは言えなくなる。

## 書き換えない範囲

下の 1 つ目のコマンドの pathspec が**書き換えない範囲**（テストとその共有物・判定表・テストのセットアップ・ストーリー）、2 つ目のコマンドが拾う行が**テストを走らせる配線**にあたる。配線を消すとテストを書き換えずに実行対象から外せてしまうため、どちらもフェーズ 5 で親が確認する。

```bash
git diff <第 1 工程のコミット> HEAD -- \
  ':(glob)**/__tests__/**' ':(glob)**/*_test.rs' ':(glob)**/test_support.rs' \
  ':(glob)**/*-cases.sh' ':(glob)**/cases-fixtures.sh' ':(glob)**/cases-report.sh' \
  src/test-setup.ts ':(glob)**/*.stories.tsx' ':(glob)**/__stories__/**'
git diff -U0 <第 1 工程のコミット> HEAD -- src-tauri .github/workflows vite.config.ts harness/githooks/pre-push \
  | grep -E '^-.*(mod [a-z0-9_]+_test;|mod test_support;|-cases\.sh|setupFiles)'
```

書き換えない範囲で**しないこと**:

- assert を含むテスト本文（期待値・入力・テスト名）を変えない（下の「してよいこと」に当たる書き換えだけが例外）
- テストを消さない（`skip` を含む）。配線も消さない（移動表に記載した移動元の削除を除く）
- 参照先を別の実装やスタブへ向け替えない

書き換えない範囲で**してよいこと**（これ以外はしない）:

- テストを追加する
- 計画の移動表にあるファイルを移動する（移動に伴う中身の変更は下の 2 つに限る）
- 参照先（import パス・`mod` の位置）を、計画の移動表にある移動先へ書き換える（同じ対象を指したまま場所が変わる書き換えに限る）
- 計画の改名表（旧名 → 新名）にある名前を本文中でも書き換える（表にない名前を変えると、`parse` → `parseLoose` のような実装の差し替えが改名に紛れて判別できなくなる）

## フェーズ 3: 計画に足すもの

- **守っている既存テスト。** 触るコードを守っているテストファイル、実行コマンド、件数
- **現状を固定するテスト。** 守っている既存テストがない範囲には、今のコードで通るテストを先に足す計画にする。足すものがなければ「無し」と書く（フェーズ 5 の第 1 工程を省く）
- **移動表**（ファイル・モジュールの移動元 → 移動先）と**改名表**（旧名 → 新名）。なければ「無し」と書く
- **移動表に `*.stories.tsx` が入る場合、** story の id が変わることを予告し、改名表に旧 `title` → 新 `title` を載せる（`title` はフォルダ階層と一致することを `story-title-violations.py` が検査するため、ファイル移動に伴い `title` も変わる）
- 仕様の変更や既存テストの書き換えが必要だと分かったら、`flow:refactor` に合わない作業なので計画せずに止め、`SKILL.md` フェーズ 1「種類の確定」の 6 に従う

## フェーズ 5: 工程ごとに書かせるものと確かめること

2 工程に分ける仕組み（工程の渡し方・第 1 工程のコミット・第 1 工程を省く場合）は `SKILL.md` フェーズ 5 を参照。

1. **第 1 工程（`工程: 現状の固定`）: 現状を固定するテストだけを足させる。** 今のコードのまま、足したテストを実行する検査が通ることを返させる。計画の「現状を固定するテスト」が「無し」なら省く
2. **第 2 工程（`工程: リファクタ`）: リファクタさせる。** commit したら、親が「書き換えない範囲」の 2 つのコマンド出力を確認する
   - 1 つ目の出力に含まれてよいのは、追加したテストと「してよいこと」に当たる書き換えだけ
   - 2 つ目の出力に出た削除行が、移動表に記載した移動元に対応するか確かめる
   - 外れていたら、該当行を指摘として `implementer` に戻す

これら 2 つのコマンドは目視確認を省くものではない。import の書き換えを除いて比較する機械検査は #1406 で判定表付きのスクリプトにする（判定表のないコードをこの文書に埋めない）。

## フェーズ 6: 直しでも既存テストを変えない

- 採用した指摘を直すときも「書き換えない範囲」の規則は同じ。テスト不足の指摘には、既存テストを書き換えず新しいテストを足して応える
- 修正のたびにフェーズ 5 の 2 つのコマンド出力を確認し直す
- **`test-reviewer` はそのまま呼ぶ。** 振る舞いが変わっていない根拠は既存テストだけなので、それが実装を守っているかを実測する必要がある

## フェーズ 7: VRT の差分を承認しない

- **`Storybook Visual Regression` の差分は `visual-approved` で通さない。** 振る舞いを変えない変更で見た目が変わったなら直す対象（`rules/ui-verification.md`「Storybook の視覚差分（VRT）」）
- **改名表にない story の `title` や export 名を変えない。** 変えると story の id が変わり、VRT は差分ではなく new と deleted の組として扱う。new は落ちないため見た目がずれても緑のまま通ってしまう（`harness/case-law/process.md`「`vrt-blind-spot`」）。**ストーリーファイルを動かす、または `title` / export 名を変える場合は、** 計画で id 変更を予告し（フェーズ 3）、第 1 工程のコミットと HEAD をそれぞれ playwright-cli で撮影して目視で比べる（`rules/ui-verification.md`「表示確認」）
- **story の `args` を変えない。** 描画される中身が変わると、差分が出ても出なくても比較したことにならない
