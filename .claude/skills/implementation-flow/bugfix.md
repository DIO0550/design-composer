# `flow:bugfix`: 再現を先に固定してから直す

`flow:bugfix` の Issue で、`SKILL.md` の各フェーズに**追加する**手順。記載のないフェーズは `SKILL.md` のままとする。

**修正より先に、症状を再現して落ちるテストを書いてコミットする。** 修正と同時に書いたテストは、修正前のコードで本当に落ちていたか誰も確認できず、直したつもりで別の箇所を直していても通ってしまう。

## フェーズ 1: ゴールに症状を書く

ゴールに加えて、**症状を次の 3 つに分けて** Issue に書く。

- 再現手順（どの入力・操作・状態から起きるか）
- 期待する結果（拠り所となる `docs/` の節があれば添える）
- 実際の結果

再現手順が書けないならゴールが決まっていない（`SKILL.md` フェーズ 1 のとおり止める）。

## フェーズ 3: 計画の先頭に再現テスト

テストケース一覧の**先頭**に再現テストを置き、次を記載する。

- 置くファイルとテスト名（仕様の文 → `rules/testing.md`）
- 再現テストを走らせる検査コマンド（対象別の対応は `.claude/agents/test-reviewer.md` 冒頭を参照）
- 修正前のコードで、**どの assert がどの値で落ちるか**（期待値と実際の値。判定表なら該当ケースの期待と実際）
- **今ある公開 API だけで書く。** 修正で追加する API を呼ぶと、修正前コードでは実行時の `TypeError` や import 失敗で落ちて assert まで届かない（vitest は型を検査しない）
- **第 2 工程（修正）で書き換える既存テストと同じファイルに置かない。** 同じファイルだとフェーズ 5 の `git diff --exit-code` が再現テストの書き換えと既存テストの書き換えを見分けられない
- **自動テストで再現できない場合は、その理由と代替の確認方法**（playwright-cli で撮影する等）を書く。このときは再現テストを置かず第 1 工程を省く
- 期待する結果の拠り所が `docs/` にも既存テストにもないと分かったら、それは仕様変更であり `flow:bugfix` に合わない作業なので、計画せずに止めて `SKILL.md` フェーズ 1「種類の確定」の 6 に従う

## フェーズ 5: 工程ごとに書かせるものと確かめること

2 工程に分ける仕組み（工程の渡し方・第 1 工程のコミット・第 1 工程を省く場合）は `SKILL.md` フェーズ 5 を参照。

1. **第 1 工程（`工程: 再現テスト`）: 再現テストだけを書かせる。** 修正はさせない
   - 返ってきた検査出力で、**再現テストだけが計画どおりの assert で失敗している**ことと、それ以外の検査（`pre-push` および `pnpm run test:run` の残り）が通っていることを親が確かめる。再現テストが通った、assert 以外（`TypeError` や import 失敗等）で落ちた、他のテストも落ちた、のいずれかなら再現になっていないため計画へ戻す
2. **第 2 工程（`工程: 修正`）: 修正させる。** 再現テストは書き換えさせない
   - 返ってきたら、親が次のコマンドを実行して終了コード 0（再現テストのファイルに変更がない）であることを確かめる

     ```bash
     git diff --exit-code <第 1 工程のコミット> -- <再現テストのファイル>
     ```

   - 同じ再現テストが通っていることを、返ってきた検査結果で確かめる

**第 1 工程を省いた場合**（フェーズ 3 で自動テストによる再現不可と判断した場合）は、計画に書いた代替の確認方法を第 2 工程の前後で行い、修正前は症状が出て修正後は出ないことを Issue に書く。

## フェーズ 6: 直しのたびに同じコマンド

採用した指摘を `implementer` に直させたら、そのたびにフェーズ 5 の `git diff --exit-code` を再実行する。修正対応でも再現テストは書き換えさせない。

## フェーズ 7: PR 本文に 2 つの工程のコミット

PR 本文に、**第 1 工程のコミット**（再現テスト）と第 2 工程以降の**修正のコミット**を並べて書く。読み手が前者だけをチェックアウトしてテストが落ちることを確かめられるようにするため。第 1 工程を省いた場合は、その理由と代替の確認方法の結果を書く。
