# 検証の周回

`implementation-flow` のフェーズ 4 とフェーズ 6 の第 1 段で使う。**上限はフェーズごとに初回を含めて 3 周。**

## 各周の進め方

1. 初回の検証範囲は各フェーズの手順に従う。2 周目以降の検証範囲は、**前周で採用した指摘を出した観点と、そのために直した差分だけ**。観点は指摘の分類タグではなく、レビューで実際に使った観点の名前で渡す。周辺は影響を確かめるために参照できるが、全体の再レビューはしない
2. 依頼したすべての観点から、根拠のある検証結果を受け取る。修正に起因する依頼範囲内の新しい指摘も採否を決める。範囲外の発見は別記し、この周の採用件数にも次の再検証範囲にも含めない
3. 下の表で行き先を決め、各周の採否と理由を Issue に記録してから移る。**未返却・検証失敗・修正差分なしは「指摘なし」ではない。** 差分や結果が欠けていれば同じ周の不足として扱い、判断待ちのときも周回を増やさない。採用を取り消して修正しない場合はその理由を記録し、採否を決めた周で行き先を再判定する

## 収束と打ち切り

上から順に判定する。

| 状態 | 行き先 |
| --- | --- |
| [前提を確かめ直す合図](https://github.com/DIO0550/design-composer/issues/1483) が出た | 上限を待たず、前提の再確認へ |
| 結果がそろい、前周の採用分が解消済みか根拠付きで採否を見直し済み、判断待ちなし、かつ今回の採用が 0 件 | 収束。各フェーズの次の手順へ |
| 3 周目の採否が確定し、採用した指摘が残った | 前提の再確認へ。4 周目も、未検証の修正を入れて次の手順へ進むこともしない |
| まだ上限前で採用した指摘があり、採否と修正方針が確定した | 採用分を直し、次の周で確かめる |

合図は各周の開始前と、採否の決定や差し戻しの後に確認する。#1483 の手順が未導入なら、計画が v3 に達したとき、または同じ観点で `planner` / `implementer` に 2 回差し戻したときを合図とする。未導入のため再確認へ移れないときは、移る理由（合図または上限）と確かめ直す前提、未解決の指摘を Issue に書いて判断を待つ。収束扱いでは先へ進まない。

## Issue に残す記録

[検証の採否の書式](https://github.com/DIO0550/design-composer/issues/1481) に合わせ、周ごとに 1 件残す。見出しのフェーズ番号を置き換え、周回番号は見出しに足さない。

```markdown
## 検証の採否（フェーズ 4）
セッション: <URL>

第 <N> 周 / 対象: <計画の版または実装のコミット>
再検証の範囲: <直す前後の版またはコミットと、対象観点>

| 観点 | 指摘 | 採否 | 理由 |
| --- | --- | --- | --- |
| <観点> | <指摘または無し> | <採用・不採用・保留・対象外> | <判断の根拠> |

採用: <件数> 件
次: <次の周・次の手順・前提の再確認・判断待ち>
```

初回の範囲には計画全体または PR 全体の差分と書く。フェーズ 6 では見出しを `## 検証の採否（フェーズ 6）` にする。採用が 0 件の周も省かず、前周の採用分がある場合は解消を確認した根拠または採否を見直した理由を添える。
