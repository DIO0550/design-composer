# 実装の検証: 受け取るものと指摘の返し方

`implementation-flow` フェーズ 6 の観点別エージェント(`.claude/agents/` の `*-reviewer.md` の
うち `plan-reviewer` 以外)が共通で従う。**観点は各エージェントの定義が持ち、ここは受け取るもの・
返し方・指摘しないものだけを持つ。** どれを呼ぶか・起動の順序は `SKILL.md` のフェーズ 6 が持つ。

## 受け取るもの

- **ゴール**
- **計画と却下案** — Issue に書いた計画と、却下した案とその理由。却下済みの案を、新しい根拠
  なしに再提案しない
- **差分** — `git diff` の出力、または変更したファイルのパス一覧

入っていない項目があれば、それ自体を指摘として返す。

## 指摘の書式

1 件ごとに次の項目を持たせる。

| 項目 | 書くこと |
| --- | --- |
| 分類 | `.claude/skills/harness-record/templates/record.md`「分類の語彙」から 1 つ。当てはまらなければ `なし` |
| 重大度 | 重大 / 高 / 中 / 低(下の目安) |
| 信頼度 | 高 = 実測・再現した / 中 = コードで経路を辿れた / 低 = 推測(未検証と明記する) |
| 証拠 | `ファイル:行` と、そこに書かれているもの |
| 起きる場面 | どの入力・操作・状態で問題になるか |
| 結果 | 起きたら何が壊れるか・誰が困るか |
| 直す方向 | 代わりにどうするか。パッチは書かない |
| 根本原因か症状か | 症状なら、どの根本原因から出ているか |

| 重大度 | 目安 |
| --- | --- |
| 重大 | `.dcmp` が壊れる・任意のファイルを読み書きできる、のように取り返しがつかない |
| 高 | ゴールを満たさない・利用者に見える誤動作・CI が落ちる |
| 中 | 規約から外れ、次の変更で壊れやすくなる |
| 低 | 読み手が迷う程度 |

- **自分の担当の中で同じ根本原因から出ている指摘は 1 件に束ね**、症状はその中に並べる
- **観点ごとに見出しを立て、該当が無い観点も「無し」と、何を見てそう判断したかを 1 行で書く**
  (観点を省略しない)

## 指摘しないもの

- **数合わせの指摘。** 重要な問題が見つからなければ、そう書いて終える
- **証拠の無い理論上の可能性を、既存の欠陥として書かない。** 挙げるなら信頼度を「低」にする
- **好み。** 規約(`rules/`)・仕様(`docs/`)・実害のどれにも結び付かないものは挙げない
- **差分と関係の無い既存の問題。** 差分がそれを悪化させる・前提にしているときだけ挙げる
- **発生確率も影響も低いもの**は、挙げるなら対処する価値があるかを添える
- **担当外の観点。** 見つけたら、担当のエージェント名を添えて 1 行に留める

指摘する前に、**差分の箇所だけでなく呼び出し元・データの流れ・影響範囲まで辿る**。差分の
その行だけを見た指摘は、呼び出し側で既に守られていることがある。見るほど新しい指摘が
出なくなったら、そこで打ち切ってよい。

## ファイルを変更しない

**指摘だけを返す。実装の修正はしない。** 作業ツリーを書き換えてよいのはミューテーションを当てる
`test-reviewer` だけで、その後始末は `test-reviewer` の定義が持つ。

- **Bash を持つエージェントは、呼ばれた直後に `git status --porcelain` を控え、返す前に
  同じであることを確かめる**
- **UI 案(`docs/Design Composer.html`)を展開するときは、`mktemp` で自分専用のパスへ書く。**
  `rules/ui-verification.md` の手順どおり固定のパスへ書くと、並列で動いている他のエージェントの
  書きかけを読む
