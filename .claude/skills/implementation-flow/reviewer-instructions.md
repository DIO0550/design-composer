# 実装の検証: 観点別のレビューエージェントへの共通の指示

`implementation-flow` フェーズ 6 の観点別エージェント（`.claude/agents/` の `*-reviewer.md` のうち `plan-reviewer`・`investigation-reviewer` 以外）が共通で従う指示。**観点は各エージェント定義に記載し、ここには観点に依存しない共通ルールだけを置く。** 呼ぶ条件と起動順は `SKILL.md` のフェーズ 6 を参照。

上記以外のエージェントにも適用する節は、その節の冒頭に適用範囲を明記する。

## 受け取るもの

- **ゴール**
- **計画と却下案** — Issue に書いた計画と、却下した案とその理由。却下済みの案を新しい根拠なしに再提案しない
- **差分** — `git diff` の出力、または変更したファイルのパス一覧
- **再検証の対象**（第 1 段の 2 周目以降） — 修正前後のコミット間の差分 / 前周から持ち越した指摘と観点。指定された観点で修正差分を検証する。周辺は修正の影響を辿るために読む

欠けている項目があれば、それ自体を指摘として返す。

## 指摘の書式

この節のうち、表の「分類」行と「指摘には形の名前を添える」「再検証では指定された観点だけを検証する」の箇条は `plan-reviewer`（`.claude/agents/plan-reviewer.md`）にも適用する（その他の項目・箇条は実装の検証向け）。`investigation-reviewer`（`.claude/agents/investigation-reviewer.md`）にはこの節のすべてを適用する。

指摘 1 件ごとに次の項目を含める。

| 項目 | 書くこと |
| --- | --- |
| 分類 | `.claude/skills/harness-record/templates/record.md`「分類の語彙」から 1 つ。当てはまらなければ `なし` |
| 重大度 | 重大 / 高 / 中 / 低（下の目安） |
| 信頼度 | 高 = 実測・再現した / 中 = コードで経路を辿れた / 低 = 推測（未検証と明記する） |
| 証拠 | `ファイル:行` と、そこに書かれている内容 |
| 起きる場面 | どの入力・操作・状態で問題になるか |
| 結果 | 起きたら何が壊れるか・誰が困るか |
| 直す方向 | 代わりにどうするか。パッチは書かない |
| 根本原因か症状か | 症状なら、どの根本原因から生じているか |

| 重大度 | 目安 |
| --- | --- |
| 重大 | `.dcmp` が壊れる・任意のファイルを読み書きできるなど、取り返しがつかない |
| 高 | ゴールを満たさない・利用者に見える誤動作・CI が落ちる |
| 中 | 規約から外れ、次の変更で壊れやすくなる |
| 低 | 読み手が迷う程度 |

- **指摘には形の名前を添える。** 分類欄には上の語彙だけを書き、各定義の本文にある判例の見出し（判例 `plan-file-omission` 等）や表の「形の名前」列の名前があれば括弧で添える。なければ観点の名前（太字の文をそのまま）を添える
- **自分の担当内で同じ根本原因から出ている指摘は 1 件に束ね、** 症状をその中に並べる
- **観点ごとに見出しを立て、該当がない観点も「無し」と、何を見てそう判断したかを 1 行で書く**
- **再検証では指定された観点だけを検証する。** 前周から持ち越した指摘が解消したかを観点ごとに根拠とともに返し、範囲外で目についたものは別記する

## 指摘しないもの

- **数合わせの指摘。** 重要な問題がなければ、そう書いて終える
- **証拠のない理論上の可能性を、既存の欠陥として書かない。** 挙げるなら信頼度を「低」にする
- **好み。** 規約（`rules/`）・仕様（`docs/`）・実害のどれにも結び付かないものは挙げない
- **差分と関係のない既存の問題。** 差分がそれを悪化させる、または前提にしているときだけ挙げる
- **発生確率も影響も低いもの**は、挙げるなら対処する価値があるかを添える
- **担当外の観点。** 見つけたら担当のエージェント名を添えて 1 行に留める

指摘する前に、**差分の箇所だけでなく呼び出し元・データの流れ・影響範囲まで辿る**。差分の行だけを見た指摘は、呼び出し側で既に守られていることがある。確認を続けても新しい指摘が出なくなったら、そこで打ち切ってよい。

## ファイルを変更しない

この節は `planner`（`.claude/agents/planner.md`）・`investigator`（`.claude/agents/investigator.md`）・`investigation-reviewer`（`.claude/agents/investigation-reviewer.md`）にも適用する。

**指摘だけを返し、実装の修正はしない。** 観点別エージェントのうち作業ツリーを書き換えてよいのはミューテーションを当てる `test-reviewer` だけであり、その後始末は `test-reviewer` の定義に従う（実装の書き換えは `implementer` の担当）。

- **Bash を持つエージェントは、呼ばれた直後に `git status --porcelain` と `git rev-parse HEAD` を控え、返す前に両方が一致していることを確かめる**
- **挙動を再現して確かめるときは、`mktemp -d` の一時ディレクトリで行う。** 作業ツリー内で書き換えると、並列稼働中の他エージェントがそれを実装として読んでしまう
- **UI 案（`docs/Design Composer.html`）を展開するときも、`mktemp` で自分専用のパスへ書き出す。** `rules/ui-verification.md` の手順どおり固定パスへ書くと、並列稼働中の他エージェントの書きかけを読んでしまう
