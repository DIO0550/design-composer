# 記録のテンプレート

`harness/records/pr-<番号>.md` へコピーして使う。

## テンプレート

````markdown
# PR #<番号> <タイトル>

- マージ日: <YYYY-MM-DD>
- 関連 Issue: #<番号>
- 差分規模: <変更ファイル数> ファイル / +<追加行> -<削除行>

## ゴールと結果

<Issue に書いたゴールと、実際に達成できたか。ずれていたらそのずれ>

## 指摘

### 1. <一行で内容>

- 分類: `<語彙>`
- 出どころ: `<語彙>`
- 内容: <何が起きたか。どう直したか>

### 2. <一行で内容>

...

## 手戻り

<計画から外れた箇所と、外れた理由。無ければ「無し」>

## 発火

<発火ログ(record-firings.sh)から。次の 3 書式のどれかで書く>

- 発火: `<スキル・エージェント名>` <回数>回
- 発火: 無し
- 発火: 計測対象外(フック不発)

## うまくいったこと

<次も同じようにやりたいこと。無ければ「無し」>

## 規約への反映

<介入した分類と、置いた場所。介入が無ければ「無し」とその理由>

- 対策済: `<分類>` 層=<hook|case-law> at pr-<番号>
````

**検証エージェントが返す分類名は、そのまま書かない。** `plan-reviewer` /
`implementation-reviewer` は語彙を畳む前の細かい綴りを出すので、**下の 13 個のどれかへ
置き換えてから書く**(畳まずに書くと、`count.sh` の対応表に無い綴りが 14 行目として表に出る)。

**`対策済` と `見送り` の行を書くのは `harness-growth` だけ。** `count.sh` はこれを
「ここから数え直す」の起点として読むので、介入していない回に書くと再発数が 0 に戻る。
記録を書く時点(`harness-record`)では、介入が無ければ「規約への反映」に**無しとその理由**を
書いて終える。

---

## 分類の語彙

`分類` はここから選ぶ。**勝手に増やさない。** どれにも当てはまらないなら `なし` と書く
(それが規範の抜けの候補になる)。

| 分類 | 対応する規範 | この語が指さないもの |
| --- | --- | --- |
| `placement` | rules/architecture.md(帰属先・層・公開 API・utils の形式) | テストファイルの置き場所は `test` |
| `typing` | rules/coding.md(コンパニオン・イミュータブル・Result / Option・シグネチャ・型で語彙と状態を閉じる) | 型名の綴りは `naming` |
| `duplication` | rules/coding.md「同じ処理が2箇所に現れたら共通化する」(doc・説明文の重複を含む) | 同じ主張が事実と食い違う形は `comment` |
| `comment` | rules/coding.md「コメントは doc と Why / Why not に絞る」(過不足・実装との食い違い) | Issue / PR 本文だけの記録漏れは `plan` |
| `naming` | rules/naming.md | ファイルの置き場所は `placement` |
| `test` | rules/testing.md(配置・ネスト・assert が落ちうるか・実物を使う) | 計画のテスト一覧の抜けは `plan` |
| `state` | rules/hooks.md(useEffect / useState / useRef) | 不正な状態を型で防ぐ話は `typing` |
| `component` | rules/components.md(Composition・イベントの受け口) | 表示が UI 案と違う形は `ui` |
| `ui` | rules/ui-verification.md(UI 案との一致・表示確認・視覚差分) | コンポーネントの組み立て方は `component` |
| `plan` | implementation-flow フェーズ 3〜4(範囲・件数・前提・却下案・未決の判断) | 実装後に気づいた形は該当する実装側の分類 |
| `over-guard` | implementation-flow フェーズ 6(過剰なブロック / フォールバック) | 足りない防御は該当する実装側の分類 |
| `harness` | ハーネス自身(規範の整合・手順のずれ・サブエージェントの制御・フック環境・外部挙動の未確認) | ハーネスのコードの書き方は該当する実装側の分類 |
| `なし` | 既存の規範に対応が無い(＝規範の抜けの候補) | — |

**この 13 個より細かい切り分けは判例(`harness/case-law/`)に置く。** 語彙を増やすと、記録を
書く側が毎回選び分けることになり、増えた分だけ記録が長くなる。数えるために要るのは
「どの規範が守られなかったか」までで、その中の亜種は判例が持てば足りる。

過去の記録にはもっと細かい綴りが残っているが、**書き換えない。** 旧い綴りは `count.sh` の
`TagFolds` が畳む。

## 出どころの語彙

`出どころ` はこの 7 つから**ちょうど 1 つ**選ぶ。`count.sh` が `再発`(外部)と `内部` に
振り分ける。

| 出どころ | 何を指すか | 列 |
| --- | --- | --- |
| `レビュー（人）` | 人が書いたレビュー。GitHub の PR(レビューコメント / レビュー本文 / PR コメント)と、セッション中に受けた指示の両方 | 再発 |
| `レビュー（bot）` | Copilot など GitHub 上の自動レビュー | 再発 |
| `CI` | CI の失敗・報告(カバレッジ・視覚差分を含む) | 再発 |
| `レビュー（plan-reviewer）` | 計画検証のサブエージェント | 内部 |
| `レビュー（implementation-reviewer）` | 実装検証のサブエージェント | 内部 |
| `フック` | git hooks / `.claude/hooks/` が止めた | 内部 |
| `自己修正` | 上のどれでもなく、自分で気づいて直した | 内部 |

**括弧の中に自由記述を足さない。** 「2 巡目」「ミューテーション実測」「カバレッジ報告」
などの詳細は**「内容」に書く**。出どころに混ぜると、綴りが 1 件ずつ違って数えられなくなる。

### なぜ外部だけで分岐するのか

**人・bot・CI まで届いた指摘は、ハーネスが止められなかったという実測データ。** サブエージェント
や自己修正が捕まえた分は逆に効いた証拠で、意味が正反対になる。混ぜて数えると、検証エージェント
が饒舌になるほど「再発」が増え、それを根拠に観点を足し、また指摘が増える、という自己増殖に
なる。`内部` は列としては出すが、介入の分岐には使わない。

### 過去の記録は書き換えない

古い記録には `レビュー`(括弧なし)・`レビュー（人間）`・`レビュー（human）`・
`レビュー（オーナー）`・`レビュー（Copilot）` が混在している。遡って直さず、`count.sh` が
古い綴りも外部として読む。**判定は行頭の語で決まる**ので、`自己修正（CI の結果）` のように
括弧の中に別の語が入っているものは、行頭の `自己修正` で内部になる。

## 層の語彙

`対策済` の行に書く `層=` はこの 2 つ。介入先がこの 2 択であることの理由は
`.claude/skills/harness-growth/SKILL.md`「Step 3」。

| 層 | 置いた場所 |
| --- | --- |
| `hook` | linter 設定(`.oxlintrc.json` / Biome)・git hooks(`harness/githooks/`)・CI・`.claude/hooks/` |
| `case-law` | `harness/case-law/`(機械判定できないもの) |

古い記録には `rules` / `skill` / `観点` が残っている。書き換えず、`count.sh` は `観点` を
`skill` に畳んで表示する。
