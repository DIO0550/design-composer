# 記録を残す

マージされた PR 1 本につき、記録を 1 ファイル残す。記録は「今回何に躓いたか」を分類タグ付きで書いたものであり、人・bot・CI へ届いた指摘を分類ごとに集計する材料になる。

- **記録は実装者への評点ではない。** 「良い／悪い」ではなく「何が起きて、次にどう防ぐか」を書く
- **このスキルの管轄は記録を 1 ファイル追加して PR にするところまで。** 集計・介入の判断・`rules/` やフック・スキルの変更は行わない（→ `harness-growth`）。境界の理由は末尾の「ここで終わる理由」を参照

---

## Step 1: 材料を集める

対象 PR について以下を集める。

| 材料 | 取り方 |
| --- | --- |
| レビュー指摘（人） | `pull_request_read` の 3 メソッドを**すべて**引く（次節） |
| レビュー指摘（サブエージェント） | `plan-reviewer` と観点別エージェント（`*-reviewer`）の返答（このセッションの履歴） |
| CI の失敗 | `pull_request_read`（`get_check_runs`）、詳細は `get_job_logs` |
| 差分の規模 | `pull_request_read`（`get_files`） |
| 関連 Issue | PR 本文のリンク（Issue のコメント履歴に計画と却下案がある） |
| 実装中の手戻り | このセッションの履歴（計画から外れた箇所・書き直した箇所） |
| フックの発火 | セッション中にフックが止めた操作（lint 抑制・push ブロックなど） |
| スキル・サブエージェントの発火 | **発火ログ**（`record-firings.sh` の出力。読み方は後述） |

### 人のレビューは 3 箇所すべて取得しないと見落とす

**`get_review_comments` だけでは足りない。** GitHub はレビューを 3 箇所に分けて保存するため、`pull_request_read` を 3 回呼んで合算する。

| メソッド | そこにしかないもの |
| --- | --- |
| `get_review_comments` | 行に紐づくレビューコメント（スレッド） |
| `get_reviews` | **レビュー本文**（行に紐づかない一言はここにしか出ない） |
| `get_comments` | PR 全体へのコメント |

一部しか取得しないと「指摘なし」と誤って結論してしまう。**0 件だったときこそ 3 つすべて確認したかを見直す。**
なお `get_comments` は CI レポートや Storybook プレビューなど bot 投稿が大半を占めるため、**`user.login` で人と bot を分ける**（`github-actions[bot]` 等は指摘ではない）。

### セッション中に受けた指示も「人のレビュー」

GitHub に残らない口頭の指示（「その UI はやめて欲しい」など）もサブエージェントが捕まえられなかった指摘であるため、**`レビュー（人）` として記録する。**

### スキル・サブエージェントの発火はログから取る

`.claude/hooks/record-firings.sh` が発火の瞬間に `${TMPDIR:-/tmp}/design-composer-firings-<session_id>.log` へ 1 行ずつ書き出している（1 列目 = 時刻、2 列目 = `session` / `skill` / `agent`、3 列目 = 名前）。**記憶（自己申告）ではなく、このログを読んで記録の「発火」欄に書く。** なお、このスキルを Skill ツールで起動すると、その起動が `implementation-flow` の区切りになる（→ `.claude/hooks/block-parent-session-edit.sh`）。

```bash
ls "${TMPDIR:-/tmp}"/design-composer-firings-*.log
```

読み方は先頭の `session` 行（セッション見出し）の有無で決まる。フックはフェイルオープンかつサイレントなため、見出しがないログでは「起動しなかった」と「フック不発」を区別できない。また、Skill ツールを通らない起動（スラッシュコマンドの直接入力など）はログに書かれないため、発火行がある回でもスキルの行が抜けうる（→ `.claude/hooks/README.md`「カバー範囲と残る穴」）。

| ログの状態 | 記録に書くこと（書式は崩さない — `count.sh --shrink` が集計する） |
| --- | --- |
| 見出しがあり、発火行もある | ``- 発火: `<名前>` <回数>回``（1 行 1 装置） |
| 見出しがあり、発火行がない | `- 発火: 無し`（**本当に起動していない** — それ自体が指摘の材料） |
| 見出しがない / ファイルがない | `- 発火: 計測対象外(フック不発)`（「未使用」と結論しない） |

**手戻りとフックの発火（止めた操作）は記憶からしか取れない。** 別セッションで実行する場合は Issue と PR の記録から復元し、復元できない分は「不明」と書く（発火ログも tmp の寿命により残っていないことがある）。**推測で埋めない**（回数の根拠として使えなくなるため）。

## Step 2: 記録を書く

`harness/records/pr-<番号>.md` に [templates/record.md](templates/record.md) の形式で書く。**`.claude/` 配下には置かない**（編集のたびに承認が求められるため → [`harness/records/README.md`](../../../harness/records/README.md)）。

- **指摘 1 件 = 1 ブロック。** 複数の指摘を 1 件にまとめない（分類が混ざって数えられなくなる）
- **`分類`** は [templates/record.md](templates/record.md)「分類の語彙」から選ぶ。**語彙を勝手に増やさない**（増やせるのは `harness-growth` のみ）。どれにも当てはまらない場合は `分類: なし` とし、内容に何の話かを書く（規約の抜けの候補になる）
- **`出どころ`** は [templates/record.md](templates/record.md)「出どころの語彙」から**ちょうど 1 つ**選ぶ。**括弧の中に自由記述を足さない**（「2 巡目」「ミューテーション実測」等は「内容」欄に書く）。人・bot・CI は `count.sh` が「再発」に数える側なので、サブエージェント由来と同じ綴りにしない
- **`形の名前`** は、指摘に形の名前が添えられていたときだけ写す（添え方は [`reviewer-instructions.md`](../implementation-flow/reviewer-instructions.md)「指摘の書式」を参照）。ルールは次の 4 つ:
  - **(a) 添えられたときだけ書く。** 自分で推測して埋めず、添えられていなければ行ごと省く（`なし` とも書かない。人・bot・CI の指摘では通常この行がない）
  - **(b) 正規形にそろえる。**
    - 先頭の接頭辞 `判例 ` `分類: ` `形の名前 ` `観点: ` を外す
    - 観点の名前（太字の文）は太字記号だけを外し、全体をバッククォートで囲まず書く（文中のバッククォートは残す）
    - 判例の見出し・表の「形の名前」列にバッククォート付きの識別子があり、かつ統合後の分類名（`comment` など）と異なる場合は、その識別子だけをバッククォートで囲んで書く（例: `` `plan-file-omission` ``）
    - 識別子がない、または統合後の分類名と同じ場合は、文の部分（「—」があればその後ろ、なければ全体）を囲まずに書く
    - 識別子どうしが「・」で並んでいる場合だけ 1 行に 1 つへ分割し、文は分割しない
  - **(c) 置く位置。** `出どころ` の直後に置く（`count.sh` はこの行を読まないため件数に影響しない）
  - **(d) 抽出コマンド。** 直前の `分類` 行と並べて取り出すときは次を使う

    ```bash
    awk '/^- 分類:/{c=$0} /^- 形の名前:/{print FILENAME ": " c " / " $0}' harness/records/pr-*.md
    ```

- **指摘が 0 件の回も記録を残す**（0 件も「順調だった」というデータ）

### `対策済` の行は書かない

テンプレート末尾の `対策済:` は **`harness-growth` が介入したときにだけ書く行**であり、`count.sh` はこれを再発カウントの起点として読む。介入していない回に書くと再発数が 0 にリセットされてしまう。介入がない回は「規約への反映」欄に**無しとその理由**を書いて終える。

## Step 3: 記録の PR を出す

- **記録対象の PR とは別のブランチを切る**（対象 PR はマージ済み）
- PR 本文には記録した分類の一覧を書く
- **指摘が 0 件の回でも PR を出す**（記録を残すこと自体が目的）
- `rules/`・フック・スキルには触れず、差分は `harness/records/` の新規 1 ファイルだけにする
- **記録 PR には Issue を立てず、`Closes` も書かない**（`AGENTS.md`「着手した Issue は、その回で閉じる」の例外）。この例外は `.github/scripts/check-pr-closing-issue.sh` が「`harness/records/` 配下の新規 1 ファイルのみ」を条件に許可しているため、2 ファイル以上必要になった場合は検査条件も合わせて直す

---

## ここで終わる理由

集計以降を同じスキルに置くと、「記録だけ残して」と指示しても後続の手順まで実行されることがある（実測済み）。**制限を文章の指示ではなくファイル境界で守るための分割**なので、ここに Step を足さない。集計や介入が必要だと気づいた場合も、このスキル内では行わず `harness-growth` へ回す。

## 注意事項

- **過去の記録を書き換えない。** 判断が変わったら新しい記録に書く（履歴が消えると回数を数えられなくなる）
- 記録は PR ごとに 1 ファイルとし、1 ファイルへ追記しない（並行 PR が必ず衝突する）
- 記録のために実装を蒸し返さない。集めるのは**すでに出ている**指摘・失敗・手戻りだけにする
