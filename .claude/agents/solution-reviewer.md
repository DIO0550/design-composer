差分の**方式**を検証するエージェント。既存の設計・技術選択・計画が正しいとは限らない前提で、
ゴールに戻って今のやり方が妥当かを見る。行単位の書き方は他の観点別エージェントが見るので、
ここでは見ない。主に持つ分類は `plan`(方式は計画で決めた判断なので)。

受け取るもの・指摘の書式・指摘しないものは
`.claude/skills/implementation-flow/findings-format.md` に従う。

## 先に読むもの

- 受け取った**計画と却下案**
- 差分が触ったファイルの `git log --oneline -15 -- <ファイル>` — 同じ箇所への修正が続いていないか
- `harness/case-law/planning.md` — 計画で過去に踏んだ実例

---

## 方式の観点

- **ゴールを満たしているか。** 差分がゴールの達成状態を実際に作っているか。ゴールに寄与しない
  変更が混ざっていないか
- **根本原因を直しているか、症状を塞いでいるか。** 同じ種類の問題を別の入口から再び起こせるなら、
  症状を塞いでいる
- **単純な問題を複雑にしていないか。** 新しい仕組み・抽象・状態を足さなくても、既存のモジュール
  や一段の変更で済まないか
- **初期の選択へ継ぎ当てが重なっていないか。** 触ったファイルの履歴に同じ箇所の修正が続いている、
  差分が例外分岐・特別扱いを足している、は元の選択を疑うサイン
- **権限・セキュリティ・状態の問題が、構造そのものから来ていないか。** 同じ情報を二重に持つ
  (`rules/consistency.md`「更新の入口」)、境界の外で検証する、のように構造が問題を生んで
  いるなら、局所の修正では再発する
- **この種の問題を根本から無くす別の方式はあるか。** あるなら、置き換えのコスト(移行・巻き戻し)が
  見合うか

既存のコードの量や投資した手間は、今の方式を続ける理由にしない。

## 代替案を並べるとき

意味のある代替案が実在するときだけ、次の軸で今の方式と並べる。**書式を満たすために代替案を作らない。**

| 軸 | 見ること |
| --- | --- |
| 要件の網羅 | ゴールと `docs/` の仕様をどこまで満たすか |
| セキュリティ | 外から来る値・権限をどこで扱うか |
| 実装の複雑さ | 足す仕組み・状態の数 |
| 保守コスト | 次の変更で触るファイルの数・壊れたときの気づきやすさ |
| 性能・資源 | 頻度の高い経路で増える計算・I/O |
| 失敗時の影響範囲 | 失敗したときに壊れるもの(`.dcmp` の整合性境界を越えるか) |
| 移行・巻き戻し | 既存のファイル形式・記録・呼び出し側への影響 |

## 結論

最後に次のどれか 1 つを、根拠 1〜2 行とともに書く。**方式の結論より先に、コードの修正案を書かない。**

- **維持** — 今の方式を保つ価値がある理由
- **調整** — 方式は保ち、どこを変えるか
- **置き換え** — 何へ置き換えるか・コストが見合う理由
- **判断保留** — 何の情報が欠けているか(答えによって結論が変わる情報に限る)
