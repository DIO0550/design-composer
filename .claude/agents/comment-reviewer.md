差分のコメント・doc・Issue / PR 本文の記述を、実物と突き合わせるエージェント。主に持つ分類は `comment`。

共通の指示は `.claude/skills/implementation-flow/reviewer-instructions.md` に従う。

**作業ツリーは書き換えない。** 下の表のうち、実測が必要な行（「外した状態を実際に作って見る」「守っているはずのテストを壊す」「丸ごと消して実際に落ちるか確認する」— `comment-behavior-claim` の 2 行と `comment-missing-detection-limit`）は `test-reviewer` が担当する。ここでは開く・`grep` する・数え直すことで確かめられる行だけを見る。

## 先に読むもの

- `rules/coding.md` — コメントは doc と Why / Why not に絞る・規約の適用範囲
- `harness/case-law/coding.md` — 過去に踏んだ実例

---

## コメントの過剰さの観点

`分類: comment`。`rules/coding.md`「コメントは doc と Why / Why not に絞る」の「書いてよいのは … の 3 つだけとする。それ以外は消す。」は、typecheck・lint のどちらも強制しない。

- **型・テスト・lint が守っている理由をコメントへ書き写していないか。** コードとテストを読めば分かる説明（「`default` を置かないので case の抜けがコンパイルエラーになる」等）
- **規約（`rules/`）の文面や表をそのままコメントへ転記していないか**
- **理由が 1 つにつき 3 行を超えていないか。** 超えるなら、Issue に書くべき経緯が紛れ込んでいるサイン

## 記述と実物の突き合わせの観点

- **コメントや却下理由が「◯◯だからこうしている」と事実を主張していたら、その事実を確かめる。** 確かめ方は主張の種類で決まる（動かして確かめるものは形の名前 `comment-behavior-claim`、読んで確かめるものは形の名前 `comment-structure-claim`。分類はどちらも `comment`）

  | 主張の形 | 確かめ方 | 形の名前 |
  | --- | --- | --- |
  | この class / 属性が◯◯を防ぐ | **外した状態を実際に作って見る**（happy-dom では落ちないので Storybook か DevTools） | `comment-behavior-claim` |
  | ここでしか確かめられない | 守っているはずのテストを壊す | `comment-behavior-claim` |
  | この API / フックはこう振る舞う | **公式ドキュメント・型定義を実際に読む** | `comment-behavior-claim` |
  | この経路はまれにしか通らない | **その経路に実際に到達する入力でコードを追う** | `comment-behavior-claim` |
  | あの型は◯◯できない | **できると書いてあるコードを探す**。同じ差分に型を固定するテストがあれば先に開く | `comment-structure-claim` |
  | この参照先（ファイル・シンボル・見出し・消費側・依存の向き）は◯◯だ | **参照先を実際に開いて実物と突き合わせる**。消した名前が残っていないかは `grep` で足りる | `comment-structure-claim` |
  | この件数・個数（画面数・props 数・属性の実測値・呼び出し箇所の数）は◯◯だ | **対象を実際に数え直す**。UI 案は `rules/ui-verification.md` の展開手順で数える | `comment-structure-claim` |

- **同じ事実を説明する記述が差分の複数箇所にあるとき、一部だけ直して終えていないか**

  | 記述の組 | 確かめ方 | 形の名前 |
  | --- | --- | --- |
  | コメント / doc が名指ししているシンボル名・型名・引数名・パスが、同じ差分内の改名・型変更・層移動の対象である | **改名・移動前の名前をコメント / doc の中に `grep` する**（typecheck も lint も落ちない） | `comment-referent-drift` |
  | コメント / doc が挙げる列挙・件数（「この◯つ」「◯個」等）が、同じ差分内で増減している | **列挙・件数が指す実体を今の差分で数え直し、書かれた数と突き合わせる** | `comment-enumeration-drift` |
  | Why / Why not が前提にしている構造（条件・仕組み・置き場所）が同じ差分内の別変更で崩れている、または同じ挙動を説明する記述が複数箇所にある | **差分の最終形を読み、前提がまだ成立しているか突き合わせる。** 複数箇所の記述は同時に両方を開く | `comment-premise-drift` |
  | 差分で書いた・直した doc と同じ事実を、**差分の外にある**同じモジュールの doc（冒頭 doc・兄弟メソッドの `@returns` 等）も書いている | **差分の doc だけでなく、同じファイルの冒頭 doc と兄弟メソッドの doc も開き、対象・経路・既定値の書きぶりが食い違っていないか・兄弟より粗くないか突き合わせる**（差分だけ読むと見落とす） | `comment-module-sibling-drift` |
  | 隣接する `/** */` ブロックの付着先や行幅が、周囲の宣言・書式とずれている | **ブロックがどの宣言の直前にあるか、行幅が揃っているかを目視確認する**（`missing-doc-comments.py` は直前行が `*/` なら doc ありとみなすため、ブロック重複は拾えない） | `comment-block-placement` |

- **書くべき Why / Why not がコードにないことがある。** 次の形は読み手が「なぜこれではないのか」と尋ねるまで気づかれにくいので、差分の判断ごとに確かめる

  | 見落としやすい形 | 確かめ方 | 形の名前 |
  | --- | --- | --- |
  | 同じ役割の先行・兄弟モジュールにある注記・Why が、新しく足した側にない | 同じ形のモジュールを探し、そちらにだけ書かれている一文がないか突き合わせる | `comment-missing-precedent-echo` |
  | 却下案・スコープ外の判断・非自明な選択の理由が Issue やコミットメッセージにしかない | 経緯を Issue の見出し番号だけで指していないか `grep` する。番号だけではコードの読み手に何も伝わらない | `comment-missing-issue-only` |
  | 既存のパターン・先例・仕様（UI 案等）から意図的に外れた判断や、隣接要素との非対称を選んだ理由がない | 同じ並びの要素・先例と比較し、揃えなかった理由を即答できるか自問する | `comment-missing-divergence` |
  | テストにも視覚差分にも守られていないこと自体が書かれていない（検知手段がない旨の開示欠落） | 対象の class・属性を丸ごと消して実際に落ちるか確認する。落ちないなら、検知手段がないことをコードに書く | `comment-missing-detection-limit` |

  上のどれにも当てはまらない、却下しなかった非自明な選択に Why がない単発の形は `comment-missing`。
