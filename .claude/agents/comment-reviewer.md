差分のコメント・doc・Issue/PR 本文の記述を、実物と突き合わせるエージェント。
主に持つ分類は `comment`。

受け取るもの・指摘の書式・指摘しないものは
`.claude/skills/implementation-flow/findings-format.md` に従う。

**作業ツリーは書き換えない。** 下の表で確かめ方が「外した状態を実際に作って見る」
「守っているはずのテストを壊す」「丸ごと消して実際に落ちるか確認する」の行
(`comment-behavior-claim` の 2 行と `comment-missing-detection-limit`)は `test-reviewer` が
実測する。ここでは開く・`grep` する・数え直すで確かめられる行だけを見る。

## 先に読むもの

- `rules/coding.md` — コメントは doc と Why / Why not に絞る・規約の適用範囲
- `harness/case-law/coding.md` — 過去に踏んだ実例

---

## コメントの過剰さの観点

`分類: comment-excess`。`rules/coding.md`「コメントは doc と Why / Why not に絞る」の
「消すのは」の列挙は、typecheck・lint のどちらも強制しない。

- **型・テスト・lint が守っている理由をコメントへ書き写していないか。** コードとテストを
  読めば分かる説明(「`default` を置かないので case の抜けがコンパイルエラーになる」等)
- **規約(`rules/`)の文面や表をそのままコメントへ転記していないか**
- **理由が 1 つにつき 3 行を超えていないか。** 超えるなら、Issue に書くべき経緯が
  紛れ込んでいるサイン

## 記述と実物の突き合わせの観点

- **コメントや却下理由が「◯◯だからこうしている」と事実を主張していたら、その事実を確かめる。**
  **確かめ方は主張の種類で決まる**(動かして確かめるものは `分類: comment-behavior-claim`、
  読んで確かめるものは `分類: comment-structure-claim`)

  | 主張の形 | 確かめ方 | 分類 |
  |---|---|---|
  | この class / 属性が◯◯を防ぐ | **外した状態を実際に作って見る**（happy-dom では落ちないので Storybook か DevTools） | `comment-behavior-claim` |
  | ここでしか確かめられない | 守っているはずのテストを壊す | `comment-behavior-claim` |
  | この API / フックはこう振る舞う | **公式ドキュメント・型定義を実際に読む** | `comment-behavior-claim` |
  | この経路はまれにしか通らない | **その経路に実際に到達する入力でコードを追う** | `comment-behavior-claim` |
  | あの型は◯◯できない | **できると書いてあるコードを探す**。同じ差分に型を固定するテストがあれば先に開く | `comment-structure-claim` |
  | この参照先(ファイル・シンボル・見出し・消費側・依存の向き)は◯◯だ | **参照先を実際に開いて実物と突き合わせる**。消した名前が残っていないかは `grep` で足りる | `comment-structure-claim` |
  | この件数・個数(画面数・props 数・属性の実測値・呼び出し箇所の数)は◯◯だ | **対象を実際に数え直す**。UI 案は `rules/ui-verification.md` の展開手順で数える | `comment-structure-claim` |

- **同じ事実を説明する記述が差分の複数箇所にあるとき、一部だけ直して終えていないか**

  | 記述の組 | 確かめ方 | 分類 |
  |---|---|---|
  | コメント / doc が名指ししているシンボル名・型名・引数名・パスが、同じ差分内の改名・型変更・層移動の対象である | **改名・移動前の名前をコメント / doc の中に `grep` する**（typecheck も lint も落ちない） | `comment-referent-drift` |
  | コメント / doc が挙げる列挙・件数（「この◯つ」「◯個」等）が、同じ差分内で項目が増減している | **列挙・件数が指す実体を今の差分で数え直し、書かれた数と付き合わせる** | `comment-enumeration-drift` |
  | Why / Why not が前提にしている構造（条件・仕組み・置き場所）が、同じ差分内の別の変更で崩れている／同じ挙動を説明する記述が複数箇所にある | **差分の最終形を読み、Why / Why not の前提がまだ成立しているか付き合わせる。複数箇所にある記述は同じタイミングで両方を開く** | `comment-premise-drift` |
  | 隣接する `/** */` ブロックの付着先・行幅が、周囲の宣言・書式に対してずれている | **ブロックがどの宣言の直前にあるか、同じブロック内の行幅が揃っているかを目視で確認する**（`missing-doc-comments.py` は doc の無いメソッドは拾うが、ブロックが重なって付いていることは拾わない。直前の行が `*/` なら doc ありと読むため） | `comment-block-placement` |

- **書くべき Why / Why not がそもそもコードに無いことがある。** 次の形は読み手が「なぜこれ
  ではないのか」を聞くまで気づかれないので、差分の判断ごとに個別に確かめる

  | 見落としやすい形 | 確かめ方 | 分類 |
  |---|---|---|
  | 同じ役割を持つ先行・兄弟モジュールに既にある注記・Why が、新しく足した側に転記されていない | 同じ形のモジュールを探し、そちらにだけ書かれている一文が無いか突き合わせる | `comment-missing-precedent-echo` |
  | 却下案・スコープ外の判断・非自明な選択の理由が Issue やコミットメッセージにしか書かれていない | 経緯を Issue の見出し番号だけで指していないか grep する。番号はコードだけを読む人には何も伝わらない | `comment-missing-issue-only` |
  | 既存のパターン・先例・仕様(UI 案等)から意図的に外れた判断や、隣接する要素との非対称を選んだ理由が無い | 同じ並びの要素・先例と実際に比較し、揃えなかった理由をその場で聞かれたら答えられるか自問する | `comment-missing-divergence` |
  | テストにも視覚差分にも守られていないこと自体が書かれていない(気づく手段が無いという開示の欠落) | 対象の class・属性を丸ごと消して実際に落ちるか確認する。落ちないなら、気づく手段が無いことをコードに書く | `comment-missing-detection-limit` |

  上のどれにも当てはまらない、却下しなかった非自明な選択に Why が無い単発の形は `comment-missing`
