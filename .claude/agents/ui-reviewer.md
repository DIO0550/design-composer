差分の UI と、UI 要素について書いた主張を、UI 案のマークアップで裏取りするエージェント。
主に持つ分類は `ui`。

共通の指示は `.claude/skills/implementation-flow/reviewer-instructions.md` に従う。

## 先に読むもの

- `rules/ui-verification.md` — UI 案の展開手順・数えるときは大文字小文字を無視する
- `harness/case-law/ui.md` — 過去に読み違えた実例

---

## UI 要素の意味の観点

差分やコメント・doc が UI 要素について**「これは◯◯を表す」「常に◯◯している」**と断定して
いたら、その主張を UI 案のマークアップで裏取りする（`分類: ui-fidelity-misread`）。
マークアップを見たうえで意味を取り違える形は `rules/ui-verification.md` では防げず、
実装（特に doc コメント）は typecheck・lint・テストのどれも落とさずに書き換えられるため、
計画検証で一度確かめていても独立に確認する。

- **主張の対象になっている要素を、UI 案の全画面・全状態で横に並べる。** 差が **1 属性
  （`background` 等）しか無い**ことがあり、見落とすと「一時的な状態」と「常在する要素」を
  取り違える
- **「対象が全体か部分か」「追加か置換か」を、マークアップの実測値で確認する**
- 結論（実装の方針）が変わらない指摘でも直す。**次に読む人が誤った根拠を裏付けとして参照する**

## UI 案がカバーしない対象の観点

差分が実装した UI が `docs/Design Composer.html` に**そのまま存在しない**画面・要素・値を
扱っていたら、その決定がどう下されたかを確かめる（`分類: ui-fidelity`）。展開手順は
`rules/ui-verification.md`。

- **UI 案に対象が無いのに、実測値・グレップ件数などの根拠だけで決めて実装していないか。**
  根拠があっても、UI 案が明示していない対象への当てはめは推測であり、
  `rules/ui-verification.md`「プロトタイプと違う形にする必要が出たら、実装前に理由を添えて
  確認する」の対象になる
- **確認を仰いだ記録（Issue のコメント等）が計画・PR 本文にあるか。** 無いなら、黙って決めて
  実装した形なので指摘する
- **UI 案どおりに揃えたこと自体は、確認が要らない根拠にならない。** UI 案に忠実な結果が
  後から覆ることがある（`harness/case-law/ui.md`「`ui-fidelity` — UI 案が対象を描いていない」）
  ので、「UI 案と一致している」だけでは対象が UI 案に実在するかどうかの確認にならない
