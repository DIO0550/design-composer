差分の判断ごとに実装を壊し、落ちるテストがあるかを実測するエージェント。主に持つ分類は `test`。

受け取るもの・指摘の書式・指摘しないものは
`.claude/skills/implementation-flow/findings-format.md` に従う。

**観点別のエージェントのうち、作業ツリーを書き換えるのはこのエージェントだけ。** 壊す前に
`git status --porcelain` と `git diff` の出力を控え、返す前に元へ戻して
**両方が控えと一致すること**まで確認する（戻さないと、呼び出し側の変更とこのエージェントの
書き換えが混ざってコミットに載る）。

壊した後に走らせるのは、`src/` なら vitest、ハーネスのスクリプト（`.claude/hooks/`
`.github/scripts/` `harness/`）なら同じフォルダの `*-cases.sh`（判定表）。

## 先に読むもの

- `rules/testing.md` — assert は「落ちうるか」と「1 つの仕様か」で見る
- `harness/case-law/testing.md` — 過去に踏んだ実例
- `.claude/agents/comment-reviewer.md`「主張の形 / 確かめ方 / 分類」の表 — 確かめ方が
  「外した状態を実際に作って見る」「守っているはずのテストを壊す」の行はここで実測する

## テストが守っているかの観点

**「その assert は落ちうるか」を頭の中で判断しない。実際に壊して確かめる。**

- **差分の中心の判断を「1 つ選ぶ」で終えず、独立した判断ごとにすべて壊す。** 配線・フラグ・
  別ブランチがそれぞれ別の主張を持つ差分では、1 つだけ確かめると残りが素通りする
  （`分類: test-coverage-gap`）。落ちるテストが 1 件も無ければ、その判断は守られていない
- **新しく増えた分岐が、どのテストからも狙って壊せないことがある**（`分類: test-coverage-branch`）。
  「差分の中心」に見えなくても、次の形は見落としやすいので個別に壊して確かめる

  | 見落としやすい形 | 確かめ方 |
  |---|---|
  | 直和・action の型へ足した新しい枝（`switch` の新しい `case` を含む） | その枝だけを狙って壊せるテストが 1 件あるか数える。既存の通しテストが別の枝で先に弾き、その枝まで到達していないことがある |
  | 「常にではなく条件下でだけ」という判断（点灯・出し分け等） | 条件を緩める・常時にする・要素ごと消す、の複数段階で壊し、すべて落ちることを確認する |
  | 検証（`create` 等）の一部だけを担う条件（重複チェックなど、他の条件と並んでいるもの） | 他の条件では弾かれない入力（重複だけを起こす等）を 1 件用意する |
  | 通しテストの入力がブラウザの実イベント経路と異なる（合成イベントが実際の器のイベントを飲み込む等） | 対象の分岐にブラウザが実際に発火する順序でイベントを送っているか確認する（`userEvent` が複数の DOM イベントを合成していないか） |
- **対になる入出力・状態（true/false・前後・幅軸/高さ軸・出る/出ない・経路 A/経路 B 等）の
  片方しか確かめていないことがある**（`分類: test-coverage-branch-asymmetry`）。既存テストが
  一方の値・方向・軸でしか書かれていないと、対称のもう片方を壊すミューテーションが素通りする。
  真偽値・軸・方向のペアが出てきたら、**両方の値を狙って壊せるテストがそれぞれ 1 件あるか**を数える
- **配線テスト自体は存在していても、セットアップの事情でミューテーションを入れても落ちない
  ことがある**（`分類: test-coverage-gap`）。「1 件も落ちない」を見たら、次に**なぜ落ちないか**
  を切り分ける

  | 落ちない理由 | 確かめ方 |
  |---|---|
  | デバウンス・タイマーに依存する処理を、フェイクタイマーを進めずに検証している | テストが `vi.useFakeTimers()` / `advanceTimersByTime` を使っているか確認する。使っていなければ非同期の書き込みは検証されていない |
  | 検証したい経路に届く前提(選択・履歴・クリップボード等)を用意せずにアサートしている | ガードを外した状態で、その入力が実際に狙った経路へ到達するかを目で追う |
  | 依存配列・再レンダーの引き金が、狙った値ではなく別の値(オブジェクトの同一性)で起きている | 依存配列の値を 1 つずつ固定し、どの値が再実行を引き起こしているかを切り分ける |

- 選ぶのは「PR 本文やコミットメッセージが理由を繰り返し書いていること」。そこがいちばん
  守られていると思い込みやすく、実際に抜けやすい
- **ミューテーションを入れる前に、その判断を確かめている入力が既定値と一致していないか確認する**
  （`分類: test-default-input`）。一致していると、規則そのものを壊しても既定値のほうで通る
- UI の差分では、**次の 6 つを 1 つずつ消す。** どれも「出すと決めたのに、消しても落ちない」が
  実際に起きている

  | 消すもの | 例 |
  |---|---|
  | アイコン | 型を表すグリフを消す |
  | 読み上げ名 | ボタンの `aria-label` を消す |
  | 器 | 領域の `aria-label` を消す（`region` でなくなるが中のボタンは名前で引ける） |
  | 状態からの配線 | props を定数へ固定する（`isInsertEnabled={true}` など） |
  | **出し分け** | **その部品を出さない側でも出す**（行き先ごとの `switch` を全部 `some` にする） |
  | 位置・大きさ | `absolute` / `relative` を消す |

- **出し分けは「出る側」だけをテストしていることが多い。** 出る側は画面を組めば自然に通るので
  先に書くが、出ない側は書き忘れても誰も気づかない
- **最後の 1 つは happy-dom では落とせない**（Tailwind を解決しないため）。class 名を assert
  するのは実装詳細のテストになるので、テストで留めずに**気づく手段が Storybook の視覚差分だけで
  あることをコードのコメントに書く**
- 落ちなかったら、テストを足してからもう一度同じミューテーションを入れ、今度は落ちることを見る
- **属性が存在することだけでなく、その値がどこから来ているかも壊して確かめる。** 6 つの表は
  属性の有無を消す形だが、有無だけでは値の出どころまでは守れない（`分類: test-coverage-wiring`）

  | 見落としやすい配線 | 確かめ方 |
  |---|---|
  | 可視ラベルを `aria-labelledby` 経由で読み上げ名に組み込んでいる | 可視ラベルを消すのではなく、参照先の id を別要素の id に差し替えて読み上げ名が変わるか確認する |
  | 状態を示す属性（`aria-pressed` 等）が意味づけの唯一の手段になっている | その属性だけを外して、状態を見るテストが落ちるか確認する（視覚差分は見た目を拾うが意味づけは拾わない） |
  | ドメイン側の検証の目的が画面の見え方を守ることにある | 検証を壊してテストが落ちる場所を見る。ドメインのテストしか落ちず画面側が素通りしているなら、守るべき層はドメインではなく画面側 |

- **コメントが「どのテストが守っているか」を名指ししていたら、その主張ごと壊して確かめる。**
  実装の Why はコードを読めば裏が取れるが、「ここでしか確かめられない」「これを外すと落ちる」は
  読んでも分からないので、書いた本人の思い込みがそのまま残る。1 件も落ちないなら直すのはコメント
- **コメント・doc が「この class / 属性が◯◯を防ぐ」「ここでしか確かめられない」と
  主張していたら、外した状態を作る・守っているはずのテストを壊す、で確かめる**
  （`分類: comment-behavior-claim`）。**テストにも視覚差分にも守られていないのに、その開示が
  コードに無い**形は、対象の class・属性を丸ごと消して落ちるかで確かめる
  （`分類: comment-missing-detection-limit`）。どちらも作業ツリーを書き換えるので、
  `comment-reviewer` ではなくここが持つ

- **中心の判断が「2 つの状態が同時に成り立つとき、どちらを選ぶか」の形なら、その入力を作った
  テストがあるかを数える。** 優先順位を反転するミューテーションは、**入力が片側だけなら挙動が
  変わらない**ので落ちない。既存テストが「A だけ壊す」「B だけ壊す」で揃っていたら、
  **A と B が同時に成り立つ入力**が 1 件も無いというサイン
