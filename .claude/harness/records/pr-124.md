## ゴールと結果

ゴールは「部品一覧が UI 案どおりに読めるようになる。見出しに部品の数（`Components · 3`）、
各行に型アイコン `◆` とその部品がドキュメント内で使われている数（`×4`）が出る」。達成した。

ずれは無い。人によるレビュー指摘は 0 件で、以下はすべて計画検証・実装検証の
サブエージェントから出たもの。

## 指摘

### 1. biome の format が落ちる状態で PR を出しかけた

- 分類: `なし`
- 出どころ: 自己修正（実装検証のサブエージェント）
- 内容: `pnpm run typecheck` / `pnpm run lint` / `pnpm run test:run` はすべて通っていたが、
  CI の `Biome check` ステップ（`pnpm exec biome check`）で 3 ファイルが format 違反になる
  状態だった。**oxlint と biome は別物で、CI は両方を独立したステップで見る**
- 既存ルール: なし。`CLAUDE.md`「Common Commands」は `pnpm run lint`（oxlint）と
  `lint:fix` しか載せておらず、**biome を走らせるコマンドがどこにも書かれていない**。
  冒頭の「Lint / Format: oxlint / Biome」で存在は示されているが、実行方法が無い
- 次にどう防ぐか: **1 回目だが直す。** これは判断基準ではなく**コマンドの記載漏れ**で、
  その回限りの事情が固定される心配が無い。`CLAUDE.md` の Common Commands へ
  `pnpm exec biome check` / `--write` を足す

### 2. 実装が何をしても通ってしまうテストを 2 件書いた

- 分類: `test-behavior`
- 出どころ: 自己修正（実装検証のサブエージェント）
- 内容: 「部品のルートの型は一覧に出ない」「公開 prop は一覧に出ない」の 2 件は、
  props を `ComponentRefCount`（名前と回数だけ）に変えた時点でその情報が入力に存在せず、
  `queryByText` が実装によらず常に `null` になっていた。落とした表示が復活しても検知できない
- 既存ルール: `rules/testing.md`「振る舞い（仕様）をテストする」（ただし
  **「その assert は落ちうるか」という観点は書かれていない**）
- 次にどう防ぐか: **2 回目なのでルールへ追記する**（下の 3 と合わせて 1 つの節にする）

### 3. 1 つの assert で 4 つの仕様を同時に固定していた

- 分類: `test-behavior`
- 出どころ: 自己修正（実装検証のサブエージェント）
- 内容: 「部品は渡された並びのとおりに出る」の検証を行全体の `textContent` 連結
  （`"◆card×0挿入"`）で書いていた。並び・アイコンの字面・使用数の綴り・ボタンの文言の
  4 つを同時に固定しており、行に要素を 1 つ足すだけで**並びと無関係に落ちる**。
  テスト名（並び）と実体（4 つ）も食い違っていた
- 既存ルール: `rules/testing.md`「1テスト1振る舞い」「リファクタリング耐性を判断基準にする」
  （原則はあるが、**assert の粒度**に踏み込んだ記述が無い）
- 次にどう防ぐか: 2 と合わせて `rules/testing.md` へ「assert の書き方」の節を足す

### 4. 既存テストが壊れることを計画に書いていなかった

- 分類: `plan`
- 出どころ: 自己修正（計画検証のサブエージェント）
- 内容: `ComponentList` の props を変える計画だったが、既存のテスト 2 ファイル
  （`normal` 5 件 / `insert` 2 件）が全滅することを計画の変更ファイル表に入れていなかった。
  さらに新規テスト案の 1 件が既存の `insert` テストと同じ振る舞いで、重複するところだった
- 既存ルール: なし。`implementation-flow` フェーズ 3 は「変更するファイルと、そこに何を置くか」
  としているが、**変更で壊れる既存の資産（テスト・呼び出し側・ストーリー）を洗い出す**
  観点が無い
- 次にどう防ぐか: **2 回目なので観点へ追記する**（下の 5 と合わせる）。
  `references/plan-review.md` の妥当性の観点に足す

### 5. UI 案から決まらない文言・空表示を未決のまま計画にした

- 分類: `plan`
- 出どころ: 自己修正（計画検証のサブエージェント）
- 内容: 見出しの仕様を `Components · 3` とだけ書き、**日本語の見出し（現在は「部品」）を

- 既存ルール: なし（フェーズ 3 の「未決の判断」は書く場所があるだけで、

### 6. 戻り値の `Record` が「不在」を `number` と偽っていた

- 分類: `illegal-state`
- 出どころ: 自己修正（計画検証のサブエージェント）
- 内容: 使用数を `Readonly<Record<string, number>>` で返す計画だった。
  `noUncheckedIndexedAccess` が無いので、定義の無い名前を引くと型上 `number`・実行時
  `undefined` になり、画面に `×` だけが出る。「0 回」と「まだ数えていない」が同じ顔になる。
  `(名前, 使用数)` の並びに変えて、「使われていない部品も 0 で含む」を構造で満たすようにした
- 既存ルール: `rules/coding.md`「不正な状態を型で表現できなくする（型による境界）」
- 次にどう防ぐか: 今回は記録のみ（1 回目）。ルールには書かれている

### 7. 部品定義側の走査が既存の private 関数と重複しかけた

- 分類: `logic-ownership`
- 出どころ: 自己修正（計画検証のサブエージェント）
- 内容: 「部品定義の中の参照を集める」処理を `DesignDocument` に新しく書く計画だったが、

  矛盾していた
- 既存ルール: `rules/architecture.md`「ロジックの帰属先」、`rules/coding.md`
  「同じ処理が2箇所に現れたら共通化する」
- 次にどう防ぐか: 今回は記録のみ（1 回目）。**既存実装を探す前に置き場所を決めた**のが原因で、
  ルール自体は書かれている（PR #122 の指摘 2 と同じ形）

### 8. ドメインが要らない依存を持ちかけた

- 出どころ: 自己修正（実装検証のサブエージェント）

- 次にどう防ぐか: 今回は記録のみ（1 回目）

### 9. 入口のコメントが実体と食い違っていた

## 手戻り

**`ComponentList` の props を `state: EditorState` にする計画を取り下げた。**
型と公開 prop の表示を落とすと、行に要るのが名前と使用数だけになり、`state` は
必要以上に広い props になる。指摘 6 で戻り値を並びに変えた結果、
`refCounts` 1 つを受け取れば済むことが分かったので、表示に徹したままにできた。

取り下げた時点で #112 のコメントへ追記済み。
