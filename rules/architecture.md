# アーキテクチャ規約

実例（NG/OK・過去に踏んだ形）は [`harness/case-law/architecture.md`](../harness/case-law/architecture.md) を参照。

## フォルダ構造（ドメイン + Feature ベース）

トップレベルおよび feature 内の構成は以下の通り。**各フォルダの内部をどうモジュール分割するかは実装者の設計判断に委ねる。**

```
src/
  app/         # エントリ層: main.tsx / App.tsx・ルーティング・Provider の組み立てのみ。薄く保つ
  features/    # Feature 層: ユースケース単位（内部構成は後述）
  domains/     # ドメイン層: 複数 feature から使われるドメインオブジェクト（コンパニオンオブジェクト）。カテゴリを 1 段挟む（後述）
  services/    # ドメインサービス層: 複数ドメインを組み合わせるロジック（置く前に帰属先のドメインを探す）
  components/  # 汎用 UI コンポーネント（ドメイン知識を持たない）
  hooks/       # 汎用カスタムフック（ドメイン知識を持たない）
  libs/        # 外部世界との境界: 外部ライブラリのラップ、Tauri API・localStorage 等の I/O、外部フォーマット（JSON 等）の解釈を閉じる
  utils/       # 汎用純粋関数（ドメイン知識を持たない）
  types/       # ロジックを持たない純粋な型定義のみ（コンパニオンオブジェクトを置いたら違反）
```

```
features/<feature-name>/
  features/    # この feature からしか使われない子 feature（深さは 2 段まで）
  domains/     # この feature 固有のドメインオブジェクト
  components/  # この feature 固有の UI
  hooks/       # この feature 固有のフック
  utils/       # この feature 固有のユーティリティ
  types/       # この feature 固有の型
```

## 配置の判断基準

- ドメインオブジェクトはまず `features/<x>/domains/` に置き、**2 つ以上の feature が必要としたら `src/domains/<カテゴリ>/` に昇格**させる（重複実装は禁止）
- ロジックを持たない純粋な型定義は `types/`（汎用は `src/types/`、feature 固有は `features/<x>/types/`）に置く。`domains/` に置いてよいのは型 + 同名コンパニオンオブジェクトが揃ったものだけ（→ `rules/coding.md`「ルール」）
- I/O（Tauri API・localStorage・fetch・外部ライブラリ）と外部フォーマットの解釈は必ず `src/libs/` を経由する
- ストーリー専用の共有物（ラッパー・サンプルデータ）は、**使う範囲がいちばん狭いフォルダの `__stories__/`** に置く（1 モジュール内なら `<モジュール>/__stories__/`、1 feature 内なら `features/<x>/__stories__/`、2 つ以上の feature が使うなら `src/components/__stories__/`）。テスト専用の共有ヘルパーを `__tests__/` に置くのと同じ考え方
- 複数ドメインを組み合わせるロジックで UI にも I/O にも依存しないものは `src/services/` に置く。ただし置く前に**帰属先のドメインオブジェクトがないか確認する**（後述）

## ロジックの帰属先

**判断の起点は「その規則は誰の性質か」。** 値を組み立てる・判定する・変換するコードは、その値を表す型のコンパニオンオブジェクトに置く。迷ったら第 1 引数の型を見る。

- ある型 `T` を受け取って `T` の性質を答える関数や `T` から別の表現を作る関数は、`T` のコンパニオンオブジェクトのメソッドにする（`services/` や呼び出し側のヘルパーに置かない）
- 2 つの値が**常に対で意味を持つ**（片方だけでは答えが決まらない）なら、対を表す型を作ってそちらに帰属させる
- **汎用の型に個別ドメインの知識を集めない。** 「A が空のときは出力しない」のような規則は A の性質なので A 側に置く。汎用の B 側に `bFromA()` を生やすと他のドメインも B に集まって肥大化する
- 帰属先の型がまだないなら、**そのときが型を作るタイミング**。引数を 4〜5 個取る中間ヘルパーや `readonly [string, string]` のようなタプルは、名前の付いていない型が隠れているサイン
- **逆向きも見る: 入力欄・表示の都合をドメインへ持ち込まない。** 「空欄なら未設定へ戻す」といった入力欄の約束事はコントロール側で解釈し、ドメインには解釈済みの値（不在なら `Option`）を渡す。人間が読む 1 行への整形は表示側の関心事であり、ドメインが持つのは値の種別（直和・列挙）まで（実例は判例 `ownership-reasoning`）

## services はドメインを探してから使う

`services/` は複数ドメインを組み合わせるロジックの置き場だが、**「複数ドメインに跨る」という感触だけを根拠に置かない**。多くは帰属先のドメインオブジェクトが見つかっていないか、まだ作られていないだけであり、そのまま置くと `services/` が帰属先未定の集積場所になる。

「サービスに置こう」と感じたときは、**先に次の順で置き場所を探す**。

1. **第 1 引数に取っている型は何か** → その型のコンパニオンオブジェクトのメソッドにする
2. **2 つ以上の値が常に対で渡っていないか** → 対を表す型を作り、そこへ帰属させる
3. **走査・再帰・`Result` の取り回しだけではないか** → 走査対象の型（ツリーならノード型）にメソッドを持てる
4. **ドメイン知識を持たない汎用操作ではないか** → `src/utils/`（`<型名>Ex`）
5. **外部フォーマットの解釈・I/O ではないか** → `src/libs/`
6. **特定のユースケースでしか意味を持たない手順ではないか** → `features/<x>/`（feature 固有のドメインオブジェクトを含む）

1〜6 のどれにも当てはまらなければ `services/` に置いてよい。その場合、**どのドメインにも帰属しない理由を PR に一言書く**（「どちらの型にも帰属しない調停そのものが目的」など）。判断が割れそうなら実装前に相談する。

### services の責務

- 責務は**オーケストレーション**（ドメインを呼ぶ順序、ツリーの走査、`Result` の取り回し）に限る
- `services/` に値の組み立て・判定・変換のロジックが現れたら、帰属先のドメインオブジェクトへ移すか新しく作る
- 単一ドメインオブジェクトの検証・整合性チェックを `XxxValidator` 等として `services/` に切り出さず、**そのドメインオブジェクト自身に持たせる**
- モジュール名が「対象 + 動作（`-validator` / `-manager` 等）」になったら置き場所を疑う
- 既存の service を触るときは、**まずドメインへ移せないか検討**してから変更し、肥大化を防ぐ

### ドメインが出力形式を必要とする場合

「CSS に出力する」などドメイン外の知識が要るからといってサービスにしない。ドメインから `services/` は import できないため、**変換手段（変換関数・対応表）を引数で受け取る**ことで依存方向を保ったままドメインに置ける。

## utils の形式

`src/utils/` はドメイン知識を持たない汎用純粋関数の置き場。**フラットな 1 ファイル + PascalCase** とし、ファイル名と同名の名前空間オブジェクトを export する（`ArrayEx` / `NumberEx` / `StringEx` / `Result` / `Option` / `Font`）。フォルダ + `index.ts` の形にはせず、テストは `src/utils/__tests__/` に集約する。

- 組み込み型への汎用操作は `<型名>Ex` に集約し、配列の範囲判定・挿入・移動、数値の性質判定、文字種判定などをドメインやサービスのローカル関数として書かない
- 汎用ユーティリティ同士も重複させない
- その値に生成・判定・変換の規則が付いてきた時点でドメイン概念になったとみなし、`utils/` から `domains/` へ移す
- **用途ではなく操作で名付ける。** 呼び出し側の用途で名付けると UI やドメインの語彙が `utils/` に入り込む。用途を外すと名前が付けられないなら呼び出し側の関心事なのでそちらに置く
- 汎用操作が 1 つだけでも、`<型名>Ex` に押し込めず**まとまりを表すモジュール**を立てる（ただし呼び出しのない操作を先回りで足さない）。型で閉じた対応表を汎用変換に置き換えない（実例は判例 `utils-form`）

## domains のカテゴリ

`src/domains/` はカテゴリを 1 段挟み、`src/domains/<カテゴリ>/<モジュール>/` に置く。**カテゴリは層であり、import してよい向きが決まっている**（向きは oxlint、カテゴリを挟む規則は `import-rule-violations.py` が強制する）。

| カテゴリ | 置くもの | import してよいカテゴリ |
| --- | --- | --- |
| `unit/` | ドキュメントに依らない値そのものの語彙。長さ・辺・時刻（`px` `side` `instant` `elapsed`） | なし |
| `dcmp/` | `.dcmp` に書かれる中身と、その語彙・派生 | `unit` |
| `compiled/` | ドキュメントから作った描画用の表現 | `dcmp` `unit` |
| `session/` | 開いている・選んでいる・保存できているといった編集中の状態と、編集操作の指定 | すべて |

- **カテゴリフォルダは `index.ts` を持たない。** 公開 API は各モジュールの `index.ts` のままにする
- 新しいドメインオブジェクトは**この向きに収まるカテゴリ**へ置く。どれにも収まらないならカテゴリの切り直しになるため、実装前に相談する
- 複数モジュールにまたがるテスト用フィクスチャは `src/domains/__tests__/` に置く（消費側が feature にもまたがるため、カテゴリの中ではなく並べて置く）

## モジュールの公開API

- モジュールフォルダ（`domains/` のカテゴリ配下、`services/`・`features/` の各サブフォルダ、およびその中で分割したサブフォルダ）は `index.ts` を公開 API とする
- モジュールフォルダの基本形は「`index.ts` + `__tests__/`」。**実装は `index.ts` に直接書く。** 複数ファイルへの分割が必要になったら、実装ファイルを 1 つだけ切り出すのではなく**サブフォルダに分割**し、各サブフォルダでも同じ形を保つ
- `.tsx` は **600 行まで**（lint の `max-lines` で強制。空行とコメントを除いた行数。閾値の根拠は `.claude/hooks/README.md`）
- フォルダ外部からの import は必ず `index.ts` 経由とし、**内部ファイルへの deep import は禁止**
- `index.ts` から export するものは外部公開が必要なものだけに絞る

## 依存方向のルール（必須要件）

```
app → features → services → domains
```

- `src/domains/<カテゴリ>/<x>/` は他の domain を import してよい（カテゴリの向きに従う・一方向のみ・循環禁止）。`services/` `features/` React・Tauri API への依存は禁止
- **domains から libs への import は `__tests__/` 内のみ許可**（理由は判例 `dependency`）。**プロダクションコードは 0 件**とし、外部の語彙が必要なら境界（`libs/`）でドメインの語彙へ詰め替える
- `src/services/` は `src/domains/`・`src/types/`・`src/utils/` のみ import 可。React・Tauri API への依存は禁止
- `features/<x>/` は自 feature 内部、`src/services/`、`src/domains/`、横断層（`components/` `hooks/` `libs/` `utils/` `types/`）を import 可。他 feature は**公開 API（`index.ts`）経由で親から直下の子のみ**（子同士・子から親は禁止 → `rules/consistency.md`「feature の構成とネスト」）
- `features/<x>/domains/` は `src/domains/` を import してよいが、他 feature の `domains/` への直接 import は不可（複数 feature で使うドメインオブジェクトは昇格させる →「配置の判断基準」）
- `app/` はロジックを持たず、`features/` の呼び出しとルーティング・Provider の組み立てのみを行う
- `components/` `hooks/` `utils/` `types/` は `domains/` `services/` `features/` を import してはならない（ドメイン知識の流入禁止）
- `libs/` は外部ライブラリ（`@tauri-apps/*` 等）・`src/types/`・`src/utils/`・`src/domains/` を import 可。`services/` `features/` `components/` `hooks/` への依存と、複数ドメインのオーケストレーションは禁止（オーケストレーションは `services/` の責務）
- 循環依存は全面禁止
