# UI表示確認規約

実例（過去に読み違えた形）は [`harness/case-law/ui.md`](../harness/case-law/ui.md) を参照。

## UIの拠り所は `docs/Design Composer.html`

画面の見た目・構成は **`docs/Design Composer.html`（UI 案。Default / Assets / Assets · Instance / Tokens / Error / Context menu の 6 画面）に従う**。仕様書（`docs/06-ui.md`）が何ができるかを文章で規定し、それをどう見せるかはこのプロトタイプが定義する。

- **UI を実装・変更する前に必ずこのファイルを開いて該当箇所を確認する。** JS で描画されるため、ブラウザか playwright-cli で開く（ソースを読むだけでは分からない）
- **見るのはスクリーンショットではなくマークアップ。** 画像からは色・余白・文言の実測値が取れず「開いたのに読めていない」状態になる。マークアップは `<script type="__bundler/template">` の **JSON 文字列**に入っているため、次のように展開してから該当箇所を切り出す

```bash
python3 -c '
import json, re
raw = open("docs/Design Composer.html", encoding="utf-8").read()
body = re.search(r"<script type=\"__bundler/template\">(.*?)</script>", raw, re.S).group(1)
print(json.loads(body))
' > /tmp/ui-plan.html
```

展開後は約 10 万字の HTML になる。`<!-- RIGHT PANEL -->` のような区切りコメントが画面ごとに入っているため、そこを目印に読む。**特定の語や色が UI 案に何回出るか**を数えるのも判断の裏取りに効く。

- **数えるときは大文字・小文字を無視する（`grep -i`）。** UI 案は小文字で書いて CSS の `text-transform:uppercase` で大文字表示している箇所がある。**「0 回だから UI 案にない」と結論する前に必ず `-i` で数え直す**
- **単一の画面・状態だけを見て「これは◯◯を表す」と断定しない。** 同じ要素を全画面・全状態で並べて属性を比較する（差が 1 属性しかないことがある）
- プロトタイプにない操作を思いつきでボタンとして足さない。プロトタイプに描かれていない操作（コピー & ペースト等）はキーボードショートカットなど既存の流儀に寄せる
- プロトタイプと違う形にする必要が出たら、実装前に理由を添えて確認する（黙って寄せない・黙って離れない）
- 現状の実装はプロトタイプと乖離している箇所が多い。乖離の解消は個別の Issue で行う

## 表示確認

UI を実装・変更した場合は、**必ず実ブラウザで表示を確認**してから完了とする。

1. ブラウザから直接開ける画面は開発サーバーを起動する（`pnpm dev`。ポート 14000）
2. 直接開ける画面は playwright-cli で開き、スクリーンショットを取得する
   - **編集画面の確認は [verify-storybook](../.claude/skills/verify-storybook/SKILL.md) を使う。** 開く導線が Tauri に依存するため、Storybook 上で操作して撮影する
3. スクリーンショットを目視確認する（レイアウト崩れ・要素の重なり・はみ出しがないこと、実装した表示が仕様通りであること、操作後の状態変化も同様であること）
4. 確認したスクリーンショットの取得コマンドと確認結果を作業ログに残す

## Storybook の視覚差分（VRT）

PR では Storybook のスクリーンショットを main のベースラインと比較する（`Storybook Visual Regression`）。**差分があるとチェックは赤になるが、これは「壊れた」ではなく「レビューで見てほしい差分がある」という意味**であり、ツールには意図した変更か判別できない。

1. コメントに貼られた VRT レポートを開き、差分画像を確認する
2. **意図した変更**なら PR に `visual-approved` ラベルを付ける（チェックが再実行され、差分があっても通る）
3. **意図しない変更**ならコードを直す（ラベルで通さない）

- ラベルを外すと再びチェックが走り、差分が残っていれば赤に戻る
- ベースラインは main へマージされた時点で撮り直されるため、マージ後の PR で同じ差分が再発することはない
- 閾値（`--max-diff-ratio`）未満の差は passed になる

### 差分ではなく撮影で落ちることがある

同じチェックは、**ストーリーが撮影範囲に収まっていないとき**にも赤くなる。差分ではないため `visual-approved` では通らない（比較まで進まずレポートも公開されない）。どのストーリーが何 px かは run の要約と撮影ステップのログに出る。理由と直し方はその失敗メッセージに従う。

**直すと、そのストーリーはこの検査の対象から外れる。** 高さを固定したコンテナを与えると、以後は中身がどれだけ伸びてもクリップされて文書の高さが動かない（この検査が見るのは文書自体が伸びた場合だけ）。コンテナの中身が撮影範囲に収まっているかは、撮影された画像を目視して確かめるしかない。

## ルール

- 「コードを書いた・テストが通った」だけでは UI 実装の完了とみなさない
- 静的な初期表示だけでなく、主要なユーザー操作フロー（要素の追加 → 編集 → 結果の反映など）を通しで確認する
- **ドラッグ等の連続操作は、結果だけでなく操作中の見え方も確認する。** 掴んだ要素が画面上に映っているか、掴める範囲が実際に反応するかは離した後の座標だけでは分からない。操作途中でスクリーンショットを撮り、操作対象が映っているかを確認する
- ビューポートはデスクトップ（1280x720 以上）を基準とする。これは目視の下限であり、VRT が撮る固定サイズとは役割が違う。どのサイズで見ても撮影範囲の検査（CI の `Storybook Visual Regression`）の代わりにはならない（→「差分ではなく撮影で落ちることがある」）
