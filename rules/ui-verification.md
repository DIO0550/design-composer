# UI表示確認規約

## UIの拠り所は `docs/Design Composer.html`

画面の見た目・構成は **`docs/Design Composer.html`(UI案。Default / Assets / Assets · Instance / Tokens / Error の5画面)に従う**。仕様書(`docs/06-ui.md`)が文章で規定するのは何ができるかで、それをどう見せるかはこのプロトタイプが持つ。

- **UIを実装・変更する前に必ずこのファイルを開いて該当箇所を見る。** JS で描画されるので、ブラウザか playwright-cli で開くこと(ソースを読むだけでは分からない)
- **見るのはスクリーンショットではなくマークアップ。** 画像からは色・余白・字面の実測値が取れず、「開いたのに読めていない」状態になる(過去 2 回、アイコンが素の div であることと、帯の色・画面数・gap を取り違えている)。マークアップは `<script type="__bundler/template">` の**JSON 文字列**に入っているので、次のように展開してから該当箇所を切り出す

```bash
python3 -c '
import json, re
raw = open("docs/Design Composer.html", encoding="utf-8").read()
body = re.search(r"<script type=\"__bundler/template\">(.*?)</script>", raw, re.S).group(1)
print(json.loads(body))
' > /tmp/ui-plan.html
```

  展開後は 10 万字ほどの HTML になる。`<!-- RIGHT PANEL -->` のような区切りコメントが画面ごとに入っているので、そこを目印に読む。**ある綴り・ある色が UI 案に何回出てくるか**を数えるのも、判断の裏取りに効く(「この色は UI 案に 1 度も出てこない」が分かる)
- プロトタイプに無い操作を、思いつきでボタンとして足さない。プロトタイプが描いていない操作(コピー & ペースト等)は、キーボードショートカットなど既存の流儀に寄せる
- プロトタイプと違う形にする必要が出たら、実装前に理由を添えて確認する(黙って寄せない・黙って離れない)
- 現状の実装はプロトタイプと乖離している箇所が多い。乖離の解消は個別の issue で行う

## 表示確認

UIを実装・変更した場合は、**必ず playwright-cli で実際の表示を確認**してから完了とすること。

## 手順

1. 開発サーバーを起動する(`pnpm dev`。ポート 14000)
2. playwright-cli で対象ページを開き、スクリーンショットを取得する
   - **編集画面はブラウザでは開けない。** ドキュメントを開く導線が Tauri の IPC / ダイアログを
     使うため、`pnpm dev` をブラウザで開いても開始画面から先へ進めない。編集画面の中
     (3 ペイン・キャンバス・各パネル)を確認するときは **Storybook(`pnpm storybook`。
     ポート 6006)** を使う。VRT が比較しているのも Storybook なので、赤くなる差分と
     見ているものが一致する
   - Storybook で見るときは `http://localhost:6006/iframe.html?id=<storyId>&viewMode=story` を
     直接開く(story の一覧を経由しないぶん速く、待ちが要らない)。story の id は
     `http://localhost:6006/index.json` から引ける
   - **操作を伴う確認は、画面全体を組み立てているストーリー**(`OpenedDocumentEditor` など)で
     行う。単体のストーリーは props が固定なので、選び直しなどの状態変化を追えない
3. スクリーンショットを目視確認し、以下をチェックする:
   - レイアウト崩れ・要素の重なり・はみ出しがないこと
   - 実装した機能の表示が仕様通りであること
   - 操作後の状態変化(クリック・入力後)も同様に確認すること
4. 確認したスクリーンショットの取得コマンドと確認結果を作業ログに残すこと

## Storybook の視覚差分(VRT)

PR では Storybook のスクリーンショットを main のベースラインと比較する(`Storybook Visual Regression`)。**差分があるとチェックは赤になる。これは「壊れた」ではなく「レビューで見てほしい差分がある」という意味**で、ツールには意図した変更かどうかは判別できない。

赤になったら次の順で扱う。

1. コメントに貼られた VRT レポートを開き、差分画像を確認する
2. **意図した変更**なら PR に `visual-approved` ラベルを付ける。チェックが再実行され、差分があっても通る
3. **意図しない変更**ならコードを直す(ラベルで通さない)

- ラベルを外すと再びチェックが走り、差分が残っていれば赤に戻る
- ベースラインは main へマージされた時点で撮り直されるので、マージ後の PR で同じ差分が再び出ることはない
- 閾値(`--max-diff-ratio`)未満の差は passed になる。ボタンが1つ増えた程度では赤にならないことがある

## ルール

- 「コードを書いた・テストが通った」だけではUI実装の完了とみなさない
- 静的な初期表示だけでなく、主要なユーザー操作フロー(要素の追加 → 編集 → 結果の反映など)を通しで確認すること
- ビューポートはデスクトップ(1280x720 以上)を基準とする
