# テスト規約

**基本方針: 古典学派（Classicist / Detroit School）でテストを書く。**

実例（NG/OK・過去に踏んだ形）は [`harness/case-law/testing.md`](../harness/case-law/testing.md) を参照。

## 配置と命名

テストはモジュールフォルダ内の `__tests__/` に置く（モジュールの形は `rules/architecture.md`「モジュールの公開API」）。

```
<モジュールフォルダ>/
  index.ts
  __tests__/
    <対象ドメイン名>.<カテゴリ>.test.ts
```

- 複数ファイルへの分割が必要になったらサブフォルダに分割し、各サブフォルダでも同じ形を保つ

命名規則: `{テスト対象ファイル}.{カテゴリ}.test.ts`

- カテゴリはテストの観点を表すラベル（`normal` = 正常系 / `edge` = 境界値・異常系 / 特定の仕様領域）
- **`describe` のネストの代わりにカテゴリ（ファイル）で分割する。** 1 ファイルが肥大化したらカテゴリを分ける

## 古典学派のテスト

2 本柱は「**何をテストするか = 振る舞い**」と「**依存をどう扱うか = 実物を使う**」。

### 1. 振る舞い（仕様）をテストする

テストは**外から観測できる振る舞い**に対して書き、実装の内部構造に対して書かない。

- テスト対象は公開 API（`index.ts` の export）の「入力 → 出力／最終状態」のみ。内部ヘルパー・中間データ構造・処理順序はテストしない
- テスト名は**仕様の文として**書く（「○○のとき□□になる」）。関数名や実装語彙ではなくドメイン語彙を使う
- 1 テスト 1 振る舞いとし、複数の仕様を 1 つのテストで検証しない
- **リファクタリング耐性を判断基準にする**: 振る舞いを変えずに実装を書き換えたときに壊れるテストは実装詳細をテストしている証拠なので書き直す
- テストケースの根拠は仕様・設計ドキュメントに求め、仕様にない振る舞いをテストで固定しない
- **API を作り替えるときは、既存テストの観点を先に数える。** 型名やメソッド名を変えると既存テストが丸ごと動かなくなるが、そこにある観点（dangling 参照・循環・定義順・空など）は仕様であり書き換えの都合で消してはならない。**新しく思いついたケースだけを並べると元の網羅より薄くなりやすい**

### assert は「落ちうるか」と「1つの仕様か」で見る

テスト名が仕様の文になっていても、assert がその仕様を捉えていないことがある。書いたあとに次の 2 つを確かめる。

**1. その assert は落ちうるか。** 入力にその情報が存在しない状態で「出ない」ことを確かめても、実装が何をしても通ってしまう。

判断の仕方: **その assert を落とすために実装をどう壊せるかを考える。** 壊し方が思いつかないなら、そのテストは何も守っていない。

- **既定値・フォールバックがある処理では、既定値と違う答えになる入力を選ぶ。** 規則で決まる答えと既定値が同じ入力では、規則を丸ごと壊しても既定値で通ってしまう
- **「空になる」「出さない」を確かめるときは、対照を 1 件置き、入力から自明にならない側を見る。** 0 件のときに行がないのは入力から決まるので、行数では実装を守れない（実例は判例「assert が落ちない形」）
- **`queryBy*` が `null` になる理由が 2 通り以上あるなら、その assert は守っていない。** 対象を `getBy*` で引いてから、外れてほしい側だけを見る
- **落ちるか迷ったら、その 1 件だけ実装を壊して走らせる。** 頭で判断せず実測する

**2. 1 つの assert が複数の仕様を固定していないか。** 表示全体を文字列として比べると、テスト名が指していない仕様まで巻き込み、無関係な変更で落ちてリファクタリング耐性が下がる。

### 2. モックは原則使わない

依存は実物を使い、相互作用（呼び出し回数・引数）ではなく**結果の状態・戻り値を検証**する。

- `domains/` `services/` のテストではフェイクも使わず実物で確かめる。フェイクが必要に感じたら設計を見直す
- features / hooks / components のテストでも、`domains/` `services/` は必ず実物を使う
- 例外として代替してよいのは**プロセス外・制御不能な境界のみ**（`libs/` が包む外部 I/O: Tauri API、localStorage、fetch、時刻、乱数）。この場合も `vi.fn` などで作るモックではなく、単純なテスト用実装（フェイク）を渡す
- 内部実装の呼び出し検証（`toHaveBeenCalledWith` 等）は外部境界の検証以外で使わない

## テストの書き方: ネスト禁止

Kent C. Dodds の "Avoid Nesting when you're Testing" に従う。

- `describe` のネストは禁止（ファイル直下に `test` / `it` をフラットに並べ、グルーピングが必要ならカテゴリファイルを分ける）
- テストは 1 つだけ読めば前提がすべて分かる状態にする（前提は各テスト内に書くか、`setup()`・ファクトリを呼んで作る）
- クリーンアップが必要な場合のみ `afterEach` を許可（リソース解放など、テストの理解に影響しないもの）

## テスト用ヘルパーの置き場所

**テストに書こうとしているヘルパーが汎用の操作なら、それは実装側に足りていない機能。** テストファイルにその場しのぎで書かず、`utils/` やコンパニオンオブジェクトへ実装する。

- 判断軸: そのヘルパーは**テストであることに依存しているか**。`expect` を含む表明はテスト固有だが、「`Ok` から値を取り出す」「オブジェクトを組み立てる」は汎用操作なので実装側に置く
- **移す前に、その assert がヘルパーを必要としていること自体を疑う。** 表示用の文字列を組み立てるヘルパーを実装側へ移すと表示の知識がドメインへ入る。多くの場合テストが見たいのは文字列ではなく**構造**であり、構造のまま比べればヘルパーごと不要になる
- 同じヘルパーを 2 つ以上のテストファイルに書いたら、その時点で共通化する（実装側へ移せるならそちらを優先）
- テスト固有のセットアップ（ファクトリ・`setup()`）は各テストから呼ぶ形で共有してよい
