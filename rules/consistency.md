# 整合性規約

実例（NG/OK・過去に踏んだ形）は [`harness/case-law/consistency.md`](../harness/case-law/consistency.md)。迷ったときと、指摘を受けたときに読む。

`rules/architecture.md` が **依存してよい向き**を規定するのに対して、この規約は **同時に正しくなければならない範囲**と、**その範囲を壊さない更新経路**を規定する。2 つは別の軸で、両方を満たす必要がある(ロジックの帰属先と import してよい向きは `rules/architecture.md`、何をモックしてよいかは `rules/testing.md`)。

## 整合性境界

**このアプリの整合性境界は `.dcmp` ドキュメント 1 つ**(`docs/01-file-format.md`)。境界の内側では、画面構造から参照される部品定義と、部品定義から参照されるトークンが同じドキュメント内に存在し、参照の向きに循環が無い。

**部分的に壊れた状態をファイルへ書かない。** 検証を通っていない中間状態を永続化すると、次に読む人(AI・外部エディタ・再起動後の自分)が矛盾したドキュメントを読む。メモリ上でどれだけ整合を作り込んでも、保存が割れていれば意味がない。

新しい型・新しいまとまりを作るとき、**どこまでを 1 つの塊として扱うか**は次の順で決める。ここで決まった範囲が、そのまま**一括で更新し、一括で検証する単位**になる。

1. **判定に何が要るか** — 規則の成立を判定するために同時に見る必要がある値の最小の集合。1 つの値で答えが出るなら、それ以上広げない
2. **同時に書き換わると壊れるか** — どちらか一方が必ず負けるべき範囲が、一括で読み書きする単位になる
3. **無制限に育たないか** — 件数に上限がない関係を 1 つの塊に含めない

## 更新の入口

**部分を直接書き換える関数を公開しない。** 深い位置にある値を変更する場合も、入口はルート側のコンパニオンオブジェクトに置き、**新しいルートの値を返す**。

- 塊の内部だけを受け取って内部だけを返す更新関数を `index.ts` から export しない。呼び出し側が整合を取り直す義務を負う形になり、守り忘れが検出できない
- 派生値の作り直しが必要なら、それを行うのはルート側の責務
- 変更後の値は**不変条件を満たしたものだけ**を返す。満たせない入力は `Result` で返す

**同じ情報を二重に持った時点で、整合性の問題が発生する。** 派生する値は保存せず、必要なときに計算する。**導出できる値をファイルへ書かない**(ファイルが source of truth である以上、ファイル内の二重化は外部編集で即座に矛盾する)。保存してよいのは、計算コストが高く毎回は回せない(計測した上で判断する)か、**その時点の値を固定したい**ときだけ。後者は整合性ではなくスナップショットの要求なので、**別の値である**ことが分かる名前にする。

## 永続化と外部変更

- 書き込みは一時ファイル + rename で**アトミック**に行う(`docs/05-architecture.md`)
- **複数ファイルに跨る保存を導入しない。** 片方だけ失敗するケースが生まれる。導入するなら実装前に相談する
- 自動保存のデバウンス中に落ちても、失われるのは最後の編集だけで**ファイルは壊れない**
- 外部(AI・エディタ・git 操作)の変更は同期しない。**あとで揃う**前提で設計する。不正な内容なら最後に正常だった描画を保持してエラーを重ね、**壊れた内容を取り込んで内部状態を壊さない**。外部の編集が正常に直った時点で必ず揃う経路があること

## feature の構成とネスト

**親でしか使わない feature は、親の配下に `features/` としてネストする。** 同じ語を使うことで、どの階層でも判断基準が同じになる。フラットに並べると「親と子は対等」という誤った構造を示す。

| ルール | 内容 |
|---|---|
| 公開API | 各 feature の `index.ts`。**deep import は禁止** |
| 兄弟参照 | **禁止**。子 feature 同士は互いを import しない。繋ぐのは親だけ |
| 親の参照 | **禁止**。子は自分を入れている親を import しない |
| ネスト | 親でしか使わない子は配下へ。**深さは 2 段まで** |
| 昇格 | 2 つ以上の階層から必要とされたら 1 つ上へ移す |

**ドメイン軸でまとまっている feature はネストしない。** 複数の画面領域に UI を提供していても、同じドメイン・同じ選択状態に反応して一緒に変わるなら 1 つのまとまり。使われ方で割ると凝集が壊れる。参照元が 2 つ以上ある feature は、共通の親の直下に置き、親が両方へ差し込む。

子が別の子の中身を必要とするとき、直接 import せず**親が差し込む**。違反は `import-rule-violations.py` が `feature-public-api` / `feature-sibling` / `feature-ancestor` / `feature-nest-depth` として報告する。

- 中身を `ReactElement` として親から渡す。`ReactNode` は `undefined` を含んで抜けが黙って通る
- 行き先が複数あるなら `Record<行き先, 定義>` で受け取り、**全行き先が揃っていることを型で保証する**
- 共有したいのが UI ではなく型やロジックなら、それは `src/domains/` へ上げる対象
