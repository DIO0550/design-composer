## 指摘

### 1. push をブロックしないフックとして出した

- 分類: `なし`
- 出どころ: レビュー
- 内容: 最初に出したのは `check-doc-comments.sh`（`PostToolUse`・報告のみ）1 本だけで、
  push は止めていなかった。レビューで「編集時 or プッシュ時に自動チェックさせるように
  したい。なんならプッシュはブロックしていいレベル」と言われて push ブロックを足した。
  報告だけのフックにした根拠は `.claude/hooks/README.md` の
  `check-test-helper-duplication.sh`（既存の重複 13 組を理由にブロックしない）を
  前例として踏襲したこと。**前例が成立していた理由（既存分を解消できない）が
  今回も当てはまるかを確かめていなかった**
- 既存ルール: なし（`harness-growth` の「フックにする / しない」は、機械判定できるか
  だけを扱っていて、止めるか報告に留めるかを扱っていない）
- 次にどう防ぐか: `harness-growth` の「フックにする / しない」へ観点を追加（後述）

### 2. 既存の doc 抜け 149 件をスコープ外へ出そうとした

- 分類: `plan`
- 出どころ: レビュー
- 内容: push ブロックを足した際、既存の抜けが 149 件あることを理由に**対象を
  「このブランチで追加した行」だけに絞り**、既存分は「別 issue で解消するか、
  このまま新規分だけ守るかの判断が要ります」とレビューへ投げた。
  返ってきたのは「修正して」で、埋める側だった。埋めたら 0 件になり、
  **絞る理由そのものが消えて push ブロックを全体へ広げられた**
- 既存ルール: なし
- 次にどう防ぐか: 指摘 1 と同じ観点で受ける（根は同じ）

### 3. 追加した doc が規約の言う項目を満たしていなかった（149 件すべて）

- 分類: `なし`
- 出どころ: レビュー
- 内容: 149 件の doc をすべて**概要 1 行だけ**で書き、引数・戻り値・投げる例外を
  書いていなかった。レビューで「パラメーターがあるならパラメータもかく / return が
  あるなら return も書く / エラーをスローするならエラーもスローする」と指摘された。
  **`rules/coding.md`「コメントは doc と Why / Why not に絞る」の 1 つ目には
  「その関数・型・定数が何か、引数、戻り値、例外的な扱い」と既に書いてあった**ので、
  規約の抜けではなく**書いてあるのに読まれていない**状態。触った 149 件を
  もう一度すべて触り直すことになった（実測 190 件 / 66 ファイル。うち約 117 件は
  この PR 以前から存在していた doc）
- 既存ルール: rules/coding.md「コメントは doc と Why / Why not に絞る」
- 次にどう防ぐか: 規約の表現を直し（「doc に書く項目」の表）、検査を項目まで
  広げて push でブロック（後述・この PR で実施済み）

### 4. `@throws` の判定が別の関数の `throw` を拾っていた

- 分類: `over-guard`
- 出どころ: 自己修正
- 内容: 項目の検査を書いたとき、`@throws` が要るかを「宣言行から 80 行」の
  固定窓で判定していた。そのため `EditorProvider` の doc に `@throws` を要求して
  いたが、実際に投げているのは**その下に並ぶ別の関数** `useEditor` だった。
  波括弧の対応で本体を切るよう直した（`body_of`）。
  **「とりあえず `@throws` を書いて通す」で済ませていたら、規約に無い doc が
  1 件混ざったうえに偽陽性が残っていた**
- 既存ルール: なし（`.claude/hooks/README.md`「例外(エスケープハッチ)」は
  誤検知の害を書いているが、検査を書くときの近似の危うさは書いていない）
- 次にどう防ぐか: `implementation-flow` の実装検証の観点へ追加（後述）

## 手戻り

**149 件の doc を 2 回触った。** 1 回目（d092124 / 37bd69a / 7814bcb）で概要 1 行を
書き、指摘 3 のあと 2 回目（63d7ad3 / de74035 / fcf2994）で全件に `@param` /
`@returns` / `@throws` を足した。1 回目の時点で `rules/coding.md` を読み直していれば
1 回で済んでいた。

**push ブロックの対象を 2 回変えた。** 「追加した行だけ」→「`src/` 全体（有無のみ）」
→「`src/` 全体（有無 + 項目）」。いずれも「既存の違反があるから絞る」で始めて、
埋め終わってから広げている。

指摘 1・2 とこの 2 つは**同じ根**を持つ。**既存の違反を数えたあと、「絞る」を選ぶ前に
「埋める」を検討していない。** 今回はどちらも埋められる量（149 件 / 190 件）だった。

## うまくいったこと

- **フックを通すために規約違反を量産しなかった。** 190 件を埋める間、`rules/coding.md`
  が消す対象にしている「What の言い換え」（`@param tokens TokenSet 型の値` など）は
  書かず、その引数が何を表すか・`Option` / `Result` が `none` / `err` になる条件を
  書いた。規約に「型の再掲は書かない」を明文化してから埋めたので基準がぶれなかった
- **偽陽性を見つけたとき、doc 側ではなく検査側を直した。** `.claude/hooks/README.md` が
  記録している「誤検知で止まるフックは、エスケープハッチを足す運用を招いて全体が
  信用されなくなる」に従った
- **見送りの判断が古くなっていたことを、見送り一覧に書き戻した。**
  `check-jsdoc-rules.sh` の見送り理由（「JSDoc 必須ルールは存在しない」）は PR #152 で
  消えていた。README に「規約が増えたら、それを理由に見送ったフックを見直す」を残した

## 規約への反映

### `なし`（doc / コメントの書き方・通算 6 回目）

pr-152 の 2 件（コメントが冗長 / Why と Why not を 1 つにまとめた）、pr-157 の 3 件
（`canvasDock` に doc が無い / doc 以外が混ざる / 非 export の定数に付いて出ない）、
今回の指摘 3 で 6 回目。

**置き場所: 1. フック + 5. `rules/` の表現を直す（この PR で実施済み）。**

| 置き場所 | 足したもの |
| --- | --- |
| 1. フック | `missing-doc-comments.py` を項目（`@param` / `@returns` / `@throws`）まで見るよう拡張し、`pre-push-doc-comments.sh` で push をブロック |
| 5. `rules/` の表現 | `rules/coding.md` に「doc に書く項目」の表と、型の再掲を書かない / 分割代入だけの引数は `@param` を省く、の 2 つの歯止め |

**4（`rules/` に追記）ではなく 5（表現を直す）にした理由**: 判断基準は既に
書かれていた（「その関数・型・定数が何か、引数、戻り値、例外的な扱い」）。
足りなかったのは**何をどう書くかの形**なので、新しい基準ではなく表と例を足した。

**フックで受けられる範囲と受けられない範囲を分けた。** 引数の有無と `@param` の
有無は括弧の対応で機械判定できるのでフックが成立する。一方「その `@param` が型の
再掲になっていないか」は判断なので機械判定できず、`rules/` の表で受けている。

### `plan`（20 回目）/ 指摘 1 の `なし`

**置き場所: 3. 既存スキルの観点（`harness-growth` の「フックにする / しない」）。**

「既存の違反があるとき、フックを弱める（報告のみ・対象を絞る）前に、その違反を
埋められるかを数えて確かめる」を追加した。今回は 149 件も 190 件も埋められる量で、
埋めたら絞る理由そのものが消えた。

- **1（フック）を採らない理由**: 「既存の違反を埋められるか」は量と内容を見た判断で、
  文字列一致では判定できない
- **2（新しいスキル）を採らない理由**: 段取りが 1 つ増えただけで、順番を間違えると
  結果が変わる種類の手順ではない
- **4 / 5（`rules/`）を採らない理由**: 実装の判断基準ではなく**フックの導入判断**なので、
  読み手が違う（`rules/` は実装者、この判断は `harness-growth` を実行する側が読む）

### `over-guard`（6 回目）

pr-139 の 2 件・pr-141 の 2 件・pr-148 の 1 件と今回の指摘 4。過去 5 件は実装コードの
過剰な分岐・正規化で、今回は検査スクリプトの過剰な検出だが、根は同じ
**「範囲を絞る根拠を、範囲の外に紛らわしいものを置いた入力で確かめていない」**。

**置き場所: 3. 既存スキルの観点（`implementation-flow` の `references/implementation-review.md`）。**

「宣言・ブロックの範囲を行数や文字数の固定窓で近似しているなら、窓の外に同種のものを
置いた入力で確かめる」を追加した。

- **1（フック）を採らない理由**: 「この近似は範囲を外れるか」は対象ごとの判断で、
  近似そのものを文字列で検出しても偽陽性しか出ない
- **2（新しいスキル）を採らない理由**: 実装検証の 1 観点であって、独立した段取りではない
- **4 / 5（`rules/`）を採らない理由**: `rules/coding.md` は書き方の規約で、
  「確かめ方」は実装検証フェーズの担当
