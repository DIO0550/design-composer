## 規約への反映

この回で 2 回以上に達し、かつ**既存のルール・観点が言い当てていない**分類は 3 つ。
置き場所は `harness-growth` の Step 4 に従い、強制力の強い順（フック → 新しいスキル →
既存スキルの観点 → `rules/`）に検討した。**上の番号を採らなかった理由も残す。**

| 分類 | 回数 | 反映先 |
| --- | ---: | --- |
| `test-behavior` | 9（うち今回 2） | 既存スキルの観点（#3）— `implementation-review.md` に「**中心の判断を壊すミューテーションを 1 つ入れて、落ちるテストがあるか確かめる**」を足す |
| `ui-fidelity` | 2（うち今回 1） | `rules/` の表現を直す（#5）— `rules/ui-verification.md` に UI 案の**読み方**（`<script type="__bundler/template">` の JSON を展開する）を書く |
| `naming` | 4（うち今回 1） | `rules/` の表現を直す（#5）— `rules/naming.md` の生成メソッドの綴りを、リポジトリの実態（`create` と `from*` の使い分け）に合わせる |

**なぜフック（#1）にしなかったか。**

- `test-behavior` — ミューテーションテストは**機械判定できる**（今回まさにそれで実証された）。
  ただし全テストを変異ごとに回すので CI 時間が跳ね、**フックとして毎回走らせるには重すぎる**。
  「差分の中心の判断を 1 つ選んで壊す」は人（またはサブエージェント）が選ぶ必要があり、
  そこを機械化できない。**費用と選択の 2 点で成立しない**
- `ui-fidelity` — 「UI 案を正しく読んだか」は読んだ結果を突き合わせないと分からない。
  文字列一致で拾える対象が無い
- `naming` — `of*` を機械的に禁止することは一応できる（`\.of[A-Z]` で拾える）が、
  `CanvasBounds.ofElement` という正当な既存の呼び出しがあり、`Object.entries` のような
  組み込みも巻き込む。`check-test-rules.sh` のように対象を絞る条件が立たない

**なぜ新しいスキル（#2）にしなかったか。** 3 件とも既存フェーズで見る観点・判断基準が
1 つ増えただけ。実装検証（フェーズ 6）と UI 実装の手順は既にあり、そこへ足せば必ず通る。

**なぜ `ui-fidelity` / `naming` を #3 ではなく #5 にしたか。** どちらも特定のフェーズでは
なく**実装中いつでも当たる**もの。UI 案は計画でも実装でも表示確認でも読むし、命名は
コードを書くたびに要る。フェーズの観点に置くとそのフェーズでしか読まれない。

`plan` / `duplication` / `illegal-state` も 2 回以上だが、**今回の該当分はいずれも既存の
ルール・観点が言い当てていて、読めていなかった側**なので記録のみとする。特に `duplication`
の 2 件は PR #144 で足した `implementation-review.md`「重複の観点」がそのまま捕まえており、
**足した観点が次の回で働いた例**として残す。

`なし` は 10 件目（`children` を optional に緩めた件）。過去 9 件のどれとも重なっていない。
