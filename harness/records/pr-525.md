## ゴールと結果

`Option` / `Result` の在／不在・成否を判別子の直読み（`option.some` / `result.ok`）で書くと、
定義元のファイルの外では機械的に止まる（CI と push 前検査の両方で）。達成した
（層 1 = `frontend.yml` の `rules-check` / 層 2 = `harness/githooks/pre-push` /
層 3 = `pre-push-result-option-reads.sh`。導入時点の違反 0 件）。

ずれが 2 つある。どちらも計画で「やらない」と決めたものを、検証の指摘で覆した。

- `rules/coding.md` への 1 行追記を「フックに置くので規約側には書かない」と計画したが、
  常時ロードの上限（843/900）に達しておらず条項が発動していないこと、#506 の分割時点で
  スコープとして 2 回記録されていることを指摘され、追記した（指摘 2）
- 共通部分の抽出を「既存 2 スクリプトを触るリスクの方が大きい」と却下していたが、
  `source_files()` がバイト単位で同一になることを指摘され、抽出した（指摘 15・16）

Issue の分割は #524（構築側・比較側のリテラル 101 箇所の扱い）を着手時に立てた。
