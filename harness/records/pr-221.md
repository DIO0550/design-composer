# PR #221 色トークンと影の色の不透明度を画面から編集できるようにする

- マージ日: 2026-08-15
- 関連 Issue: #142
- 差分規模: 11 ファイル / +538 -99

## ゴールと結果

色トークン（`colors`）と影の色（`shadows` の `color`）の alpha を画面から編集でき、
往復しても値が変わらないようにする。あわせて `ColorToken.withRgb` の
「alpha を引き継ぐ / 引き継がない」が種別ごとに逆向きだった場当たりを解消する。達成した。

**#142 は「決めること」5 件を残したままの判断待ち Issue だった。** 推測で埋めず、
各項目に選択肢・根拠・推奨を出して回答を得てから着手した（#143 / PR #219 と同じ形）。
このとき **整数 % では 256 通りの alpha のうち 155 通りが往復しない**ことを実測し、
「往復しても値が変わらない」という完了条件から丸めの粒度（小数第 1 位）が
一意に決まる、という構造を着手前に確定させた。

着手時点でセッション URL を Issue へ残した（`AGENTS.md`「Issue に紐づいて起動したら、
セッションの URL を Issue に残す」）。#135 / #143 で「あとから特定できなかった」と
記録した形は、今回は起きていない。

### 2. ピッカーに載せられない値を載せられる型のまま渡していた

- 出どころ: 自己修正（計画検証のサブエージェント）
- 内容: 計画では `TokenControlInput` の色欄が `ColorToken`（alpha を持ちうる）を持ち、

## うまくいったこと

- **判断待ちを推測で埋めなかった。** #142 の「決めること」5 件について、UI 案の
  マークアップを実際に読んで「`<input>` が全画面で 0 個」「編集できる `name` 行も
  同じ枠線付き div」という事実を出し、**「div だから表示専用とは読めない」ところまでを
  示したうえで判断を仰いだ**。判断が返るまで実装に入らなかった
- **仕様の数値を実測してから決めた。** 「整数 % では 256 通り中 155 通りが往復しない」
  「小数第 1 位なら 256 通りすべて往復する」を計算で確かめ、丸めの粒度を根拠付きで
  決めた。この実測が無ければ整数 % を選んでいた
- **初期テーマの値が「たまたま通る」ことに気づけた。** 影の alpha `1a` / `26` / `33` は
  整数 % でも往復するため、**その 3 つだけでテストを書くと丸めの粒度を壊した実装が
  通ってしまう**。256 通りすべてを回すテストにし、実際に整数 % へ壊して落ちることを
  確認した（`rules/testing.md`「既定値と違う答えになる入力を選ぶ」）
- **ミューテーションを判断ごとに実際に走らせた。** 丸めの粒度 / `normalize` の `ff` 落とし /
  「読めない色はテキスト欄」の 3 つを壊し、3 件・4 件・（当初）0 件が落ちることを見た。
  0 件だった 1 つが指摘 9 になった
- **VRT の差分をレポートまで開いて確かめた。** 変更 2 件の中身が「行が 1 本増えた分の
  ずれ」「影の hex が 8 桁 → 6 桁」「スクロールバーの出現」の 3 点だけであることと、
  **色を持たない 4 ストーリーが passed のまま**であること（＝色以外に影響していない
  対照）を確認してから `visual-approved` を付けた
- **push 前検査を `&&` で連ねず 1 つずつ実行した。** oxlint が 0 件でも biome が
  整形差分 4 件を出しており、連ねていれば見落として CI を落としていた
