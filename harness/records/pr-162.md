# PR #162 [ui] インスタンスの編集（Public props / Detach instance）を実装する

- マージ日: 2026-08-09
- 関連 Issue: #130（分割先 #161）
- 差分規模: 31 ファイル / +1328 -119

## ゴールと結果

**インスタンスを選ぶと右ペインが公開 prop だけの編集欄になり、どれが上書き済みか・元がどの
部品かが分かる。`Detach instance` で実体の木になり、`Go to source component` で元の部品を
`Assets` で示せる。** 達成した。

Issue が挙げた 6 項目のうち `Select all N instances` だけを #161 へ分けた（選択を複数持つ
変更で、ツリー・キャンバス・削除 / コピー / リサイズまで波及するため）。

**Issue が「仕様に無いので実装前に確認する」としていた `Detach` の内側ノードの自動改名規則は、
`InstanceComposition.detach` に既に実装され、テスト 10 件で固定されていた。** 新しい規則は
決めず、既存規則のまま UI へ繋いだ。

## 指摘

### 1. reducer にアクションを足したのに、その reducer のテストを足していなかった

- 分類: `plan`
- 出どころ: レビュー（オーナー）
- 内容: `use-editor-reducer` は木を編集するアクションごとにテストを持ち、挿入・削除・
  コピー & ペーストはいずれも「送ると木が変わる」と「送っても変わらない（`Option.none` の
  経路）」の両方を固定している。`detach_instance` だけがその形から漏れた。据え置きの経路には
  3 通り（選択なし / インスタンスでない / 参照先の部品が無い）から到達し、どれも画面の操作から
  届く。**枝を足しただけなので typecheck も既存テストも落ちず、計画のファイル表にも
  `use-editor-reducer/__tests__` が挙がっていなかった**
- 既存ルール: implementation-flow フェーズ 3「公開 API を変える場合は…`__tests__/` も
  変更するファイルとして数える」（**「変える」場合しか書いておらず、直和へ枝を足す場合が
  漏れている**）
- 次にどう防ぐか: 下記「規約への反映」1

### 2. 解除できないインスタンスでも `Detach instance` を押せる状態になっていた

  返すので、`Option.none` を返して何も起きないボタンになる。dangling 参照のドキュメントは

  `Select all N instances` を外しており、自己矛盾していた**。`isDetachEnabled` を

- 既存ルール: なし（却下案の中でだけ使っていた判断基準で、どこにも書かれていない）
- 次にどう防ぐか: 今回は記録のみ（計画の中で立てた基準を計画自身に当て直す、という話で、
  分類としては `plan` に収まる）

### 3. 「元がどの部品か」の導出が 3 経路に分かれていた

- 分類: `duplication`
- 出どころ: 計画検証（サブエージェント）
- 内容: 見出しの `Instance` バッジ（`Selection.kind`）、`from ◆ 部品名`（`SelectionControls`）、
  `Assets` の行の強調（`EditorState.sourceComponentName`）が同じ事実を別々に導いていた。
  「パネルはインスタンスなのに `Assets` はどこも光らない」が型で作れる。
  `EditorState.sourceComponentName` を作らず `SelectionControls.sourceName` 1 つに集約した
- 既存ルール: rules/coding.md「同じ処理が2箇所に現れたら共通化する」
- 次にどう防ぐか: 今回は記録のみ（既存ルールで説明が付く）

### 4. `sourceComponentName` を `EditorState` に置く理由が事実と食い違っていた

- 次にどう防ぐか: 今回は記録のみ

## 規約への反映

### 1. 直和へ枝を足す場合も `__tests__/` を数える（指摘 1）

`plan` は既に 19 回目。`implementation-flow` フェーズ 3 の一文を次のように広げた。

- 「公開 API を**変える**場合」だけでなく「**アクション・状態の直和へ枝を足す**場合」も
  `__tests__/` を数える
- 理由も添えた: 枝を足しても**既存テストは落ちず typecheck も通る**ので、数え漏らしても
  誰も教えてくれない（API を変えた場合は typecheck が落ちるので気づける、という前提が
  ここでは成り立たない）

**フック（強制力 1）を採らなかった理由**: 「触ったモジュールに `__tests__/` があるのに
テストを触っていない」は機械判定できるが、doc コメントの修正・リネーム・整形でも必ず鳴る。
`.claude/hooks/README.md`「誤検知で止まるフックは、エスケープハッチを足す運用を招いて
全体が信用されなくなる」に当たる。

**新しいスキル（強制力 2）を採らなかった理由**: 段取りが増えたのではなく、既に通っている
フェーズ 3 の観点が 1 つ足りなかっただけ。

### 2. 検証エージェントが返ったら作業ツリーを見る（指摘 10）

`implementation-flow`「サブエージェントの使い方」に、返ってきたあとの確認を足した。
「実装させない」と書くだけでは、守られなかったときに気づけない。

**フックを採らなかった理由**: `git status` に出た変更が「エージェントの書き換え」か
「自分の編集」かは機械的に区別できない。未コミットの変更を知らせる stop フックは既にあり、
今回もそれで気づけた（気づいたあと**戻す**ことが手順に無かったのが問題）。
