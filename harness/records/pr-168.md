# PR #168 [ui] プロパティパネルの入力をセグメントコントロール・スウォッチにする

- マージ日: 2026-08-10
- 関連 Issue: #132（分割先 #166 / #167）
- 差分規模: 23 ファイル / +898 -143

## ゴールと結果

**プロパティパネルの各 prop が UI 案（`docs/Design Composer.html` の `Default` 画面）と同じ
入力形式で編集でき、その編集がキャンバスへ反映される。** 達成した。

Issue が挙げた 6 項目のうち 2 つを分けた。`padding` の T / R / B / L 4 分割は #166
（UI 案は 4 分割だが `docs/03-schema.md` が「X / Y の 2 軸」と決めており、パネルだけ 4 分割に
すると T と B、R と L が連動する）、セクション見出しの `⋯` は #167（メニューの中身が UI 案に
無く、押しても何も起きないボタンになる）。残り 2 項目（見出しの「型 + 名前」・トークン参照の
ドロップダウン化）は #112 までに実装済みだった。

Issue が「実装前に決めること」としていた 2 点（セグメントコントロールの置き場所・`⋯` の中身）
に加えて、**UI 案が答えを持っていない判断が 1 つ出た**（セグメントに「未指定」の枠が無い）。
これは計画に選択肢と却下理由を書いて進め、レビューでの差し替えを受けられる形にした。

人のレビュー指摘は 1 件（命名）、CI の失敗は 1 件（biome の format）。以下はそれらと、
計画検証・実装検証のサブエージェントからの指摘。

## 手戻り

- **セグメントの器を `<div role="group">` から `<fieldset>` へ変えた。** Biome の
  `lint/a11y/useSemanticElements` が「その role を持つ意味づけの要素を使え」と指摘し、
  抑制コメントはフックで禁止されているため素直に従った。読み上げ名は `aria-labelledby` で
  付くのでテストの引き方は変わらなかった
- **`visual-approved` と `ui` を同時に付けて VRT の再実行がキャンセルされた。** VRT の
  ワークフローは `labeled` イベントのうち `visual-approved` のときだけ走るが、2 つ同時に
  付けると 2 本のイベントが並び、同時実行制御で先の 1 本がキャンセルされた。失敗した
  ワークフローを明示的に再実行して解消した（**ラベルは 1 つずつ付ける**）

## うまくいったこと

- **計画検証・実装検証の両方が、実際に効いた。** 計画検証は「そのまま実装すると通らない /
  仕様を落とす」を 5 件見つけ、実装検証は**ミューテーションで「守られていない判断」を 3 件**
  実測で見つけた。どちらも頭の中の判断では見つからなかったもの
- **表示確認を操作込みで通せた。** Storybook + headless Chromium を CDP で操作し、
  「ツリーで artboard を選ぶ → `Direction` の `row` を押す → キャンバスが横並びになる」まで
  実画面で確かめられた。`rules/ui-verification.md` が求める「主要な操作フローを通しで確認」に
  初めて実操作で応えられた
- **UI 案が答えを持たない判断を、却下案つきで Issue に残してから実装に入れた。** 「未指定の
  見せ方と戻し方」はレビューで差し替えられる形になっており、実際にレビューはこの点ではなく
  命名 1 件だけだった

## 規約への反映

### 1. 「biome の format を見落として push」が 2 回目 → `implementation-flow` フェーズ 7 を具体化する

PR #124 では「`CLAUDE.md` にコマンドが載っていない」ことが原因だったので Common Commands へ
追加した。今回はコマンドは載っており、**実行もしたのに出力を確認していなかった**。原因が
違うので、置き場所も変える。

**採らなかった置き場所と理由:**

- **1. フックを足す** — 足す必要が無い。`pre-push-lint.sh` が既にあり、`git push` を含む
  コマンド（`&&` で連結したものを含む）にマッチして biome の format 差分を検出し、push を
  deny することを**実測で確かめた**（一時ファイルを置いてフックへ直接 JSON を流した）。
  それでも今回 push は通っており、このセッションでは `post-edit-lint.sh` による編集後の
  自動整形も一度も働いていなかった。**フックが発火しない実行環境がある可能性が高いが、
  確証は取れていない**ので、フックの内容を変えても防げない。この観察は
  `.claude/hooks/README.md` へ注記として残す
- **2. 新しいスキルを作る** — 「push 前に検査を通す」は既に `implementation-flow`
  フェーズ 7 が担当している。順番が結果を変える種類の段取りでもないので、スキルを増やす理由が無い
- **4 / 5. `rules/` に書く** — 判断基準ではなく手順なので、`rules/` ではなくスキルの手順に置く

**採った置き場所（3）:** `implementation-flow` フェーズ 7 に、push 前に走らせる 4 つと
「**1 つずつ独立に実行して、それぞれの結果行を確認する**」ことを書く。`&&` で連ねると
途中の出力が流れて末尾しか見えない、という今回の失敗の形も一緒に残す。

### 2. `naming` が 10 回目 → `rules/naming.md` に `utils/` の語形を足す

指摘 13 は `rules/naming.md`「メソッド名を既存のドメインに揃える」の趣旨に当たるが、
**この節が挙げているのはコンパニオンオブジェクトの語彙（`create` / `from*` / `is*` /
`to*` / `collect*`）だけ**で、`utils/` の `<型名>Ex` には触れていない。`ArrayEx` /
`SetEx` の既存メソッドが全て動詞または結果を表す語で始まっている、という事実がどこにも
書かれていないため、`withPrepended` を選んだときに照らす先が無かった。

**採らなかった置き場所と理由:**

- **1. フック** — 「その名前がその層の語形に合っているか」は機械判定できない
  （`with` を一律に禁じると、`withLocation` のような正当な名前まで止まる）
- **2 / 3. スキル** — 段取りではなく判断基準なので、スキルの手順には乗らない

**採った置き場所（4）:** `rules/naming.md`「メソッド名を既存のドメインに揃える」へ、
`utils/` の `<型名>Ex` は動詞または結果を表す語で始める（`with*` の過去分詞は使わない）を
NG / OK つきで足す。

### 3. その他の分類は記録のみ

`plan`（31）/ `test-behavior`（30）/ `duplication`（18）/ `illegal-state`（9）/
`over-guard`（8）/ `logic-ownership`（7）/ `comment`（3）はいずれも 2 回以上だが、
**今回の指摘はどれも既存のルールに書かれている観点で、しかもその観点を持つ検証
（計画検証・実装検証のサブエージェント）が実際に全件を捕まえている**。ルールの抜けではなく
「1 人で書いているときには見えない」種類のものなので、規約を足さずに記録だけ残す。
