# PR #435 全体を収める / 選択に合わせるズームを足す（Shift+1 / Shift+2）

- マージ日: 2026-09-06
- 関連 Issue: #419（#373 から分離した 21 件のうちの 1 件）
- 差分規模: 30 ファイル / +1208 -72（15 コミット）

## ゴールと結果

Shift+1 で文書全体が、Shift+2 で選んでいるものが、キャンバスの中に収まる倍率と位置になる
（Figma の Zoom to fit / Zoom to selection）。倍率は既存の上下限（0.1〜4）を超えない。達成した。

**前回の調査（#419 の着手前コメント）が挙げた 3 つの前提は、いずれも成立しなかった。**
「ビューポートを持っていないので `ResizeObserver` を足すところから」→ 押された瞬間だけ測れば
要らない（`rules/hooks.md` の判定軸）。「外接矩形を `document.artboards` から取るか
`ArrangedArtboard` から取るかが最初の設計判断」→ どちらでもなく DOM を実測する（ノードの大きさを
決めるのはブラウザのレイアウトなので、Shift+2 はドキュメントからは出せない）。「VRT に差分が
出る」→ 出なかった（0 changed / 147 passed）。**調査コメントの前提を疑うところから計画が始まった
回**で、3 つとも実物へ当てて覆している。

想定外だったのは **Shift + 数字段が打つのは数字ではなく記号**（US で `!` `@`、JIS の Shift+2 は
`"`、AZERTY は逆に Shift 側が数字）だったこと。`event.key` では待てないので `KeyShortcut` を
判別可能な直和にし、`event.code` で待つ枝を足した。この差分でいちばん大きい変更になった。

## 手戻り

**1. Playwright の `scrollIntoView` で数値が合わないように見えた。**
`page.locator('[data-name="settings"]').click()` で artboard を選ぼうとしたとき、収まり方が
手計算と 250px ほどずれた。原因は **Playwright が click の前に `scrollIntoViewIfNeeded` を走らせ、
`overflow-hidden` のキャンバスの土台を `scrollLeft = 368` までスクロールしていた**こと。
`page.mouse.click(760, 280)`（絶対座標）に変えると一致した。実アプリでスクロールしうるかも
確かめている（画面外の artboard へ Tab で辿り着いても `scrollLeft` は 0 のまま。ホイールは
`preventDefault` してパンへ読み替えている）。**確認手段の側が前提を壊していた**形で、実装は
正しかった。

**2. 面積のガードを余白を足したあとに置いていた。** `+48` されたあとは必ず正になるので、
0 × 0 の対象でも余白ぶんの大きさを持ってしまい、空の範囲へ寄る倍率が決まる。ガードを割り戻し
直後（余白を足す前）へ移した。

**3. 期待値の計算違いが 1 件。** `use-canvas-view.fit.test.tsx` の期待値を `translate(12px, 237px)`
と書いたが実際は `212px` だった（縦の隙間の半分を計算し違えた）。テストが落ちて気づいた。
実装ではなくテストの側が間違っていたので期待値を直した。

**4. 通しテストを 1 件書いてから消した。** 4 本目として「フォーカスのある入力欄では収める
ズームが効かない」を書きかけたが、`within` を import しておらず、かつ**その振る舞いは
`useKeyShortcut.isConsumedBy` の責務**で既存の慣例どおり共有フック側のテストが持っていた。
編集画面の通しへ重ねる理由が無いので消した。
