# PR #1015 Result / Option の値リテラルをコンパニオンへ寄せ、判別子の検査を直書きまで広げる

- マージ日: 2026-10-05
- 関連 Issue: #524
- 差分規模: 42 ファイル / +432 -458

## ゴールと結果

ゴールは「`Result` / `Option` の表現（`ok` / `some` という判別子を持つ形）を、読み側だけでなく作る側・比べる側でも定義元の外へ漏らさず、push / CI で剥がれないようにする」。達成した。テストの期待値 104 件を `Result.ok` / `Result.err` / `Option.some` / `Option.none` へ移し、直読みの検出器を直書きまで広げて改名した（`result-option-discriminant-violations.py`、種別 `result-option-read` / `result-option-write`）。

GitHub 上の人のレビューは 0 件だった。`get_reviews` / `get_review_comments` / `get_comments` の 3 つとも確認した。コメントは、自分が投稿したテストケース表と bot の投稿（Storybook プレビュー・CI レポート・VRT）だけ。CI は全件緑で、VRT の差分は 0 件だった（189 件 passed）。

`solution-reviewer` は検出器を型（定義元だけが名前を持てる `unique symbol` キー）で置き換える方式を結論したが、Result / Option の表現を変える設計判断なので採らず #1013 に分けた（指摘 15）。
