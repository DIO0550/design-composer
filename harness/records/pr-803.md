# PR #803 hex でない colors トークンを invalid-color として報告し、3・4 桁の短縮形は展開する

- マージ日: 2026-09-26
- 関連 Issue: #773
- 差分規模: 11 ファイル / +171 -16

## ゴールと結果

ゴールは達成した。hex でない colors トークンが `invalid-color` の検証エラーとして報告される。3・4 桁の短縮形は読み込み時に 6・8 桁へ展開され、エラーにならない。
Issue の段階で仕様が決まっていなかった点（docs/04「値域の扱い」との関係・影とグラデーションを対象にするか・kind・`isValid` の扱い）は、実装前に 2 回止めてユーザーに確認した。影・グラデーションの色の報告は #801 に、トークンを指すエラーにノードの「表示」ボタンが出る件は #802 に、`validation/` 全体の見直しは #808 に分けた。
GitHub 上の人のレビューは 0 件（`get_reviews` / `get_review_comments` / `get_comments` の 3 つとも確認。コメントは bot の投稿と自分のテストケース表だけ）。セッション中に人の指摘が 1 件あった（指摘 1）。CI は初回から緑で、VRT は差分なし。

## 指摘

### 1. 不正な色の走査を validation 側に書いていた

- 分類: `ownership`
- 出どころ: `レビュー（人）`
- 内容: 判定は `ColorToken.isValid` にあったが、「トークン一式のどの色が不正か」の走査を `validation/` の `collectColorTokenErrors` に書いていた。セッション中に「validation は検証だけのファイルになっている。ドメインが自分の不変条件を管理すべきでは」と指摘を受けた。
  `TokenSet.collectInvalidColorNames` へ移し、validation はエラーへの詰め替えだけにした（main の `TokenSet.collectPaintNameConflicts` と同じ形）。validation 全体は #808。
- 既存ルール: rules/architecture.md「services はドメインを探してから使う」

### 2. 計画に「未決: なし」と書いたが、エラー一覧の「表示」ボタンの扱いが決まっていなかった

- 内容: `nodeName` にトークン名を入れると、エラー一覧にノードを探す「表示」ボタンが出る。既存のトークン名エラーに揃えて据え置く判断を Issue に書き、#802 に分けた。
- 既存ルール: `.claude/skills/implementation-flow/SKILL.md` フェーズ 3
