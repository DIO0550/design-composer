## ゴールと結果

ゴールは達成した。`publicProps` の宣言名に数字だけの名前（`1` / `20` / `007`）を書いたドキュメントは、検証エラー `invalid-public-prop-name` としてエラー一覧に出る。宣言名の規則は docs/02-data-model.md に書いた。
Issue は規則の形（識別子と同じ規則か別の規則か）を「docs と照らして決める」と委ねていた。既存テストの fixture が camelCase の宣言名（`actionLabel` / `textAlign`）を使っていたので、kebab-case は課さず、数字だけの名前だけを禁止した。
GitHub 上の人のレビューは 0 件（`get_reviews` / `get_review_comments` / `get_comments` の 3 つとも確認。コメントは bot の投稿と自分のテストケース表だけ）。CI は初回から緑で、VRT は差分なし（179 件）。

## 指摘

### 1. 禁止する理由「宣言順が保てない」が実物と食い違っていた

- 分類: `plan`
- 出どころ: `レビュー（plan-reviewer）`
- 内容: `Component.toJson` は publicProps を `Json.sortedMap` で名前の昇順に書き出すので、保存した時点で宣言順は保たれていなかった。
  崩れるのは「ファイルに書かれた順（読み込み時の `Object.keys`）」と「書き出しの昇順」の 2 つだと node で確かめ、理由を書き直した。
- 既存ルール: `.claude/skills/implementation-flow/SKILL.md` フェーズ 3 手順 3

### 2. docs に「既存 fixture が壊れる」を仕様の理由として書く計画だった

- 出どころ: `レビュー（plan-reviewer）`
- 内容: テストの都合は仕様の理由にならない。docs には「宣言名は prop 名を書く位置から指される」だけを書き、fixture の件は Issue の却下理由に留めた。
