3. **`🐛` と `[New Feature]` を取り違えたコミットメッセージを amend した。** タグと絵文字の対応を間違えた
4. **`Reveal` が左ペインを戻す振る舞いは計画に無かった。** 通しテストが「プロパティパネルに `home-title` が出ない」で落ちて発覚した。トークンを消して不正を作った直後は左ペインが Tokens なので、選んでもツリーにもプロパティにも出ない。`Go to source component` が Assets へ移すのと同じ形で Layers へ戻すようにした。**テストが無ければ気づかないまま「押しても何も起きない Reveal」を出していた**

### 介入 2: `plan` — 観点から **skill** へ上げる

指摘 3〜6 の 4 件がすべて `plan`。`count.sh` の時点で再発 9・pr-164 で観点層へ介入済みなので、4b の「介入後に 2 回再発 → 層を 1 つ上げる」に該当する（今回でさらに増える）。

**前回と同じ層（観点）への追記は選択肢に入れない。** plan-review.md には既に「変更で壊れる既存の資産を洗い出しているか」という観点があり、指摘 3 はまさにその観点で捕まったもの — つまり**観点は書かれていたが、計画を書く側が実行していなかった**。観点を増やしても同じことが起きる。

`hook` にできないかを先に確かめた: 計画は Issue のコメントに書かれた文章で、コード上に存在しない。「計画に挙げたファイル一覧」と「実際に変更したファイル一覧」の突き合わせは機械的だが、**計画の書式が固定されていないため抽出が成立しない**（見出しの表記ゆれで偽陽性が出る）。フックにはできない。

`skill` を選んだ理由: 指摘 3〜6 に共通しているのは「**計画をそのまま実行できるかを、計画の時点で機械的に確かめていない**」こと。これは判断ではなく**毎回同じ順番で踏む段取り**（触る公開 API を grep する → 呼び出し側を数える → テストの前提が既に在るかを確かめる）で、順番を間違えると意味が変わる（呼び出し側を数える前にテストを書き始めると、後から型が通らなくなる）。スキルの成立条件に合う。

置いたもの: `.claude/skills/plan-feasibility/`（計画の実行可能性を確かめる手順）。`implementation-flow` のフェーズ 3 と 4 の間から呼ぶ。

**下の層の記述を縮めた。** plan-review.md の「変更で壊れる既存の資産を洗い出しているか」は、手順そのものを新スキルへ移し、参照 1 行に置き換えた。
