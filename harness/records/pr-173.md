# PR #173 上部バー（パンくず・保存状態・ズーム）を足し、倍率の操作をキャンバスから移す

- マージ日: 2026-08-10
- 関連 Issue: #134
- 差分規模: 24 ファイル / +909 -504

## ゴールと結果

「開いているファイルの名前・保存状態・倍率が画面上部の帯から読め、ズームがそこから
操作できる。キャンバス上部の操作列は無くなっている」。達成した。

ゴールから 1 つずれた。Issue のゴール文は「**1 本の**帯」だったが、`開く / 新規作成` の帯
（`DocumentToolbar`）を消すとファイルを開く導線が無くなるため残し、帯は 2 本になった。
計画検証の A-3 で指摘され、ゴール文を「上部バーから読める / 操作できる」へ書き直して
Issue と Discord に乖離として記録している。

## 手戻り

計画から外れた箇所が 2 つ。どちらも Issue #134 に追記済み。

1. **保存バッジの出し分け**を、計画の `switch` から `as const satisfies Record<…>` の
   対応表へ変えた。持たせるものが「字面と色の 2 つ」で、`switch` にすると同じマークアップが
   3 回並ぶだけになるため。網羅の保証は `satisfies` が同じく効く（キーを 1 つ消すと `tsc` が
   落ちる）。`rules/coding.md`「状態をキーにした対応表は網羅のためだけに選ばない」に触れるので、
   なぜ対応表でよいかをコードのコメントに書いた
2. **コンポーネント名**をレビュー後に `DocumentTopBar` → `EditorTopBar` へ改名した（指摘 15）

## 規約への反映

`count.sh` で最後の介入以降の再発を数えたところ、今回足す分類のうち複数回に達しているのは
`duplication`（pr-152 / 層=hook 以降 7 回）・`plan`（pr-164 / 層=観点 以降 7 回）・
`comment`（pr-171 / 層=観点 以降 0 回 → 今回 4 件）・`test-behavior`（pr-171 / 層=rules
以降 0 回 → 今回 2 件）・`ui-fidelity`（pr-152 / 層=rules 以降 3 回）・
`over-guard`（pr-159 / 層=観点 以降 2 回）・`logic-ownership`（pr-157 / 層=rules 以降 2 回）。

**この回は記録だけにして、規約・スキル・フックへは介入しない。** 理由は次のとおり。

- **`duplication` については、機械で判定できる穴が 2 つ見つかったので #179 へ切り出した。**
  `.claude/hooks/lib/duplicate-test-helpers.py` が (a) 引数の型注釈を本体と読み違えて
  偽陽性を出す（この PR の `setup.tsx` で実際に発生）、(b) 同じ `__tests__/` の中しか
  見ないので指摘 7 の重複を捕まえられなかった。**フックを直す変更は記録と混ぜず、
  別 PR にする**（記録の PR にフックの挙動変更が乗ると、どちらをレビューしているのか
  分からなくなる）
- **`plan` / `over-guard` / `comment` / `test-behavior` / `ui-fidelity` / `logic-ownership`
  は、いずれも既存の観点（計画検証・実装検証のサブエージェント）が全件を捕まえている。**
  指摘 1〜14 はすべて自己修正で、レビューまで残ったのは 15・16・17 の 3 件だけ。
  観点が働いていないのではなく、働いた結果が記録に載っている。ここで規約を足すと、
  「見つかっている」ことを理由に文言だけが増える
- **`logic-ownership`（指摘 2）は判断そのもの**（第 1 引数の型が根拠にならない、という
  読み方）なので機械判定にできない。`rules/architecture.md` には既に
  「判断の起点は『その規則は誰の性質か』」と書かれており、抜けではなく読み落とし
- **`なし` の指摘 16（feature の粒度）は 1 回目**。`AGENTS.md`「1 回目の分類は記録するだけ」に
  従い、判断基準は #174 で決めてから規約へ反映する

**`illegal-state` が未介入のまま最多（10 回）になっている。** 今回の指摘 1 もこれに当たる。
ただし今回に限れば、実装へ入る前に計画検証の観点
（`plan-review.md`「不正な状態が型で表現できてしまわないか」）が捕まえており、
**観点が働いていないから溜まっているのか、単に頻出する分類だから溜まるのかが記録から
読み取れない**。ここを決めるには過去 10 件を読み直して「どの段階で見つかったか」を
数える必要があり、それは 1 本の PR の振り返りの範囲を超える。**次回以降の起点として
ここに書き残す**（数え方が決まらないうちに層を上げると、いちばん弱い `rules/` への
追記に落ち着いて次も同じ分類が出る）。
