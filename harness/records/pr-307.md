# PR #307 左ペインのストーリー枠を LeftPaneShell へ寄せ幅を 248px に統一する

- マージ日: 2026-08-24
- 関連 Issue: #304
- 差分規模: 8 ファイル / +130 -16

## ゴールと結果

ゴールは「左ペインのパネルを真似るストーリーの枠が 1 箇所になり、幅が 248px に揃う。`EditorLayout` のグリッド左列を直したときにストーリー側が黙って古くならない（テストが落ちる）」。達成した。6 ストーリーに散っていた枠（`w-62` 2 本 / `w-64` 4 本）を新設 `LeftPaneShell` に寄せ、`19rem − 15.5rem === 3.5rem`（レール `w-14`）の突き合わせテストを追加した。#305（右ペイン側）と対になる回。

human レビューは 0 件。CI は 1 回の push で、視覚差分（`visual-regression`）以外すべて success。**指摘はすべてサブエージェント（`plan-reviewer` 7 件 / `implementation-reviewer` 1 件）から出た。**

**この回の中心は、計画段階で「高さの変種」という抽象を捨てられたこと。** 当初の計画は `LeftPaneShell` に `height: "content" | "panel"` を持たせて `assets-panel` の `h-96` を維持する形だったが、`plan-reviewer` の指摘 1・2（`panel` が既存の `LeftPanePanel` と衝突する / `h-96` は実ペインの高さではないのに名前がそう約束する）で、prop ごと落として幅・枠線・地色だけの殻にした。結果としてテストの観点も 1 件で足り（指摘 3 が消える）、殻は children だけを取る形になった。実装後の指摘は biome の整形 1 件のみ。

VRT は 2 本が Changed（`features-tokens-tokenlist--default` / `--color-selected`、diffRatio 0.0022 / 0.0023）で、差分画像を見て「枠の右端と右寄せの hex が 8px 左へ寄っただけ」を確認してから `visual-approved` を付けた。**`w-64` を縮めた残り 2 本と `assets-panel` の `h-96` 除去は閾値 0.002 未満で passed になっている**（指摘 8）。

## 指摘

### 1. 高さの値名 `"panel"` が既存の `LeftPanePanel` と衝突し、`RightPaneShell` の語彙とも割れていた

- 分類: `naming-prefix-collision`
- 出どころ: レビュー（`plan-reviewer`）
- 内容: `panel` はこのリポジトリで既に「248px の中身パネル」`LeftPanePanel` を指す語で、それを「高さ = `h-96`」の値名に使うと 1 語が 2 つの意味を持つ。加えて兄弟の `RightPaneShell` は同じ「背の高い変種」を `"content" | "pane"` と綴っており、`"panel"` にすると対で作った部品どうしで語形が 2 通りに割れる
- 既存ルール: rules/naming.md「その名前が既に別の意味を持っていないか確認する」
- 次にどう防ぐか: 今回は記録のみ（`height` prop ごと落とした。#305 の指摘 5 に続き `Pane*` の射程で 2 回連続）

### 2. `h-96` は実ペインの高さではないのに、値名がそう約束していた

- 分類: `naming-vocabulary-alignment`
- 出どころ: レビュー（`plan-reviewer`）
- 内容: `RightPaneShell` の `"pane"`(=`h-[32rem]`) には「スクロールを視覚差分に載せる」という記された Why があるが、`h-96`(384px) は `assets-panel` の既存高さを引き継ぐだけで、実画面の左ペインは全高。`"pane"` / `"panel"` という名前は「実ペインの高さ」を示唆するのに実体が伴わず、なぜ 384px なのかも書かれていなかった
- 既存ルール: rules/naming.md「名前と実体を一致させる」
- 次にどう防ぐか: 今回は記録のみ（兄弟 4 本が元から hug 高で成立していることを根拠に `h-96` を落とし、殻から高さの概念を無くした）

### 3. 新しいテストの一覧が、既存ファイルの観点より薄かった

- 分類: `plan-migration-mapping`
- 出どころ: レビュー（`plan-reviewer`）
- 内容: `editor-layout.pane-width.test.tsx` は既に 2 件（`"pane"` / `"content"` の両方で幅 = 3 列目）を持ち、「高さの選択が幅を漏らさない」を守っていた。計画は左ペイン側を `"content"` 相当 1 件しか挙げておらず、`"panel"`(h-96) 枝に幅 class が混じっても捕まらない状態だった。既存の観点を数える前に新しいケースだけを並べていた
- 既存ルール: rules/testing.md「API を作り替えるときは、既存テストの観点を先に数える」
- 次にどう防ぐか: 今回は記録のみ（指摘 1・2 の対応で高さの変種自体が消え、1 件で網羅になった）

### 4. 却下理由が事実と違い、検討が閉じていなかった

- 分類: `plan`
- 出どころ: レビュー（`plan-reviewer`）
- 内容: 「本物の `LeftPaneRail` を描画して幅を読む」を却下した理由を「依存方向で届かない」と書いたが、`features/editor` から `features/sidebar` の import は公開 API 経由で**許可されている**。実際の妨げは `LeftPaneRail` が `sidebar/index.ts` に公開されていないこと。あわせて「レール幅を公開して `3.5` の重複を消す案」が却下案に無く、検討が閉じていなかった
- 既存ルール: `AGENTS.md`「計画・却下した案・その理由は、すべて Issue に追記する」
- 次にどう防ぐか: 今回は記録のみ（理由を書き直し、公開案も「JIT がリテラルしか拾わないので class と定数の 2 箇所重複が新たに生まれる」として却下案に足した）

### 5. テスト内の `3.5` と `w-14` を結ぶものが無く、結合が doc に書かれていなかった

- 分類: `comment-missing`
- 出どころ: レビュー（`plan-reviewer`）
- 内容: テストが強制する `列[0] − 殻幅 === 3.5` の `3.5` は `LeftPaneRail` の `w-14` の写しで、レール幅が変わったときにこのテストは「殻幅（パネル部 248px）を動かせ」と誤って迫る。割り切りとして許容できるが、その結合と「レール幅を変えたらここも直す」が計画にも doc にも無かった
- 既存ルール: rules/coding.md「コメントは doc と Why / Why not に絞る」
- 次にどう防ぐか: 今回は記録のみ（`RailWidthRem` の doc に写しである旨・Why not・「レール幅を変えたらこの値も直す」を書いた）

### 6. 「`p-3` 据え置き」を視覚差分ゼロと同義に扱い、実例へ当てていなかった

- 分類: `plan-scope-verification`
- 出どころ: レビュー（`plan-reviewer`）
- 内容: `assets-panel` は元が `h-96 … p-3`（枠自体に padding）で、新形は枠（padding 無し）+ 内側 `p-3` div。padding 値が同じでも `h-96` の中での中身の伸び方は変わりうるのに、計画は「`p-3` は据え置き」とだけ書いて確認手段を挙げていなかった
- 既存ルール: `.claude/skills/implementation-flow/SKILL.md`「計画」フェーズ 3 手順 2
- 次にどう防ぐか: 今回は記録のみ（`h-96` を落とす判断になったため構造変化そのものが消え、Storybook で 6 ストーリーの実測幅 248px と崩れの無いことを確認した）

### 7. 任意値 `w-[15.5rem]` を選んだ理由の doc が無かった

- 既存ルール: rules/coding.md「コメントは doc と Why / Why not に絞る」

### 8. 8px の幅縮小は 4 本中 2 本しか VRT に出なかった

## 手戻り

**実装のやり直しは無し。** 計画段階での作り替えが 1 つある。

- **`height` prop（`"content" | "panel"`）を計画から丸ごと落とした**（指摘 1・2）。`assets-panel` の `h-96` を維持する形から、殻は幅・枠線・地色だけを持ち高さは持たない形へ。これに伴い `assets-panel` は hug 高になり、意図した視覚差分として扱った（閾値未満で VRT には出なかった / 指摘 8）
- コミット直前の修正が 1 つ（指摘 9 の biome 整形）。コミットには整形後の形しか載っていない

計画からの逸脱: 上記のとおり公開する prop が 1 つ減った以外は計画どおり。ファイル表・テスト一覧に変更なし。

## うまくいったこと

- **`plan-reviewer` の指摘で、実装前に抽象を 1 つ捨てられた。** `height` prop は書いてから消すと 6 ストーリー分の書き換えが二度手間になるところだった
- **却下案を「なぜ採らないか」まで書き直した。** レール幅を公開する案は、採らない理由（重複が消えず場所が増える / テストのために公開 API を広げる）まで Issue に残した
- **VRT の差分画像を開いてから `visual-approved` を付けた。** 件数（2 本）だけでなく、pink が枠の右端に限られていること・左側（名前・スウォッチ）が動いていないことを画像で確認した
- **push 前検査を 1 つずつ独立に実行した**（typecheck / oxlint / biome / vitest / doc コメント / テスト規約）。フックが不発の環境だったので、通したことを PR 本文にも書いた
- **#305 と対で分けた Issue の分割が効いた。** 左右で幅が別（15.5rem / 18rem）という判断が最初から分かれていたため、`RightPaneShell` を汎用化する誘惑に乗らずに済んだ
