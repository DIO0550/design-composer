# PR #157 アプリ内編集で作った不正を画面に出す（state.errors とは別の器で持つ）

- マージ日: 2026-08-09
- 関連 Issue: #128
- 差分規模: 17 ファイル / +553 -79

## ゴールと結果

**アプリ内の編集で作った不正（使用中トークンの削除など）が、ファイルを開き直さずに画面へ出る。
外部変更由来の表示と区別が付き、キャンバスは凍らない。** 達成した。

器の設計は「別の器にする」だけでなく、**ドキュメント由来は器を持たず導出する**形に落ちた
（入力が表示中のドキュメントだけなので、持つと食い違った一覧が表現できてしまう）。

ゴールからずれたところは無い。ただし**この issue の外に 2 つの穴が見つかり**、どちらも
別 issue へ切り出した（#156 / #158）。

## 規約への反映

置き場所は Step 4 に従い強制力の強い順（フック → 新しいスキル → 既存スキルの観点 →
`rules/`）に検討し、**採らなかった理由も残す**。

### `なし`（doc コメントが無い / 3 回目のコメント系）→ フック（#1）

`.claude/hooks/check-doc-comments.sh` と `.claude/hooks/lib/missing-doc-comments.py` を足した。
編集したファイルの中で、**doc コメントの無い宣言**（ファイル直下の `function` と、
`export` された `function` / `const` / `type`）を知らせる。

**これは機械的に判定できる。** 「宣言の直前に `/** */` か `//` があるか」は白黒が付き、
判断が要らない。`check-test-helper-duplication.sh` が「同じ `__tests__/`」「本体が完全一致」と
対象を絞って成立しているのと同じ形で、こちらも次の 3 つで絞っている。

- **`src/` の実装ファイルだけ**（`__tests__/` / `*.stories.tsx` / `__stories__/` は対象外）
- **ファイル直下の宣言だけ**（入れ子の関数・オブジェクトのメソッドは見ない）
- **同じファイルに同名の宣言があり、そちらに doc があれば対象外**
  （型とコンパニオンオブジェクトが doc を共有する、このリポジトリの形を偽陽性にしないため）

**`.claude/hooks/README.md`「移植元から見送ったもの」の判断を更新した。** 見送りの理由は
「JSDoc 必須ルールはこのリポジトリの規約に存在しない」だったが、その前提は PR #152 で
`rules/coding.md`「コメントは doc と Why / Why not に絞る」が入った時点で消えていた。
**規約が増えたときに、それを理由に見送ったフックを見直す**という手順が無かったのが根本。

**ブロックにしなかった理由**: 導入時点で既存の違反が **73 件（ファイル直下の `function`）/
77 件（`export` された宣言）** ある（`--all` で機械的に数えた）。触っていない分まで push を
止めると、直す気の無い違反を避けるためのエスケープハッチが増え、フック全体が信用されなく
なる（README.md「例外(エスケープハッチ)」が記録している失敗の形）。
`check-test-helper-duplication.sh` と同じく**編集したファイルの分だけ**を報告する。

**粒度は PR #157 のレビュースレッドで確認中。** 上の 2 つ（ファイル直下の `function` /
`export` された宣言）を両方対象にしてあるが、`export` された宣言だけへ狭める判断もありうる。
狭めるのは `lib/missing-doc-comments.py` の 1 定数で切り替えられる形にしてある。

### `logic-ownership`（5 回）→ `rules/` に追記（#4）

`rules/architecture.md`「ロジックの帰属先」の**逆向きの節に、出口側**を足した。
これまでは「入力欄の約束事をドメインへ持ち込まない」（入口）だけが書かれており、
**表示の綴り（出口）**についての記述が無かった。

あわせて `rules/testing.md`「テスト用ヘルパーの置き場所」へ歯止めを 1 つ足した。
今回の誤りは**規約どうしの衝突**で起きている。

| 規約 | 今回の働き方 |
|---|---|
| rules/testing.md「テストのヘルパーが汎用の操作なら実装側へ」 | 表示の綴りをドメインへ押し込む圧力になった |
| rules/architecture.md「ロジックの帰属先」 | 押し込んではいけないと言っている |

**移す前に、その assert が表示の綴りを必要としていること自体を疑う**という一段を入れると、
今回の場合は「構造のまま比べればよい」に着地し、衝突そのものが消える。

**それより上を採らなかった理由**: フック（#1）にはできない（「その値は表示のための綴りか」は
判断で、文字列一致では偽陽性しか出ない）。新しいスキル（#2）でもない（段取りが増えたのでは
なく、既存の判断基準に**向きが 1 つ足りなかった**だけ）。既存スキルの観点（#3）にも
置けるが、**帰属先の判断そのもの**なので、判断基準を書いてある `rules/` に隣り合わせで
置くほうが読まれる。

### `test-behavior`（21 回）→ 既存スキルの観点（#3）

`implementation-review.md`「テストが守っているかの観点」へ、**中心の判断が「2 つの状態が
同時に成り立つとき、どちらを選ぶか」の形をしているなら、その入力を作ったテストがあるかを
確かめる**を足した。

今回の空振り（指摘 7）は、既存テストがどれも**片側しか作っていなかった**ために起きている。
「壊すミューテーションを入れる」という既存の観点は通っていたのに、**反転しても入力が
片側だけなら挙動が変わらない**ので落ちなかった。ミューテーションの入れ方ではなく、
**入力の作り方**の観点が抜けていた。

**フック（#1）にしなかった理由**: PR #150 / #152 と同じ。全テストを変異ごとに回すと CI 時間が
跳ね、「差分の中心の判断」を選ぶところが機械化できない。
**新しいスキル（#2）にしなかった理由**: フェーズ 6 で必ず読まれる場所にある観点の
**確かめ方が 1 段浅かった**だけで、段取りは増えていない。

### `plan`（18 回）→ 既存スキルの観点（#3）

`plan-review.md`「変更で壊れる既存の資産を洗い出しているか」へ、**部品から位置・大きさを
外す（別の場所へ移す）計画なら、その部品の単体ストーリーが位置を与えているかを見る**を
足した。

指摘 17 は「実画面は変わっていないのにストーリーだけが変わる」形で、**テストでは絶対に
落ちない**（happy-dom は Tailwind を解決しない）。既存の観点は `*.stories.tsx` を数えることを
求めているが、**位置を持たせている decorator まで見る**とは書かれていなかった。

**フック（#1）にしなかった理由**: 「この部品は位置を失ったか」は差分の意味の話で、
機械判定できない。VRT が実際に赤くして知らせるので、検出は既に効いている
（今回も VRT で気づいた）。足りないのは**計画の段階で数えること**。
