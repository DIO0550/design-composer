## ゴールと結果

`harness/records/count.sh` の再発トップだった `plan`(再発 13・pr-164 で観点層へ
介入済みだが、以降 7 本中 13 件再発)へ `harness-growth` スキル Step 2 で介入する
かどうかを判断すること。

**結果: `implementation-flow` フェーズ 3 へ、下記の必須手順を追記した。**
反映を見送っていた理由と、見送りを解除した経緯は下記。

## 再発の内訳(pr-164 以降)

| PR | 件数 | 概要 |
| --- | --- | --- |
| pr-168 | 3 | UI 案の再確認漏れ(可視文言・ARIA 操作性) |
| pr-171 | 4 | 却下理由の事実誤認・`switch` 内 `useId`・変更で壊れる既存資産の未把握・通しテスト漏れ |

`pr-185.md`(`harness/records/pr-185.md`「規約への反映」)が既にこの 13 件を分析済みで、
共通点を「**計画をそのまま実行できるかを、計画の時点で機械的に確かめていない**」と
特定している。`hook` は不成立(計画は Issue コメントの自由記述で書式が固定されて
おらず抽出できない)、`skill` が候補(「触る公開 API を grep する → 呼び出し側を
数える → 計画に書くテストが実際に書けるかを確かめる」という順序の決まった段取り)、
という結論も pr-185 の時点で出ている。本 PR はこの分析を再確認しただけで、
新しい判断材料は加えていない。

## この回、いったん反映を見送っていた理由

pr-190(#187 の棚卸し)のレビューで次の指摘があった:

> 集計が 4a/4b/4c の閾値を満たしていても、規約・スキルへの実際の書き込みを伴う
> 介入は棚卸しルーティンの判断だけで確定させず、まず記録のみで PR を出し、
> オーナーの承認を経てから反映してほしい

これに従い、本 PR は当初この分析だけを載せ、`ui-fidelity` / `comment` / `なし`
(#187)と同じ「記録のみ・オーナー承認待ち」で止めていた。

## 見送りを解除した経緯

本 PR(#193)を提示した後、オーナーから会話で直接「PR を作ってください」と
反映の承認を得た。承認は**この PR(`plan` の skill 層への層上げ)に対するもの**で、
#187(`ui-fidelity` / `comment` / `なし`)・`duplication` の語彙分割検討は含まない
(別トリガーで個別に承認を得る)。

## 反映内容

1. `implementation-flow/SKILL.md` フェーズ 3 の末尾へ、フェーズ 4 へ渡す前の
   必須手順として「呼び出し側を grep で数える」「テストの前提(ヘルパー・
   フィクスチャ・API)が実在し想定通り動くか確認する」の 2 つを追記した
2. `implementation-flow/references/plan-review.md`「変更で壊れる既存の資産を
   洗い出しているか」は、grep での数え上げが手順 1 に移ったため、
   「ファイル表に挙がっているか」だけを見る形に縮めた(参照 1 行化)
3. `harness/records/pr-185.md`「規約への反映」に `対策済: plan 層=skill at pr-193`
   を追記した(次回の `count.sh` はここから数え直す)
