## ゴールと結果

`harness/records/count.sh` の再発トップだった `plan`(再発 13・pr-164 で観点層へ
介入済みだが、以降 7 本中 13 件再発)へ `harness-growth` スキル Step 2 で介入する
かどうかを判断すること。

**結果: この回は反映せず、記録のみとする。** 理由は下記。

## 再発の内訳(pr-164 以降)

| PR | 件数 | 概要 |
| --- | --- | --- |
| pr-168 | 3 | UI 案の再確認漏れ(可視文言・ARIA 操作性) |
| pr-171 | 4 | 却下理由の事実誤認・`switch` 内 `useId`・変更で壊れる既存資産の未把握・通しテスト漏れ |
| pr-173 | 2 | 配線を通す通しテストの不足・不要になる公開 API の見落とし |
| pr-185 | 4 | 同じ部品を使う別画面の見落とし・テストの足場が無いことへの未把握・テストヘルパーの前提不成立・却下理由の不成立 |

`pr-185.md`(`harness/records/pr-185.md`「規約への反映」)が既にこの 13 件を分析済みで、
共通点を「**計画をそのまま実行できるかを、計画の時点で機械的に確かめていない**」と
特定している。`hook` は不成立(計画は Issue コメントの自由記述で書式が固定されて
おらず抽出できない)、`skill` が候補(「触る公開 API を grep する → 呼び出し側を
数える → 計画に書くテストが実際に書けるかを確かめる」という順序の決まった段取り)、
という結論も pr-185 の時点で出ている。本 PR はこの分析を再確認しただけで、
新しい判断材料は加えていない。

## この回、反映を見送る理由

pr-190(#187 の棚卸し)のレビューで次の指摘があった:

> 集計が 4a/4b/4c の閾値を満たしていても、規約・スキルへの実際の書き込みを伴う
> 介入は棚卸しルーティンの判断だけで確定させず、まず記録のみで PR を出し、
> オーナーの承認を経てから反映してほしい

`plan` の層上げ(`implementation-flow` フェーズ 3 への必須手順の追記)も同種の
反映であり、`ui-fidelity` / `comment` / `なし`(#187)と同じ扱いにする。

**`対策済` の行は書かない。** 反映していないため、`count.sh` の再発数はリセットしない。

## 積み残し

- `plan` を実際に skill 層へ上げる作業(`implementation-flow` フェーズ 3 に
  「触る公開 API を grep → 呼び出し側を数える → テストの足場を確認」の順で
  必須手順を追記する案)は、オーナーの承認後に別 PR で行う
- `duplication`(再発 10・pr-152 で既に hook 層。最上位のため上げ先が無く、
  語彙の分割(2c)を検討する必要がある)は、この回のスコープ外(条件ごとに PR を
  分けるため、次回以降の棚卸しで扱う)
- #187(`ui-fidelity` / `comment` / `なし`)も同じ理由で承認待ちのまま。この PR の
  スコープ外
