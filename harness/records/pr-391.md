- マージ日: 2026-08-31

## ゴールと結果

#383: `.dcmp` の artboard がキャンバス上の座標（`x` / `y`）を持ち、その座標で描かれる。
#390: 見出しを掴んでドラッグすると、その座標が動く。
#392: 背景（子が乗っていないところ）でも掴め、見出しも枠の幅いっぱいになる。

3 つとも達成した。ただし**ゴールは 2 回広がっている**。

1. #383 を単独で出したあと、オーナーが実機で触って「全然ドラッグで移動できないけど」と
   指摘。#390 を同じ PR へ畳んだ（指摘 3）
2. #390 のあと、オーナーが「名前のところだけドラッグできるのは使いにくい」「ハンドルも
   ないからリサイズできるか分かりにくい」と指摘。前者を #392 として同じ PR へ載せ、
   後者は既存の #371 に寄せた（新規起票しない判断）

## 規約への反映

無し。`harness-record` の管轄は記録を 1 ファイル足すところまでで、集計・介入の判断・
`rules/` やフック・スキルの変更は `harness-growth` が行う。

この回の材料は次の 4 点。

- **`subagent-control` が 1 件（指摘 18）。この分類で唯一、CI を実際に落としている。**
  `implementation-flow` は「返ってきたら指摘を読む前に `git status` を見る」までは
  書いているが、**走っている最中にコミットしない**は書かれていない。層としては
  観点（スキルの手順）で、hook（コミット前に走行中のエージェントを検出する）まで
  上げる余地がある
- **`plan-comment-reference` が同じ PR 内で 2 回（指摘 2・17）。** どちらも
  「コメントの中でだけ対象を名指ししているファイルが、import を数えたファイル表に
  挙がっていない」形。#383 で 1 度指摘を受けたのに、#392 の計画で同じ数え方をしている
- **すり抜けが 2 件**（指摘 3・7 のうち `レビュー（人）` は指摘 3、`CI` は指摘 7・18）。
  指摘 3 は**実機で触るまで誰も気づかなかった**もので、計画・実装の両方のサブエージェントを
  通過している。前回（pr-384）のすり抜け 2 件も同じ性質で、**2 回連続で「操作して
  みるまで分からない」形がすり抜けている**
- **`分類: なし` が 3 件（指摘 3・5・25）。** 内訳は
  (a) 「壊れない」と「単独で使える」を分ける分割の判断軸が無い、
  (b) まだ消費者が居ない規則を次の消費者で検算する形が無い、
  (c) 「1 つの assert が複数の仕様を固定していないか」は規約にあるのに分類の語彙が無い。
  (c) は語彙表の穴がはっきりしている。

  （`onPointerLeave` での取り消し）が新しい操作を巻き込む形で、`over-guard` が想定する
  「自分で足した過剰なブロック」とは向きが違う
