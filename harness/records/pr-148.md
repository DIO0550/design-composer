# PR #148 選択中トークンの参照元を右ペインに列挙する

- マージ日: 2026-08-08
- 関連 Issue: #127
- 差分規模: 13 ファイル / +1278 -2

## ゴールと結果

ゴールは「トークンを選ぶと、そのトークンをどのノード / artboard / 部品定義のどの prop が
参照しているかが右ペインに件数付きで並び、参照が無いトークンは 0 件として読み取れる」。達成した。

Issue #127 は当初 5 タスク（収集・`Used by`・キャンバスの破線・フローティング表示・
`reveal in tree`）を持っていたが、**キャンバス連動を #147 として分離**して 2 タスクにした。
Issue 本文自身が「旧案には無かったキャンバスとの連動が加わっている」と線を引いており、
右ペインの列挙だけでも独立してマージできる（キャンバスは何も変わらない）ため。

**ゴールのずれが 1 点ある。** 「設定されている prop だけを数える」と決めたため、
スキーマデフォルトで解決されるトークン（Text の `typography` の既定 `body` など）が
`Used by` 0 件と出る。理由（行が指すのは編集できる prop であり、今の dangling 検証も
設定済み props しか見ない）は残したが、「よく使われている既定のトークンが 0 と出る」
ズレは残る。PR で判断を仰いだ。

指摘は 16 件。うち人によるレビューが 2 件、残る 14 件は計画検証（6 件）と実装検証（8 件）の
サブエージェントから。CI の失敗は 0 件（VRT は差分ありだが `visual-approved` で承認済み）。

## 指摘

### 1. 部品定義の中の参照を「数えない」と計画していた

- 分類: `ui-fidelity`
- 出どころ: 自己修正（計画検証のサブエージェント）
- 内容: UI 案の `Used by` の 2 行目 `◆ primary-button.background` を**インスタンスの行**と
  読み、「部品定義はキャンバスにもツリーにも出ないので数えない」と計画した。しかし
  `primary-button` は同じ UI 案の `Assets` パネルに `Components` の 1 行として出ており、
  `Layers` ツリーのノード名には無い。さらに `background` は `primary-button` の公開 prop
  ではない（初期部品セットの `publicProps` は `label` だけ）ので、**インスタンスの上書きの
  行としては成立し得ない**。部品定義の行としか読めなかった。
  実害も具体的で、`DocumentTemplate.DEFAULT` のトークンは大半が部品定義からしか
  参照されていない（`white` / `gray-100` / `gray-500` / `sm` / `lg` / `subheading` など）ため、
  除外すると新規ドキュメントで `Used by` がほぼ全部 0 になり、ゴールが反転していた
- 既存ルール: `rules/ui-verification.md`「UIの拠り所は `docs/Design Composer.html`」
  （**開いて見たうえで読み違えた**。1 画面だけを見て、他の画面と突き合わせなかった）
- 次にどう防ぐか: 下の 14 と合わせて観点へ追記する

### 2. 参照元を「名前 + prop 名」だけの型にしていた

- 分類: `illegal-state`
- 出どころ: 自己修正（計画検証のサブエージェント）
- 内容: `{ nodeName; prop }` で計画したが、行に出す型アイコンを決めるために表示側が
  `findNode` →（`none` なら）`findArtboard` の 2 段引きを書くことになる。すると
  (a) 「artboard かノードか」の場合分け（ドメインの知識）が features のコンポーネントに入り、

  `switch` の網羅をコンパイラに守らせる形にした。副産物として、計画にあった
  `type-glyph` の抽出と `document-tree` の変更（2 ファイル）が不要になった
- 既存ルール: `rules/coding.md`「不正な状態を型で表現できなくする」
- 次にどう防ぐか: **`illegal-state` は通算 5 回目。** ただし今回は計画検証で捕まっており、
  ルールも観点も既にある（実装前に直せた）。追記はせず、既存の段が働いた例として記録する

## うまくいったこと

- **計画検証が値の定義の誤りを実装前に捕まえた。** 指摘 1（部品定義を数えない）は
  実装後に見つかっていたら domain・テスト・ストーリーの全部を書き直すことになっていた。
  検証エージェントが UI 案の他の画面（`Assets` の `Components` 一覧）と突き合わせて
  「この行はインスタンスではありえない」まで降りたのが効いた
- **直したテストにミューテーションを入れて落ちることを確かめた**（指摘 10）。
  「枠を出さない」に変えたあと、実装のガードを外して落ちることと、変更前の assert なら
  通ってしまうことの両方を見た
- **UI 案の該当箇所を playwright で要素単位に切り出して見た。** `Used by` の行が
  「型アイコン + `<名前>.<prop名>`」で、`+ 5 more` が `cursor:pointer` を持たない灰色の
  文字であることまで確認できたので、「`+ N more` は押せない表示にする」を根拠付きで決められた
- **操作の通しを実機で確認した。** `OpenedDocumentEditor` のストーリーで
  Tokens へ切り替え → `primary` を選ぶ → `white` へ選び直す、を playwright で操作し、
  件数・行・アイコンが入れ替わることを見た（静止画だけでは選び直しの更新は分からない）

**`なし` の 1 件（表示確認の手順）について。** これは指摘ではなく、この回で見つけた
**手順の穴**として記録する。`rules/ui-verification.md` は `pnpm dev`（ポート 14000）での
確認を手順としているが、編集画面はドキュメントを開くのに Tauri IPC / ダイアログを使うため
**ブラウザでは開始画面から先へ進めない**（実際に開いて確認した）。手順が実行不能なまま
書かれていると、毎回その場で代替（Storybook）を判断することになり、確認の粒度が回ごとに
ぶれる。VRT が比較しているのも Storybook なので、そちらを正式な手順として書く。

**なぜフック（#1）にしなかったか。**

- `ui-fidelity` — 「UI 案を開いて他の画面と突き合わせたか」は成果物に痕跡が残らない。
  文字列でもコマンドの成否でも判定できない
- `duplication` / `plan` — 判定が判断（pr-141 / pr-144 と同じ結論）。「既存の公開 API と
  同じことをしているか」は名前も形も違うので一致では拾えない（今回の
  `publicPropTarget` と自前の 3 段がまさにそれ）
- `test-behavior` — ミューテーションテストなら機械判定できるが CI 時間が跳ねる
  （pr-144 で同じ検討をして「費用が見合わない」と結論済み）。**今回はその代わりに、
  疑わしい 1 件だけ手でミューテーションを入れて確かめた**（指摘 10）。この「1 件だけ手で回す」
  を観点として書くほうが現実的なので、`rules/testing.md` の追記に含める
- `なし`（表示確認の手順）— 手順の記述であってコードの判定ではない
