# PR #205 フックの不発を、検出できる形と抜けない配線に直す

- マージ日: 2026-08-12
- 関連 Issue: #147

## ゴールと結果

ゴールは #147 のコメント（[#issuecomment-5268046487](https://github.com/DIO0550/design-composer/issues/147#issuecomment-5268046487)）が
記録した「フック不発環境」を直せるかどうか。**達成したが、報告されていた症状そのものとは
別の欠陥が原因の中心だった。**

調べた結果、独立した 3 つが重なっていた。

1. カナリアが `jq` に依存しており、`jq` の無い環境では**カナリア自身が exit 127 で終わって
   「配線が読まれていない」と見分けが付かない**（＝検出が信用できない）
2. `core.hooksPath` の配線が DevContainer の `postCreateCommand` にしか無く、
   **クローン直後は未設定**（この回のセッションでも未設定・`.git/hooks/` も空だった）
3. その結果、doc コメントとテスト規約の検査は層 2・層 3 の両方が抜けた状態になっており、
   実際に doc の無い宣言が main へ入っていた

**この回のセッションではフックは発火していた**（`echo hook-canary` が deny された）。
不発は環境ごとに出たり出なかったりする。前回（#147 の記録）と同じリモート実行環境で
結果が割れている。

`.claude/hooks/README.md`「強制力の序列」は「層 3 が抜けても層 2 が守る」と書いていたが、
**層 3 が抜ける環境と層 2 が抜ける環境は同じもの**だった。序列が前提にしていた独立性が
無く、2 層が同時に外れていた。

## フックの発火

**発火した（この PR の主題なので詳しく残す）。**

- `echo hook-canary` は **deny された**。前回（#147 のコメントが記録した回）は
  同じリモート実行環境で通ってしまっており、**環境ごとに結果が割れている**
- `pre-push-doc-comments.sh` が最初の `git push --dry-run` を**実際にブロック**した
  （指摘 2 の既存違反を検出）。PreToolUse が配線どおりに効いていることの実証にもなった
- `post-edit-lint.sh` が Edit のたびに oxlint / biome を走らせていた（いずれも 0 件）
- **git hooks（層 2）は、この PR を作る時点では効いていなかった。**
  `core.hooksPath` が未設定で `.git/hooks/` も空だった。`prepare` を入れた後の push では
  `harness/githooks/pre-push` が実際に走っている
- この環境には `jq` / `python3` とも存在した。したがって**前回の不発の原因が
  `jq` の欠落だったのか、配線が読まれなかったのかは特定できていない**。
  改修後のカナリアは前者なら欠落を名指しするので、次に不発が出た回で切り分けられる

## うまくいったこと

- **報告された症状をそのまま信じずに、まず現在の状態を測った。** 「フック不発環境だった」
  という報告に対し最初にやったのが `echo hook-canary` の実行で、**この回は発火している**
  ことが分かった。ここで「環境の問題なので直せない」と結論せず測り続けたので、
  本命（`core.hooksPath` 未設定）に辿り着けた
- **「見分けが付かない」を実際に再現してから直した。** カナリアの `jq` 依存は、
  PATH から `jq` を外して exit 127 になることを実測してから修正した。
  修正後も「`jq` あり」「`jq` が exit 127」「PATH に `bash` と `cat` だけ」の 3 通りと、
  誤検知しないこと（コミットメッセージ・grep・`hook-canary-x`）を確かめている
- **フォールバック層が本当に存在するかを確かめた。** README が「git hooks が守る」と
  書いていることを鵜呑みにせず `git config --get core.hooksPath` を引いたのが、
  この回のいちばん効いた 1 コマンドだった。**ドキュメントが宣言している防御は、
  配線されているかどうかを別に確かめる必要がある**

## 規約への反映

**この記録では行わない。** 集計と介入の判断は `harness-growth` の管轄。
次に数える人へ、この回で見えた候補を 3 つ残す。

- **`naming` がこの回で pr-168（層=rules）以降 4 件目になる。** 内容は
  「慣習的な名前（`install`）を借りたが、このリポジトリの語彙では何を指すか言えていない」。
  rules には既に明文があって素通りしているので、再発が続く場合の介入先は
  rules 層ではなく**その上**が候補になる
- **`comment-missing` について、この PR 自体が hook 層（CI の `rules-check`）へ検査を
  置いている。** pr-192 の介入は層=観点だったので、これは 1 段上げたことになる。
  ただし `対策済` の行は `harness-growth` が書くものなので、ここには書かない。
  棚卸しの際にこの回を起点として数え直すかどうかを判断してほしい
- **「ドキュメントが宣言している防御が、実際には配線されていない」形は分類の語彙に無い。**
  指摘 2 の根本原因はこれで、`comment-missing` は入ってしまった違反の側を指しているに
  過ぎない。同じ形（README や規約が「〜が守る」と書いているのに、その仕組みが有効に
  なっているかを誰も確かめていない）が再発したら、語彙の候補になる
