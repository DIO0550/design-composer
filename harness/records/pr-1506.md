## ゴールと結果

Issue を起こす前に、実装中に判断が割れそうな分岐を調べ、人と決めた結果と却下理由を本文に残せるようにした。Epic では独立してマージできる子への分け方まで扱う。人と対話できない起動は既存手順のまま。実例 [#1505](https://github.com/DIO0550/design-composer/issues/1505) は、検索欄のフォーカス枠について人と選んだ仕様を新規起票し、共通 4 節・機能追加の必須欄・決めた判断・ラベルを確認した。検索欄そのものは変更していない。

GitHub のレビュー本文・インライン・PR 会話を確認し、修正指摘は人・bot ともに 0 件。セッションでは名前についてオーナーの指摘 1 件があり、内部レビューの 6 件と区別して記録した。最終 head `f143357` の PR CI は [6 ワークフロー成功](https://github.com/DIO0550/design-composer/pull/1506/checks)。Storybook の画像差分はなく、ローカルの厳格 pre-push 39 検査・Vitest 6,136 件も通過した。Claude Code の自動選択とフックの実発火は未実測。

## 指摘

### 1. スキル名が起票の準備に寄りすぎていた

- 分類: `naming`
- 出どころ: `レビュー（人）`
- 内容: セッション中にオーナーから、仕様を人と詰めるなら `prepare-issue` より `grill` ではないかとの指摘。名前は `grill` を採用し、今回の起動範囲は Issue と Epic の起票前に限定した。
- 既存ルール: rules/naming.md「名前と実体を一致させる」

### 2. 通常の起票だけに導線があり Epic が漏れる計画だった

- 分類: `plan`
- 出どころ: `レビュー（plan-reviewer）`
- 形の名前: この変更が新しく開く経路・生む非対称・生みうる不正な状態を、計画のスコープ・完了条件が数え切れているか
- 内容: 採用。手順 4(a) にだけ導線を置く案では、Epic の 4(c) から辿れない。対話中の共通入口へ移し、通常の起票・Epic・無人を区別した。
- 既存ルール: `.claude/skills/implementation-flow/SKILL.md` フェーズ 3〜4

### 3. 独立した質問が上限を超えたときの確認が抜けていた

- 分類: `test`
- 出どころ: `レビュー（plan-reviewer）`
- 形の名前: 対になる入出力・状態（true / false・前後・幅軸 / 高さ軸・出る / 出ない・経路 A / 経路 B 等）の両方が、計画のテストケース一覧に挙がっているか
- 内容: 採用。4 問以内は 1 回、独立した 5 問は 4＋1、回答に依存する問いは先行回答の後に組み直すという 3 通りを手順と確認項目に分けた。
- 既存ルール: `.claude/agents/plan-reviewer.md` のテスト観点

### 4. 呼び出す側と呼ばれる側が同じ Issue を起票しうる書き方だった

- 分類: `plan`
- 出どころ: `レビュー（solution-reviewer）`
- 形の名前: 権限・セキュリティ・状態の問題が、構造そのものから来ていないか。
- 内容: 採用。直接の依頼は `grill` が起票し、実装フローから呼ばれたときは本文と種類を返すだけにした。二重起票の実発生ではなく、手順の読み違いを指摘された。
- 既存ルール: `.claude/agents/solution-reviewer.md` の方式の観点

### 5. フォームの固定文言と種類の書式を重ねて書いていた

- 分類: `duplication`
- 出どころ: `レビュー（duplication-reviewer）`
- 形の名前: 同じ判断根拠・説明（Why・仕様説明・定義理由・列挙）を、コードではなく doc・comment・README・仕様書側で独立に複数箇所へ書いていないか
- 内容: 採用。共通 4 節の問いを新スキルに残し、既定の文言はフォーム、起票時の本文と種類の書式は既存手順への参照に寄せた。
- 既存ルール: rules/coding.md「同じ処理が2箇所に現れたら共通化する」

### 6. 「通常の Issue」が既存フローの対象外も含むように読めた

- 分類: `naming`
- 出どころ: `レビュー（naming-reviewer）`
- 形の名前: 対象は合っていても、規約の別の判断軸から外れていないか
- 内容: 採用。対象を「実装フローに通す Issue または Epic」と明記し、棚卸しなど Epic 以外の対象外が混ざらないようにした。
- 既存ルール: rules/naming.md「名前と実体を一致させる」

### 7. 実装できることと UI の採用判断を切り分けていなかった

- 分類: `ui`
- 出どころ: `レビュー（ui-reviewer）`
- 形の名前: `ui-fidelity`
- 内容: 採用。試作は実現可能性の確認とし、UI 案にない見せ方や案から変える方針が未承認なら、調査結果を添えて人に尋ねると明記した。
- 既存ルール: rules/ui-verification.md「プロトタイプと違う形にする必要が出たら、実装前に理由を添えて確認する」 / harness/case-law/ui.md「UI 案が対象を描いていない」
