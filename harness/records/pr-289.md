## ゴールと結果

ゴールは「他 feature の内部への import・循環参照・モジュール内部への deep import が CI で無条件に落ちる」（#257 のゴール 1・2・6）。達成した。#284 で `.oxlintrc.json` へ入れた層・方向の対（ゴール 3・4・5）の続きで、**oxlint では書けない残り**を `.claude/hooks/lib/import-rule-violations.py` が受け持つ形にした。

置いたのは判定スクリプト 1 本と層 3 のフック 1 本で、CI（`frontend.yml` の `rules-check`）・git hooks（`harness/githooks/pre-push`）・Claude Code hooks の 3 層すべてへ配線した。導入時点の既存違反 8 件（feature をまたぐ fixture の直接 import）は、feature ごとのテスト用公開口（`features/canvas/__tests__/index.ts` / `features/assets/__stories__/index.ts`）を置いて 0 件にしてから入れた。

human レビューは 0 件（reviews 0）。CI は 6 チェックすべて 1 回目で success、視覚差分も 0 changed / 105 passed。**指摘はすべてサブエージェント（`plan-reviewer` 10 件 / `implementation-reviewer` 13 件）から出た。**

**この回の中心は 3 つ。** 1 つは**計画の前提が実例に当たっていなかった**こと（指摘 1）。「fixture を層直下へ移せば違反 0 になる」という計画の骨格が、実際にコピーへ移動を適用して走査すると成立せず、案ごと差し替えになった。数えていたのは「移動前の違反 8 件」だけで「移動後の違反」を数えていない。

2 つめは**検査そのものが守られていなかった**こと（指摘 6・7）。`implementation-reviewer` が 18 のミューテーションを入れて実測したところ、終了コードを `return 0` に固定しても、`.tsx` を対象から落としても、当初の動作確認コマンドは 7/7 通った。**層 1（CI の `run:`）と層 2（`pre-push` の `set -e`）は終了コードだけが配線**なので、ゴールの本体が確認手段から漏れていた。

3 つめは**検査自身に穴が開いていた**こと（指摘 8・9）。feature へ入る辺を「呼び出し元が feature か」で判定していたため、`app/` から feature の内部モジュールへ直行する経路がどの層からも見えていなかった（`app → features` は依存方向としては許されるので oxlint も止めない）。行き先で判定する形へ変えて塞いだ。

テストは 350 ファイル / 2366 テスト（追加・変更なし。`src/` の変更は import 先の付け替えと doc のみ）。

## 手戻り

**3 件。**

1. **計画の骨格を差し替えた**（指摘 1）。「fixture を層直下へ移す」→「feature のテスト用公開口を置く」。`plan-reviewer` が「却下案に無い選択肢」として挙げた案を採った。移動が無くなったことで、計画時に懸念していた「層直下 fixture が feature の内部知識を持つ」問題（`plan-reviewer` 指摘 3）と「同名ファイルが 2 つ並ぶ」問題（同 5）も前提ごと消えた
2. **`__tests__/` に `index.ts` を置いた副作用を実装中に踏んだ。** 公開口を足した瞬間、`__tests__/` が「モジュールフォルダ」に見えて**同じ feature の中からの直接 import 11 件**が違反として出た。`__tests__/` / `__stories__/` はモジュールとして数えない判定を足して解消
3. **README に最初に書いた `module-public-api` の動作確認コマンドが、違反を出さなかった。** `@/features/canvas/domains/canvas-view/index` は入れ子モジュールの index なので設計上は許可される側だった。`src/domains/node/internal-probe.ts` を一時的に置いて外から読む形に直し、実際に 1 件出ることを確認してから README へ載せた

## うまくいったこと

**`plan-reviewer` の「却下案に無い選択肢」の提示が、計画の破綻をそのまま解決に変えた。** 指摘 1 は前提を壊す指摘だったが、同じ指摘の中で A(iii)（テスト用の公開口）が 1 行で提示されていたため、方針の再検討で止まらずに済んだ。

**`implementation-reviewer` のミューテーション実測が、確認手段の欠落と検査の穴を同時に出した。** 18 のミューテーションのうち 6 件が素通りし、そのうち 2 件（終了コード・`.tsx`）は確認手段の欠落、2 件（`parts[2] in names`・`app/` 経路）は検査そのものの穴だった。**「検査を書いた」だけでは検査が効いているか分からない**という形で、自分では気づけていない。

**ゴール 2 を feature 単位でも見る判断が、実測で裏付けられた。** canvas ⇄ tokens を `index.ts` 経由で相互 import させたとき、`feature-cycle` は 1 件出たが `import-cycle` は 0 件だった。バレルが内部ファイルを再 export しない構成では feature の閉路がファイルの閉路にならない、を確認できている。
