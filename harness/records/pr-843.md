## 指摘

### 1. 既存テストでは「出力は変わらない」を守れなかった

- 分類: `test`
- 出どころ: `レビュー（plan-reviewer）`
- 内容: 既存の validate-missing-name / validate-identifier テストが文言まで見ていたのは 1 件（`child 1 of "screen"`）だけで、どのテストもエラー 1 件の入力だった。
  書き換え前に文言・並び順・入れ物名の引き継ぎを固定する特性テストを足し、今の実装で緑になることを確かめてから移す計画に直した。
- 既存ルール: rules/testing.md「API を作り替えるときは、既存テストの観点を先に数える」

### 2. 消す関数を doc が名指ししている箇所がファイル表に無かった

- 分類: `comment`
- 出どころ: `レビュー（plan-reviewer）`
- 内容: `collectPaintNameConflictErrors` / `collectColorTokenErrors` の doc が `collectTokenNameErrors` を参照していた。
  実装では、この関数を詰め替えだけの形で残したので、参照は正しいまま保てた。
- 既存ルール: `.claude/skills/implementation-flow/SKILL.md` フェーズ 3 手順 7

### 3. collectInvalidNames が既存の collectInvalidColorNames と語形で食い違っていた

- 分類: `naming`
- 出どころ: `レビュー（plan-reviewer）`
- 内容: 既存の `collectInvalidColorNames` は「値が不正な色の名前」を返す。新しいメソッドは「名前が不正なトークン」を `TokenRef[]` で返すのに、`*Names` という同じ語形だった。`collectInvalidNameRefs` に改名した。
  DocumentNames 側も「欠落を不正な名前に含める」語だったので、docs/03 の「バリデーション違反」に揃えて `NameViolation` / `collectNameViolations` にした。
- 既存ルール: rules/naming.md「名前と実体を一致させる」

### 4. 名前空間の範囲を 2 箇所で独立に決める計画だった

- 分類: `duplication`
- 出どころ: `レビュー（plan-reviewer）`
- 内容: `collectNames` と新しい走査が、同じ「部品キー → 内部ノード → artboard → 配下」の範囲を別々に書く計画だった。
  名前と位置の出現を 1 回だけ列挙する非公開の走査を置き、両方をそこから導く形にした。
- 既存ルール: rules/coding.md「同じ処理が2箇所に現れたら共通化する」

### 5. DocumentNames に置く理由を計画に書いていなかった

- 分類: `ownership`
- 出どころ: `レビュー（plan-reviewer）`
- 内容: 第 1 引数は `ComponentSet` なのに、DocumentNames に置く理由が無かった。
  名前空間の範囲と識別子の規則は DocumentNames の性質で、`ComponentSet` / `Artboard` は片方しか知らない、と反証して書き足した。
- 既存ルール: rules/architecture.md「ロジックの帰属先」
