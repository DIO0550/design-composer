## 指摘

### 1. 推奨した「utils に残す」がオーナーに却下された

- 分類: `ownership`
- 出どころ: `レビュー（人）`
- 内容: 実測(同じ形の語彙が utils に 4 つある、components・hooks から libs への import が 0 件)を根拠に A を推奨した。オーナーの判断は「UI や DOM の語彙が utils にあるのは違和感がある」で、却下された。
  libs に `canvas-dom` がすでにあること、components・hooks から libs への import を lint が禁じていないことは、この指示の後に調べて分かった。「libs はすべて差し替えられる I/O 境界」という最初の説明は誤りだった。
- 既存ルール: rules/architecture.md「配置の判断基準」

### 2. 3 つをもう 1 段のフォルダにまとめるよう指示された

- 分類: `dependency`
- 出どころ: `レビュー（人）`
- 内容: libs 直下に 4 モジュールを並べる計画に対して、オーナーから「もう 1 つフォルダを作った方がいい」と指示された。
  親の `index.ts` から re-export する形(前例 `src/domains/dcmp/token`)と、`index.ts` を持たない入れ物の形を示し、前者に決まった。
- 既存ルール: rules/architecture.md「モジュールの公開API」

### 3. ElementEx を libs へ移して改名する計画が、オーナーに却下された

- 分類: `ownership`
- 出どころ: `レビュー（人）`
- 内容: plan-reviewer の命名の指摘(libs は「フォルダ名 = PascalCase の export 名」、`Ex` は utils の語形)を受けて、`ElementEx` を `libs/dom-element` の `DomElement` にする計画に直していた。
  オーナーの判断は「元の型に対する処理の拡張なので `<型名>Ex` として utils でよい」だった。
- 既存ルール: rules/architecture.md「utils の形式」

### 4. libs の命名慣習(フォルダ名と export 名)から外れた計画だった

- 分類: `naming`

- 既存ルール: rules/naming.md「その名前が既に別の意味を持っていないか確認する」

### 5. 却下理由に事実と合わないものが 3 つあった

### 6. libs へ移す理由が、残す側の ElementEx にも当てはまっていた
