# PR #171 [ui] トークン参照の prop に解決後の数値を併記する

- マージ日: 2026-08-10
- 関連 Issue: #133（申し送り先 #166）
- 差分規模: 10 ファイル / +318 -30

## ゴールと結果

**プロパティパネルでトークン参照を選んだとき、トークン名の右に解決後の数値が併記され、
トークンの値を変えれば併記も追随する。** 達成した。

Issue が「実装前に決めること」としていた 2 点（解決値を出すのはどの prop か / dangling の
表示）は、どちらも UI 案（`docs/Design Composer.html` の `Default` 画面）のマークアップと
既存実装（色の見本の出し方）から決められた。**種別で線を引く規則を採ると、UI 案の 4 行
（`gap` / `radius` に数値あり、`shadow` / `background` に無し）をすべて説明できる**ことが
決め手になっている。

UI 案から離れる点が 1 つ出た。UI 案の `padding` は T / R / B / L のどれにも数値を添えて
いないが、種別で線を引く以上 `paddingX` / `paddingY` には出る。UI 案の padding が半幅
2×2 セルであるのに対し現状は `gap` と同じ全幅 1 行なので密度の事情が当てはまらない、と
判断して併記し、**4 分割にするときに併記を続けるかを #166 へ申し送った**。

人のレビュー指摘は 0 件、CI の失敗も 0 件（1 回の push で 4 チェックすべて成功、VRT も
差分 0 件）。以下はすべて計画検証・実装検証のサブエージェントからの指摘。

## 規約への反映

### 1. `comment` が 5 回目 → 「コメントが主張している事実を確かめる」を実装検証の観点へ広げる

指摘 1（却下理由が事実と違う）と指摘 9（`shrink-0` のコメントが守る対象を取り違え、しかも
実質 no-op）は、どちらも「**書いた理由が本当かを確かめていない**」型。
`implementation-review.md` には既に「コメントが**どのテストが守っているか**を名指ししていたら
壊して確かめる」があるが、今回の 2 件はどちらも**テストの名指しではない**（class が何かを
防ぐ、という主張と、他の型についての主張）ので、その節に引っかからなかった。

**採らなかった置き場所と理由:**

- **1. フックを足す** — 「コメントの主張が事実か」は機械判定できない。文字列で
  「防ぐ」「できない」を拾っても、正しい主張と誤った主張を区別できず偽陽性しか出ない
  （`.claude/hooks/README.md`「例外(エスケープハッチ)」の経緯どおり、誤検知は
  フック全体の信用を落とす）
- **2. 新しいスキルを作る** — 段取りではなく確かめ方なので、既存の検証フェーズの観点に載る
- **4 / 5. `rules/` に書く** — `rules/coding.md`「コメントは実装と一致させる」は既にあり、
  今回不足していたのは判断基準ではなく**確かめる手順**。読み手の記憶に頼る場所へ置いても
  同じことが起きる

**採った置き場所（3）:** `implementation-review.md`「テストが守っているかの観点」の
「コメントが名指ししていたら壊して確かめる」の直後に、主張の形ごとの確かめ方を表で足す
（class の主張は**外した状態を作って Storybook で見る**、型についての主張は
**できると書いてあるコードを探す**）。今回の 2 件を例として残す。

### 2. `test-behavior` が 34 回目 → `queryBy*` が null になる理由を `rules/testing.md` に足す

指摘 8 の形（`queryByRole(..., { name, description })` が `null` を返す理由が
「説明が無い」と「欄そのものが無い」の 2 通りある）は、`rules/testing.md`
「『出さない』を確かめるときは、入力から自明にならない側を見る」の趣旨には含まれるが、
**絞り込みの条件を重ねた `queryBy*` という具体形が書かれていない**。既存の例が
「行が無いのを数える → 枠そのものを見る」という**要素の有無**の話なので、
「要素はあるが属性が無い」を確かめたいときに照らす先が無かった。

**採らなかった置き場所と理由:**

- **1. フックを足す** — 「`queryBy*` + 絞り込み条件 + `toBeNull`」は文字列で拾えるが、
  **対象そのものが無いことを確かめるのが正しい場合も同じ形**になる（未選択の画面に
  欄が出ないことを見る、など）。区別できないので偽陽性が出る
- **2 / 3. スキル** — 段取りではなく assert の書き方の判断基準なので、`rules/` が置き場所
- **5. 表現を直す** — 既存の一文は誤っていないので、直すのではなく具体形を足す

**採った置き場所（4）:** `rules/testing.md`「assert は『落ちうるか』…」の
「『出さない』を確かめるとき」の直後へ、NG / OK の対比を 1 組足す。

### 3. その他の分類は記録のみ

`plan`（35）/ `duplication`（19）/ `ui-fidelity`（8）はいずれも 2 回以上だが、
**今回の指摘はすべて既存のルール・観点に書かれており、その観点を持つ検証
（計画検証・実装検証のサブエージェント）が全件を捕まえている**。ルールの抜けではないので
規約は足さない。指摘 7（隣にある同型のテスト群と観点を突き合わせる）は既存ルールに
対応が無いが 1 回目なので、記録だけ残す。

## 手戻り

計画から外れた箇所が 1 つ。計画検証の S7（`inputOf` の `switch` を別関数へ切り出す）は
**意図だけを採り、手段を変えた**。切り出すと `names` は明示値から、解決値は「効いている値」
から作るため引数が 4 つになり、narrowing を運ぶためだけの型を作ることになる。代わりに
`isEnum` → `isLiteral` → 残り（= トークン参照）の順に並べ替え、`switch` を関数の末尾に
置いた。これで `case` の抜けが TS2366 としてその関数の中に出る（実際に `case "typography"`
を消して確認した）。この判断は Issue #133 に書いてから実装へ入っている。

## うまくいったこと

- **UI 案のマークアップを展開して、4 つの prop がそれぞれ何を出しているかを表にしてから
  規則を決めた。** 「数値を出す / 出さない」の線を prop 単位ではなく種別で引けたのは、
  4 行を並べて初めて見えている。スクリーンショットでは取れなかった
- **ミューテーションを 7 種入れて、中心の判断がすべて守られていることを実測した。**
  そのうち「`shadows` を `numericToken` 扱いにする（出さない側でも出す）」は、雛形の
  `spacing.sm` と `shadows.sm` が同名であることを利用して落ちる形にしてある。
  実装検証の指摘 8 を直したあと、同じミューテーションで落ちることを再確認できた
- **型で網羅を強制する形が実際に効いた。** パネル側に `case` を足す前に typecheck が
  TS2366 で落ち、実装の順番がそのまま抜けの検出になった
