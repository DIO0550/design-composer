# PR #320 👷 [CI]: タグ push のリリース資材を spec-viewer に揃える（.dmg 追加 + アプリ名の修正）

- マージ日: 2026-08-26
- 関連 Issue: 無し（チャットからの直接依頼。「spec-viewer のタグ作成でモジュール作成する Actions をパクって design-composer に反映して欲しい」）
- 差分規模: 2 ファイル / +15 -6

## ゴールと結果

ゴールは「spec-viewer の `release-macos.yml`（タグ push → リリース資材ビルド）を design-composer にも反映する」。達成した。

**着手して最初に分かったのは、design-composer には既に同系の `release-desktop.yml` があったこと。** タグ push で macOS `.app.zip` と Windows `.exe.zip` を作る形が揃っており、spec-viewer との実質的な差は 2 点だけだった。

| | spec-viewer | design-composer（変更前） |
|---|---|---|
| macOS の資材 | `.app.zip` + `.dmg` | `.app.zip` のみ |
| productName | `Spec Viewer` | `tauri-devcontainer-template` |

そこで macOS ジョブを `--bundles app` → `--bundles app,dmg` にし、`.dmg` の存在確認（fail closed）と Release への添付を足した。あわせて template 由来のまま残っていた `productName` / `identifier` / ウィンドウタイトルを `Design Composer` へ直した（リリース資材のファイル名は `productName` から作られるので、直さないと `tauri-devcontainer-template-...` という名前で配布される）。

human レビューは 0 件。CI は 1 回の push で 6 チェックすべて success（`lint / typecheck / test` / `doc コメント・テスト規約・import 規約` / `lint 抑制コメント` / `preview` / `post ci report comment` / `visual-regression` は差分 0・passed 138）。**サブエージェントによる検証は 0 件**（理由は指摘 3）。

なお、参照元の spec-viewer 側のワークフローは [v0.1.11](https://github.com/DIO0550/spec-viewer/releases/tag/v0.1.11) まで実運用されているが、**design-composer 側の `release-desktop.yml` はタグが 1 つも無く一度も実行されていない**。今回の変更もタグを打つまで実行されないので、正しさは机上の検算でしか確かめていない（→「うまくいったこと」）。

## 指摘

### 1. コミットメッセージを取り違えた（heredoc を 1 行に 2 つ並べた）

- 分類: `なし`
- 出どころ: 自己修正
- 内容: `git commit -F - <<'MSG' && git add ... && git commit -F - <<'MSG2'` を 1 行で書いた。bash は 1 行に複数の heredoc を書けるので、2 つの本文は**現れた順**に食われる。結果として 2 つ目のコミット（ワークフローの変更）に 1 つ目のメッセージ（アプリ名の修正）が入った。`git log` で気づき `--amend` で直したが、直せたのは push 前だったからで、そのまま push していれば履歴に残っていた
- 既存ルール: なし（規約はコミットの分け方・メッセージの体裁を定めるが、複数コミットをまとめて作るときのシェルの落とし穴には触れていない）
- 次にどう防ぐか: 今回は記録のみ。コミットを分けるときは 1 コマンド 1 コミットにして、作った直後に `git log --format=%s -n <本数>` で対応を見る（今回もそれで気づいた）

### 2. PR 本文に書いた山括弧が投稿時に除去され、意味の通らない表記になった

### 3. `implementation-flow` を通しておらず、`plan-reviewer` / `implementation-reviewer` の検証を受けていない

## うまくいったこと

- **「パクる」前に、反映先に既に何があるかを確認した。** design-composer 側に同系のワークフローが既にあり、しかも Windows ビルドを持っている（spec-viewer には無い）ことが分かったので、丸ごと置き換えて既存機能を削る事故を避けられた。差が `.dmg` と `productName` の 2 点だけだと確かめてから触っている
- **依頼の解釈が一意に決まらない点を、実装前に確認した**（`AGENTS.md`「設計判断の確認」）。Windows ジョブの扱いと `productName` の修正はどちらも「読み方が変われば成果物が変わる」分岐で、勝手に決めていれば作り直しになっていた
- **実行できないワークフローを、机上ではなく実測で検算した。** 偽のビルド出力（`Design Composer.app` / `Design Composer_0.1.0_aarch64.dmg`）を置いて「Prepare release assets」の `run` をそのまま走らせ、`release-assets/` に 2 件揃うことと、`.dmg` が無いときに exit 1 になることを確かめた
- **`productName` に空白が入る影響を、頭ではなく引数の展開で数えた。** `gh release upload ... release-assets/*` はグロブ展開の結果が単語分割されないので引数は 2 個のままになる。これを実際に展開して確認し、さらに spec-viewer が `Spec Viewer`（空白入り）で実運用できている事実と突き合わせた
- **参照実装の「結果」を見てから寄せた。** spec-viewer のワークフローの YAML だけでなく、v0.1.11 の Release に実際に `.app.zip` と `.dmg` の両方が付いていることを確認している
- **やらなかったことを PR 本文に明記した。** `src-tauri/Cargo.toml`（crate 名 `app` / `authors = ["you"]`）は `Cargo.lock` の再生成が要り検証できないので触らず、Windows ジョブが持つ `app.exe` フォールバックで壊れないことと合わせて書いた。`package.json` の name と README の見出しが template のまま残っていることも残件として書いた
