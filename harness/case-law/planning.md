# 判例: 計画

規範は [`.claude/skills/implementation-flow/SKILL.md`](../../.claude/skills/implementation-flow/SKILL.md)
フェーズ 3 と [`.claude/agents/plan-reviewer.md`](../../.claude/agents/plan-reviewer.md)。
ここはその実例。

`plan` は通算 144 件でいちばん多い分類。だから層 3（既存スキルの手順・検証エージェントの観点）まで上げてある。

## `plan-scope-verification` — 件数・接続先・検証コマンドの範囲を実例に当てずに計画へ書いた

一括置換・grep 収集など**機械的な手順を伴う計画**で、立てた条件・件数・基数・判定基準を
対象になる実例へ実際に当てて検算していない形。pr-227 で `plan` から分割し、pr-286 で
さらに `plan-file-omission` / `plan-goal-verification` へ分割し(移動・変更対象のファイル
表への計上漏れと、ゴール達成の確認手段の欠如はそれぞれ別項を見る)、pr-352 で
`plan-scope-count-verification`(件数・列挙の数え直し) / `plan-scope-premise-verification`
(接続先・前提・検証手段の成立確認)へさらに分割した(下 2 項を見る)。

| 起きたこと | 結果 |
|---|---|
| 直和へ足す枝が、全メンバ共通のフィールドに依存する呼び出し側を数えていなかった | 実装中に TS2339 |
| SCREAMING_SNAKE → PascalCase の一括置換で、`const` 宣言以外の形・別言語のファイルが指すコメント・置換の対象ルート・書き換えが要る既存テストの件数のどれも実例に当てていなかった | **5 件連続で実装中に発見** |

## `plan-scope-count-verification` — 件数・列挙を実例に当てて数え直していない

計画に書いた件数・基数・列挙(モジュール表へ併記する実体の列挙を含む)を、対象になる実例へ
**項目ごとに突き合わせて**数え直していない形。総数だけを合わせて内訳を数え違えたり、
見積もりの計算そのものを誤る形も含む。

| 起きたこと | 結果 |
|---|---|
| 「73 ファイル / 6,881 行」と見積もったが実測は「75 ファイル / 7,039 行」で、移動対象に挙げたテストヘルパー 2 本を行数集計に入れていなかった | レビューで指摘、実装前に訂正 |
| 分割後の行数目安の合計(976 行)が分割前(1,017 行)より少なかった。分割は import/export 行を増やすので合計は必ず増える | 実測で `prop-field` 約 275 行・`instance-body` 約 172 行と、目安の 2 つが超過していた |
| 「実装 1・テスト 25」と数えたが実際は「実装 2・テスト 24」で、総数は合っていたが内訳が違った | コメント内の言及 1 件を実装側へ畳んでいたことに気づかず提出していた |
| モジュール表の行(「ノード・部品・トークンの型」)に併記する実体を、責務の文が名指ししている処理と 1 つずつ数え合わせていなかった | 部品(`component` / `component-binding`)とトークン(`token`)が実体から漏れていた |

**「だいたい合っている」で止めず、内訳・総数・見積もりの計算過程を項目ごとに実例へ当て直す。**

## `plan-scope-premise-verification` — 接続先・前提・検証手段が実例で成立するかを確かめていない

想定した接続先(既存ヘルパー・retarget 先の fixture 等)・「A なら B」という前提・検証手段が、
実例で本当に成立する/機能するかを、読むだけで済ませて実際に動かして確かめていない形。
**検証コマンド自体が意図した範囲を覆っているか**(ディレクトリの深さ・拡張子の指定漏れ、
`git mv` 後は `diff` に出ない、表記ゆれで grep が対象を拾えない、を含む)も同じ観点で見る。

| 起きたこと | 結果 |
|---|---|
| 既存テストの retarget 先を、現在の fixture に実際に当てずに「成立する」と書いた | fixture が対応しておらず計画が成立しなかった |
| 依存方向の確認 grep に `src/domains/*/index.ts` を使ったが、これは深さ 1 の `index.ts` しか見ない(深さ 2 が 11 個・`__tests__/` も対象外) | 結果は 0 件で偶然正しかったが、確認手段が確認したい範囲を覆っていなかった |
| `git diff -M --stat` で rename を確かめようとしたが、`git mv` は index に入るため worktree との比較では rename が見えない | `git diff --cached -M --stat` でなければ検算にならなかった |
| 「境界は lint が強制している」と、実際に `pnpm run lint` を走らせずに計画へ書いた | 実行すると warning 止まりで exit 0 だった(強制はされていなかった) |
| 「rename として出る = 内容が変わっていない」を前提にしたが、移動対象 198 のうち 82 ファイルは自身が import 文を書き換えるため同じコミットで内容も変わる | 検算の条件を「rename が検出されること」と「rename 以外の新規/削除が 0 であること」の 2 つに分ける必要があった |

**文章のまま計画に書かない。** `grep` / 実際のスクリプトを走らせ、想定した前提・接続先が
崩れていないかを実行結果で確かめる(0 件という結果は「対象が無い」と「見ていない」の
両方で起きる)。

## `plan-file-omission` — 移動・変更の対象がファイル表から漏れる

コードの `import` だけを grep したファイル表は、次を見落とす。

| 見落とした対象 | 具体例 |
|---|---|
| props を変える対象のストーリー・テストの入口 | `EditorState` を直に組む 4 本のストーリーと、移動する 33 テストすべての入口だった `__tests__/setup.tsx` |
| 更新が要る `docs/` | スキーマを変える計画で `docs/03-schema.md` の更新が抜けていた |
| 必ず触ることになる private 型 | 公開 API の変更に伴って書き換えが要る非公開の型が計画に出てこなかった |
| 移動で使わなくなるテストヘルパー | `features/editor/__tests__/frozen-state.ts` を移動後も `artboard-canvas.frozen.test.tsx` が import しており、却下したはずの deep import 形が残る経路になっていた |
| コメント内でだけ名指しされた移動対象 | `分類: plan-comment-reference` を参照(同じ「ファイル表が import しか見ていない」原因の別の現れ) |

## `plan-comment-reference` — コメント内でだけ名指しされた移動対象がファイル表に無い

コードの `import` だけを `grep` したファイル表は、doc / Why / Why not コメントの中でだけ
シンボルや対象ファイルを名指ししている箇所を見落とす。pr-261 / pr-269 で初出してから
pr-317 まで 10 本の記録で 12 件出た、`plan` 系でいちばん再発した形。

| 起きたこと | 見落としの種類 |
|---|---|
| 移動先の feature を名指しした Why not コメント(「あちらはドキュメントを持たない」等)が、移動でその主張ごと嘘になる | 昇格・移動先を名指し |
| `import` していない別ドメインを Why コメントで名指ししていた(コード上の依存が無いので参照 grep に掛からない) | コード依存の無い名指し |
| JSX 内の Why コメント 2 文が、器の分割で両方とも嘘になる | doc 以外(JSX 内)のコメント |
| 「#43 待ち」のように Issue 番号を根拠にした doc が 6 ファイルに散らばっていた | 同じ理由を複数ファイルが共有 |
| ファイル表に行はあったが「置換する」としか書いておらず、同じファイルの別の行にある Why not が嘘になることが計画に無かった(pr-301#3) | 行はあるが対象の記述まで書いていない |

**「ファイル名がファイル表にあるか」だけでは足りない。** pr-301#3 のように、ファイルは
挙がっていても**そのファイルの何行目の何を直すか**が書かれていないと、同じファイル内の
別のコメントが見落とされる。

## `plan-goal-verification` — ゴールを確かめる手段が計画に無い

「`feature-a → feature-b` の辺を作らない」のような検証可能なゴールを立てても、
`.oxlintrc.json` の `curly` / `max-depth` しか対象にしていない override では、
辺ができても typecheck も lint もテストも全部緑になる。

pr-277#4 → pr-282#7 → pr-286#12(`分類: plan` のまま)と、feature を切り出すたびに同じ形が
3 回出た。**「今回は記録のみ」で完了条件に `rg` / `grep` を 1 行足すだけの場当たり対応を
繰り返しており、依存境界を機械的に強制する lint(全 feature を対象にした import 制限)は
まだ無い。** そちらは `harness/records/pr-286.md` が「独立してマージできるので別 Issue にする」
と書いた通り、rules や観点ではなくアプリ側の lint 設定を足す話なので、このリポジトリの
実装 Issue 側の課題として残る(このハーネス側の観点強化は「計画の時点で確認コマンドを
書かせる」までが担当範囲)。

## `plan` — 呼び出し側を数えずに書いた

| 起きたこと |
|---|
| 消す/変える公開 API の呼び出し側を grep で数えず、実装中に既存の利用箇所を発見（2 回） |
| 流用する既存ヘルパー（`denyingIpc()` / `breakFileExternally` 等）が、確かめたい経路へ実際に到達できるかを読まずに計画へ書いた（2 回） |

**アクション・状態の直和へ枝を足す場合も呼び出し側として数える。** 枝を足しても既存テストは
落ちず typecheck も通るので、数え漏らしても誰も教えてくれない（`use-editor-reducer` は
アクションごとに「送ると変わる」と「送っても変わらない」を固定しているが、`detach_instance`
だけが漏れてレビューまで残った）。

## `plan-open-decision-unverified` — 「未決の判断: 無し」が成立していなかった

計画の「未決の判断」欄を「無し」で締めたのに、実装中に手が止まる判断が残っていた形。
pr-317 以降で 11 件（pr-332#9・pr-435#11・pr-442#9・pr-455#15・pr-459#15・pr-476#7・
pr-495#8・pr-500#2・pr-512#5・pr-525#9・pr-539#5）。**11 件とも `plan-reviewer` が捕まえて
いる**（すり抜け 0）ので、崩れているのは検証ではなく計画を書く側の段取り。

| 残っていた判断の例 |
|---|
| 0 件のときに何を出すか / 同名をどう見分けるか / どの順に並べるか（pr-400#11・pr-500#2） |
| 語の意味（`DropParent` は何を指すか）・モジュールを分けるか・スコープ内か（pr-459#15） |
| `docs/` へ何を書くか（揃え先の範囲・閾値の単位・同距離の決め方）（pr-442#9） |
| 既存の書き方を保つか括り出すか（`Result.isOk(...)` の 6 連）（pr-512#5） |

**「未決の判断: 無し」と宣言していない 12 件も同じ根本形**（pr-400#11・pr-400#12・pr-432#11・
pr-442#11・pr-455#5・pr-455#10・pr-467#30・pr-482#6・pr-497#13・pr-533#7・pr-539#2・pr-539#3）。
このうち pr-400#12・pr-455#10・pr-539#2 は「手順・方針を計画に書いていない」形で直し方が違う
ため語彙を分けていない。**旧タグ `plan` が次に飽和するとしたら、この 12 件と同じ形がいちばん早い。**

## `plan-decision-trace-omission` — 下した判断が計画にも Issue にも残らない

| 起きたこと |
|---|
| スコープ外と書いた項目の後続 Issue を実際には作っておらず、読む人から「やり残し」と区別が付かなかった（pr-442#28。オーナーの指摘まで届いた） |
| 「独立してマージできるので分ける」と却下案に書いたが、後続 Issue を立てるとは書いていなかった（pr-507#4） |
| 別 Issue へ回すと書いたのに番号が無く、立てる前に書いて採番がずれかけた（pr-525#11） |
| Issue を「分けない」と決めた理由を計画に書いていなかった（pr-539#23） |
| 既定値を Box と揃えるという**採用**判断が、却下案にも未決にも現れていなかった（pr-516#12） |

## `plan-derived-scope-omission` — 変更が新しく開く経路・生む非対称を数えていない

ゴール文が名指ししていないだけで、計画どおり実装すると通れるようになる経路がある。

| 起きたこと |
|---|
| `free` の Box を座標経路の候補にすると、別の親から絶対配置の子を運び込む経路も同時に開く（pr-459#12） |
| 検証を広げると「`Used by` 0 件と表示されたトークンを消すとエラーが出る」状態が利用者から見えるようになる（pr-339#8） |
| Box を外すと `widthMode: fill` の子が `free` の親の直下へ来てドキュメントが不正になる（pr-526#16） |
| `free` の器に `placement: flow` の子を置けることを仕様として決めていなかった（pr-438#3。オーナーの指摘まで届いた） |
| ゴール文が「判別子を直接読む場所」なので構築側リテラルは対象外だが、それを計画に書いていなかった（pr-512#7） |
| `対策済` を足すと別の分類が 2c / 2a の分岐に入ることを、スコープ外と明示していなかった（pr-533#12） |

**崩れるのが既存の性質なら `plan-implicit-condition`、増えるのが到達できる状態・経路なら
こちら。** ゴール文が名指ししている経路の通しテストが無いだけなら `plan-path-coverage`。

## `plan-integration-coverage` — 配線を通すテストが一覧に無い

ドメインが既にあって**配線だけを足す回**で抜ける。単体（ドメイン / reducer / 単体 UI）だけを
揃えると、**配線が切れていても全テストが緑になる**。

通しは `opened-document-editor/__tests__/` が担当で、そこにしか無い前提（選択・行き先の
切り替え・親が持つ `key`）は単体では通らない。

**一度この観点を足したのに、同じ形（`useNodeActions` → `PropertyPanel` の配線切れ）が再発した。**
計画のテスト一覧に単体しか無いなら、通しが要らないと確定したのか挙げ忘れなのかを 1 行で書かせる。

### 仕様に根拠が無いテストケース

「同じ名前 2 つは単一選択になる」を計画に挙げたが、名前は単一名前空間で一意なためどの経路からも
重複は来ず、根拠が無いまま計画に残っていた。

### 既存の不変条件を崩す

doc / Why コメントが「常に◯◯である」と書いている前提は、それを崩す変更（単一選択 → 複数選択、
単一 artboard → 複数 artboard 等）が来ると同時に嘘になる。「選択は常に今見ている artboard の
中にある」という Why コメントが複数選択の追加で崩れることを、計画の時点で拾えていなかった。

## 既存の公開 API を探さずに書いた

「部品を引く → binding を引く → prop 定義まで辿る」の 3 段を自前に書いたが、
`ComponentSet.publicPropTarget` が同じことをしていた。

**既存の呼び出し側が別の API を使っていたのは、そちらは別の情報も要るから**であって、
同じ答えを得る近道が無かったからではない。**触るドメインの `index.ts` は実際に開いて読む**
（名前も引数の形も違うので grep では見つからない）。

## API を作り替えるときの観点の引き継ぎ

型名やメソッド名を変えると既存のテストファイルが丸ごと動かなくなるが、そこにある観点
（dangling 参照・循環・定義順・空など）は仕様であって、書き換えの都合で消えてよいものではない。

**新しく思いついたケースだけを並べた一覧は、たいてい元より薄い。** ファイルをリネームして
観点を引き継いでから、新しい観点を足す。
