# 判例: UI

規範は [`rules/ui-verification.md`](../../rules/ui-verification.md)。ここはその実例。

## `ui-fidelity` — UI 案を開いたのに読めていない

**見るのはスクリーンショットではなくマークアップ。** 画像からは色・余白・字面の実測値が
取れない。実際に取り違えたもの:

- アイコンが素の div であることを取り違えた
- 帯の色・画面数・gap を取り違えた

マークアップは `<script type="__bundler/template">` の **JSON 文字列**に入っているので、
展開してから読む（手順は `rules/ui-verification.md`）。展開後は 10 万字ほどになるので、
`<!-- RIGHT PANEL -->` のような区切りコメントを目印にする。

### 数えるときは `grep -i`

UI 案は小文字で書いて CSS の `text-transform:uppercase` で大文字にしている箇所がある。
`grep "STALE"` は 0 を返すが `grep -i "stale"` は 1 を返す。

**この読み違いで、実在する `STALE · LAST VALID` バッジを「今の案には無い」と誤って
訂正しかけた（#112）。** 「0 回だから UI 案に無い」と結論する前に、必ず `-i` で数え直す。

## `ui-fidelity` — UI 案が対象を描いていない

`rules/ui-verification.md`「プロトタイプと違う形にする必要が出たら、実装前に理由を添えて
確認する」を実行しても、**対象がそもそも UI 案のどの画面にも無い**ケースでは効かない。
根拠（実測値・グレップ件数）を揃えて筋の通る答えを自分で決めても、UI 案どおりにしても
UI 案どおりにしなくても、オーナーが実際に見る／操作するまで誰も気づかなかった。

| 起きたこと | 実際は |
|---|---|
| ハンドルを UI 案どおり四隅 4 個にした（pr-394） | オーナーが望んだのは各辺中間を足した 8 箇所。UI 案に忠実だったこと自体が不正解だった |
| 開くボタンの色を、UI 案での使われ方（選択・ハンドル・挿入位置の指示にしか出ない）から外して黒にした（pr-400） | オーナーは単に「青でいい」。UI 案の色の使われ方から筋の通る理由を導いても、対象（開始画面のボタン配色）自体が UI 案に無いので根拠にならなかった |
| 「ゴースト」語彙が UI 案・`docs/06-ui.md` に 0 回なので出さなかった（pr-400） | オーナーは持っていてほしかった。UI 案に語彙が無いことは「作らない」の理由にならない |
| 左ペインの `↑` / `↓` に揃えてドラッグ移動を却下していた（pr-317） | `docs/06-ui.md` が並べ替えを「ドラッグまたはツリービュー」と明記しており、UI 案にも仕様にも根拠の無い既存実装（`↑` / `↓`）の方を疑うべきだった |

**対象が UI 案のどの画面にも無いと確かめたら、その時点で止めて確認する。** 実測値や
グレップ件数で組み立てた理由は「筋が通っている」ことの証明にしかならず、「UI 案が
求めている」ことの証明にはならない。

## `ui-fidelity-misread` — マークアップを見たうえで意味を取り違えた

`rules/ui-verification.md` を実行しても防げない形。**単一の画面・単一の状態だけを見て断定する**
のが原因。

| 起きたこと | 何を見落としたか |
|---|---|
| `◆` を「一時的な状態表示」と読んだ | 実際はドラッグ画面だけ背景色が違う**常在スロット**。差は `background` の **1 属性だけ**だった |
| 「帯が 3 つ」と書いた | 画面全体の帯の数なのか、ある帯の中の一部（倍率の並び）の数なのかで意味が変わる |
| `Used by` の `◆ primary-button.background` をインスタンスの行と読んだ | `primary-button` は `Assets` の部品定義側にしか居らず、`background` はその部品の公開 prop でもないので、インスタンスの行としては成立しなかった |

確かめ方: **主張の対象になっている要素を、UI 案の全画面・全状態で横に並べて属性を比較する。**
差が 1 属性しか無いことがある。

取り違えたまま進むと、結論（実装の方針）自体は変わらなくても、**次に読む人が誤った根拠を
裏付けとして参照する**ことになる。結論が変わらない指摘でも直す。

## Storybook / VRT

- 編集画面はブラウザでは開けない（開く導線が Tauri の IPC / ダイアログを使う）。編集画面の中を
  見るときは Storybook。**VRT が比較しているのも Storybook** なので、赤くなる差分と見ているものが一致する
- 操作を伴う確認は、画面全体を組み立てているストーリー（`OpenedDocumentEditor` など）で行う。
  単体のストーリーは props が固定なので状態変化を追えない
- **部品から位置・大きさを外すと、decorator が位置を持っていない単体ストーリーだけが変わる。**
  実画面は変わっていないのに VRT が赤くなる。happy-dom は Tailwind を解決しないので
  **テストでは絶対に落ちない**
- 新しいコンポーネントを足したのに story を足さないと、VRT の対象にも入らない

## `vrt-blind-spot` — VRT が緑でも、変えた UI が絵に写っていない

差分 0 は「見た目が変わっていない」ではなく「**比較した絵に写っている範囲では**変わっていない」
しか意味しない。この節が扱う写らない理由は 3 つ（閾値未満 / そのストーリーが無い / 器の中に
隠れている）で、実例は 4 件。どれも**変えた箇所については CI が何も言わない**。

| 何を見込んだか | 差分が出なかった理由 |
|---|---|
| `w-64` → 248px の 8px 縮小が 4 本で出る（pr-307） | **閾値未満。** Changed になったのは `token-list` の 2 本だけ（0.0022 / 0.0023）で、残り 2 本と `assets-panel` の `h-96` 除去は `--max-diff-ratio 0.002` を超えなかった。`token-list` だけ出たのは `p-3` を持たず中身が枠の縁まで届くため。**赤くはなったが、赤くなったのは変えた 4 本のうち 2 本**だった |
| 「視覚差分は `AbsoluteNode` で出る想定」と PR 本文に書いた（pr-402） | **その状態のストーリーが無い。** プロパティパネルに絶対配置のノードを選んだ状態を写すストーリーが無く、増えた 2 行が土俵に乗らなかった。部品は既にあり、足りないのは**状態** |
| `Opacity` の行が 1 つ増えるので赤くなる（pr-483） | **器の中に隠れている。** パネルのストーリーは高さの決まった器（`RightPaneShell` の `height="pane"` = `h-[32rem]`）の中で内側スクロールし（`PaneBody` の `min-h-0 flex-1 overflow-auto`、scrollHeight 829 / clientHeight 466）、増えた行が器の下にある。差分 0（152 passed）で通った |
| 新設した `document-open-failure`（pr-544） | **ストーリーが無い。** 同じ形は `Storybook / VRT` 節の「新しいコンポーネントを足したのに story を足さないと」と、[`process.md`](process.md) の `vrt-blind-spot`「視覚差分でしか守れない部品には、単体のストーリーを置く」の**両方に既に書かれていた**（PR #544 のマージ時点の main で確認） |

**「器の中に隠れている」は「撮影範囲の外」ではない。** `rules/ui-verification.md`「差分ではなく撮影で
落ちることがある」が言う撮影範囲は、文書が `1280x720` を超えて**撮影の検査が CI を赤にする**形。
器が中身をクリップする場合は文書が伸びないので、その検査は鳴らず、静かに 0 件で通る。

4 つめの理由（**story の id が変わるとベースラインが無く `new` 扱いになり `failed` に数えられない**）は
[`process.md`](process.md) の `vrt-blind-spot` の見出しにある。

### VRT の緑を、守られている証拠として読まない

pr-544 は、写らない形が 2 箇所の判例に既に書かれていたうえでの再発だった。**形を並べるだけでは
止まらない。** 増えた／変わった UI については、次の 3 点を確かめるまで「視覚差分で守られている」と
書かない。「VRT が赤くなるはず」を PR 本文・Issue・通知へ書く前も同じ。

1. **その UI を写すストーリーが在るか。** Storybook で実際に開く。新設した部品だけでなく、
   既存の部品の**新しい状態**も
2. **変わった箇所が、撮った絵そのものに見えているか。** 高さを決めた器（`RightPaneShell` の
   `height="pane"` など）を着たストーリーは、ビューポートを広げても隠れた部分が出てこない。
   `rules/ui-verification.md`「器の中身が撮影範囲に収まっているかは、絵を見て確かめるしかない」は
   ここに当たる
3. **レポートの Passed に、自分が変えた部品が居ないか。** 閾値未満の差分は `passed` に分類され、
   `Within threshold` のラベルで Passed の節に並ぶ（`.github/scripts/storybook-visual-regression.mjs`
   の `compare` と `CATEGORIES`）。数 px の移動・余白だけの変更はここへ落ちる

どれか 1 つでも「いいえ」なら、その変更は**視覚差分では守られていない**。ストーリーを足せるなら足し、
足さない（スコープ外にする）なら、守られていないことを PR 本文に書く。
