# 判例: UI

規範は [`rules/ui-verification.md`](../../rules/ui-verification.md)。ここはその実例。

## `ui-fidelity` — UI 案を開いたのに読めていない

**見るのはスクリーンショットではなくマークアップ。** 画像からは色・余白・字面の実測値が
取れない。実際に取り違えたもの:

- アイコンが素の div であることを取り違えた
- 帯の色・画面数・gap を取り違えた

マークアップは `<script type="__bundler/template">` の **JSON 文字列**に入っているので、
展開してから読む（手順は `rules/ui-verification.md`）。展開後は 10 万字ほどになるので、
`<!-- RIGHT PANEL -->` のような区切りコメントを目印にする。

### 数えるときは `grep -i`

UI 案は小文字で書いて CSS の `text-transform:uppercase` で大文字にしている箇所がある。
`grep "STALE"` は 0 を返すが `grep -i "stale"` は 1 を返す。

**この読み違いで、実在する `STALE · LAST VALID` バッジを「今の案には無い」と誤って
訂正しかけた（#112）。** 「0 回だから UI 案に無い」と結論する前に、必ず `-i` で数え直す。

## `ui-fidelity` — UI 案が対象を描いていない

`rules/ui-verification.md`「プロトタイプと違う形にする必要が出たら、実装前に理由を添えて
確認する」を実行しても、**対象がそもそも UI 案のどの画面にも無い**ケースでは効かない。
根拠（実測値・グレップ件数）を揃えて筋の通る答えを自分で決めても、UI 案どおりにしても
UI 案どおりにしなくても、オーナーが実際に見る／操作するまで誰も気づかなかった。

| 起きたこと | 実際は |
|---|---|
| ハンドルを UI 案どおり四隅 4 個にした（pr-394） | オーナーが望んだのは各辺中間を足した 8 箇所。UI 案に忠実だったこと自体が不正解だった |
| 開くボタンの色を、UI 案での使われ方（選択・ハンドル・挿入位置の指示にしか出ない）から外して黒にした（pr-400） | オーナーは単に「青でいい」。UI 案の色の使われ方から筋の通る理由を導いても、対象（開始画面のボタン配色）自体が UI 案に無いので根拠にならなかった |
| 「ゴースト」語彙が UI 案・`docs/06-ui.md` に 0 回なので出さなかった（pr-400） | オーナーは持っていてほしかった。UI 案に語彙が無いことは「作らない」の理由にならない |
| 左ペインの `↑` / `↓` に揃えてドラッグ移動を却下していた（pr-317） | `docs/06-ui.md` が並べ替えを「ドラッグまたはツリービュー」と明記しており、UI 案にも仕様にも根拠の無い既存実装（`↑` / `↓`）の方を疑うべきだった |

**対象が UI 案のどの画面にも無いと確かめたら、その時点で止めて確認する。** 実測値や
グレップ件数で組み立てた理由は「筋が通っている」ことの証明にしかならず、「UI 案が
求めている」ことの証明にはならない。

## `ui-fidelity-misread` — マークアップを見たうえで意味を取り違えた

`rules/ui-verification.md` を実行しても防げない形。**単一の画面・単一の状態だけを見て断定する**
のが原因。

| 起きたこと | 何を見落としたか |
|---|---|
| `◆` を「一時的な状態表示」と読んだ | 実際はドラッグ画面だけ背景色が違う**常在スロット**。差は `background` の **1 属性だけ**だった |
| 「帯が 3 つ」と書いた | 画面全体の帯の数なのか、ある帯の中の一部（倍率の並び）の数なのかで意味が変わる |
| `Used by` の `◆ primary-button.background` をインスタンスの行と読んだ | `primary-button` は `Assets` の部品定義側にしか居らず、`background` はその部品の公開 prop でもないので、インスタンスの行としては成立しなかった |

確かめ方: **主張の対象になっている要素を、UI 案の全画面・全状態で横に並べて属性を比較する。**
差が 1 属性しか無いことがある。

取り違えたまま進むと、結論（実装の方針）自体は変わらなくても、**次に読む人が誤った根拠を
裏付けとして参照する**ことになる。結論が変わらない指摘でも直す。

## Storybook / VRT

- 編集画面はブラウザでは開けない（開く導線が Tauri の IPC / ダイアログを使う）。編集画面の中を
  見るときは Storybook。**VRT が比較しているのも Storybook** なので、赤くなる差分と見ているものが一致する
- 操作を伴う確認は、画面全体を組み立てているストーリー（`OpenedDocumentEditor` など）で行う。
  単体のストーリーは props が固定なので状態変化を追えない
- **部品から位置・大きさを外すと、decorator が位置を持っていない単体ストーリーだけが変わる。**
  実画面は変わっていないのに VRT が赤くなる。happy-dom は Tailwind を解決しないので
  **テストでは絶対に落ちない**
- 新しいコンポーネントを足したのに story を足さないと、VRT の対象にも入らない

## `vrt-blind-spot` — VRT の green / 差分 0 は「新しい UI 表面が写っている」ことの証明にならない

`rules/ui-verification.md`「表示確認」を実行し、VRT が差分 0 / passed で通っても、それは
**「見た目が変わっていない」の証明ではない**。差分が出ない理由はいくつもあり、実際に起きた形:

| PR | 起きたこと | 差分が出なかった理由 |
|---|---|---|
| pr-307 | `w-64` → 248px に縮めた 4 本のうち、VRT が Changed にしたのは 2 本だけ | 縮小分が `--max-diff-ratio 0.002` 未満で passed 扱いになった。`p-3` を持たず中身が枠の縁まで届く 2 本だけ diffRatio が閾値を超えた |
| pr-402 | 絶対配置ノードを選んだときだけ増える 2 行 | その**状態**を写すストーリーが無く、ベースラインにも新版にも 2 行とも現れない（差分の土俵に乗らない） |
| pr-483 | Appearance に増えた `Opacity` の行 | パネルのストーリーが高さの決まった内側スクロール枠（`min-h-0 flex-1 overflow-auto`）を持ち、増えた行が撮影範囲より下（scrollHeight 829 / clientHeight 466）にあるため画面に映らない。**撮影自体は失敗せず、静かに 0 件で通る** |
| pr-544 | 開けなかったことを伝える帯（新設コンポーネント） | 新設したコンポーネントにストーリー自体が無く、VRT の対象にすら入らない（上の「新しいコンポーネントを足したのに…」と同じ形。この判例が既にあった状態で再発した） |

**共通するのは、VRT が「何かが変わった」ことしか検知せず、「見せたいものが実際に画面へ出たか」
は見ていないこと。** 新しい UI 表面（新しいコンポーネント・既存コンポーネントの新しい状態・
新しく増えた行）を足したら、VRT の結果を見る前に **その状態を実際に Storybook で開いて
スクリーンショットを撮り、増えた/変わった要素が撮影枠の中に見えていることを自分の目で確認する**
（`rules/ui-verification.md`「表示確認」の手順どおり）。VRT の diff 件数や passed / Changed の
表示は、その確認の代わりにならない。

- 新しいコンポーネントを足したら、まずストーリーを足す（pr-544）
- 既存コンポーネントに新しい**状態**（enum・条件分岐）を足したら、その状態を写すストーリーが
  無いか確かめる。無ければストーリーを足すか、「VRT の対象外」であることを PR に明記する
  （pr-402）
- 内側にスクロールする器（固定高さ + `overflow-auto`）を持つストーリーでは、増えた行がスクロール
  枠の外にあるかもしれない。**器の中身が撮影範囲に収まっているかは、絵を見て確かめるしかない**
  （下の「差分ではなく撮影で落ちることがある」と根は同じだが、あちらは撮影そのものが失敗して
  赤くなるのに対し、こちらは撮影が成功して**静かに 0 件で通る**点が違う）（pr-483）
- 閾値未満の縮小・移動は Changed にならないことがある。件数が 0 でも、実際に変えた箇所の
  差分画像（または実測値）を確認してから `visual-approved` を付ける・付けないを判断する
  （pr-307）

**新しいコンポーネント・新しい状態・撮影範囲の 3 通りとも、`.claude/hooks/` の検出器では
拾えない。** `src/components/` `features/*/components/` の `index.tsx` は約 2 割（60 件中 12 件）
がストーリーを持たずに存在しており（非表示の Provider、スタイル専用モジュール、親ストーリー
経由でしか使われない子部品など）、「変更した `index.tsx` に対応するストーリーが無ければ検出」を
機械的にブロックすると、これらの正しい形が毎回誤検出される。状態・撮影範囲の 2 つは見た目の
判断そのものなので、なおのこと機械化できない。
