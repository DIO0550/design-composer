# 判例

`rules/` から切り出した**実例**の置き場。規範と判例の分け方および常時ロードしない理由は `AGENTS.md`「規範と判例を分ける」を参照。

## 誰がいつ読むか

| 読む人 | いつ |
| --- | --- |
| `plan-reviewer` / 実装検証の観点別エージェント（`*-reviewer`） | 検証のたび（`rules/` と対で読む） |
| 実装するエージェント | **その分類で実際に迷ったとき・指摘を受けたとき**だけ |

## 誰が書くか

**判断を書くのは `harness-growth` だけ**（`.claude/skills/harness-growth/`）。ここでいう「判断」は、起きたこと・NG / OK の形・判定の分かれ目・機械化できるかの結論を指す。判例は介入先の 1 つ（フックにできないものの置き場）であるため `harness-record` は触らない（規範も変えないので、下の写し・参照の修正も発生しない）。

- 見出しは**分類**（`.claude/skills/harness-record/templates/record.md`「分類の語彙」）で引けるようにし、その下に **NG / OK の形と判定の分かれ目**を書く
- **過去の判断を書き換えない。** 判断が変わったら新しい判例を足し、古いほうに「この判断は `<PR>` で更新された」の 1 行を添える
- 規範の写し・規範への参照は「判断」ではないため、規範に合わせて直すことは書き換えに当たらない。規範を変えた回のスキル（`implementation-flow` / `harness-growth`）が直し、食い違いを見つけた回もその PR で直してよい（→「判例の外の文書を変えたとき」。綴りの前例は `.claude/hooks/README.md` の `named-path-violations.py` の項）
- 判断を書くときは規範の文を写さず、規範の節名で参照する（写しを増やさない）

## 判例の外の文書を変えたとき

判例ファイルと記録（`harness/case-law/` の各判例と `harness/records/`）以外の文書で、既存の文・節名・語の意味を変える／消す回は、判例に残る写し・参照を**同じ PR で**直す。規範の役を持つこの README 自身も対象に含める（#938 / #712 で規範を変えた際、判例が追いつかないままマージされ #952 まで食い違いが残った）。

1. **探す。** 変える前の文から 10 字ほどの句を取り、`grep -rn '<句>' harness/case-law/` で引く。判例は全角括弧で写し途中で折り返すため、括弧・`**`・行末をまたがない位置で切る。節名を変えるなら `grep -rn '「<古い名前>」' harness/case-law/`、語に新しい意味を与えた・狭めたならその語でも引く
2. **分ける。** 行ではなく句の単位で見て、次のように扱う。判断の文の中にある節名・規範の語は参照として直してよいが、判断の結論は変えない。判断の中身（結論）かどうか迷ったら判断として扱う
   - **写し**（規範の文をなぞるだけ）→ 消す。写し元が常時ロード（`AGENTS.md` / `rules/`）の外なら、写し元の節への参照 1 行に置き換える。新しい文へ写し直さない
   - **参照**（節名・規範の語）→ 新しい名前・語に合わせる
   - **判例が独自に付けた語が規範の新しい意味と衝突する場合** → 語だけを直し、判断は変えない（`.claude/hooks/README.md` の `named-path-violations.py` の項と同じ考え方）
   - **判断** → 書き換えない（「誰が書くか」）

規範から判例へ移した文（`harness-growth`「縮める」）は写しではなく、移した先が原本になる。

これをフックにしないのは、規範から判例へ移した文と意味を変えた文を字面では区別できないため。判例ができて以降に `rules/` を触ったマージ 29 本で検証したところ（変えた規範の文と判例の行の 20 字以上の一致で集計）、12 本が該当したが追随が必要だったのは 1 本だけだった。
