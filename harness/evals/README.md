# テスト配置・命名のハーネス比較

同じ規約と課題を配り、`rules/testing.md`「配置と命名」の説明だけを変えたときの回答を比べる。実験者が各週の候補と規約の基準コミットを選び、A に元の文章、B に候補の置換を適用する。

| 候補 | B の差分 | 検証する仮説 |
| --- | --- | --- |
| P-001 | ディレクトリ例6行を削除 | 周囲の文章で配置と命名を再現できるか |
| P-001-short | 同じ例を対象ドメイン名を明記した1行に置換 | ファイル名の手掛かりを残して5行減らせるか |

| 課題 | 条件 | 採点 |
| --- | --- | --- |
| grid-step | 単一モジュールの次のグリッド位置 | 配置・命名、グリッド上と間の入力、全期待値 |
| label-limit | 同名の隣接モジュールと旧テスト置き場がある | 対象機能への配置・命名、長さの両端とその外側、全期待値 |

`naming` は実験で先に定めた採点条件で、ファイル名の先頭に対象ドメイン名を求める。例えば `grid-step.normal.test.ts` は合格する。既存スキャン（`rules`）は命名形式を検査するため、`index.normal.test.ts` も通過する。

結果は、[6行を削った実験](reports/P-001-2026-11-24.md) と [1行に短縮した実験](reports/P-001-short-2026-11-24.md) でそれぞれ確認できる。

## 選んだエージェントで比較する

1回の比較に使うエージェントは実験者が選ぶ。A/B は同じエージェント・設定で実施し、別のエージェントを試すときは別の出力先に記録すると、それぞれの結果を比較できる。

リポジトリルートで Python 3.10 以降、Git、Bash、awk が使える Linux/macOS から実行する。試行データはリポジトリ外の新しいディレクトリに保存する。

```bash
cli=harness/evals/harness_eval.py
runs=$(mktemp -d)
git fetch origin main
python3 "$cli" inventory
python3 "$cli" validate --candidate P-001-short --base origin/main
python3 "$cli" prepare --candidate P-001-short --base origin/main --repeat 2 --out "$runs/external"
```

1. `manifest.json` の試行順に、各 `prompts/<id>.txt` の全文だけを同じ条件の新規セッションに渡す。採点器・他の回答・manifest は渡さない。各セッションにツールや過去会話を付けない。
2. 各 JSON 回答を `answers/<id>.json` に以下の形で保存する。`prompt_sha256` は配布したファイルの SHA-256。採点前に配布物と回答の対応を照合する。

   ```json
   {
     "prompt_sha256": "<配布したファイルの SHA-256>",
     "answer": {"path": "<モデル回答のパス>", "cases": [{"input": 0, "expected": false}]}
   }
   ```

3. 回答を採点して集計する。未着の回答を追加して `collect` を再実行すると残りを採点する。

   ```bash
   python3 "$cli" collect "$runs/external"
   python3 "$cli" report "$runs/external"
   ```

実行元を記録するときは最初の回収で自由記述の `--agent` と `--model` を任意で指定する。未指定は不明として記録し、回収再開時に省略した値は採点済みの記録から引き継ぐ。従来の `--runtime` も `--agent` と同じ意味で使える。

計測できた場合は、回収者が回答と同じ JSON のトップレベルに `"metrics": {"input_tokens": 120, "wall_time_ms": 3100, "cost_usd": 0}` を追加できる。カウント・時間は0以上の整数、費用は0以上の数値。省略と `null` は未取得、0は実測値を表す。`output_tokens`、`cache_read_input_tokens`、`cache_creation_input_tokens`、`rework_count` も記録できる。

### 既知の回答で動作を確認する

```bash
python3 "$cli" run --adapter replay --out "$runs/replay"
python3 "$cli" report "$runs/replay"
python3 -m unittest discover -s harness/evals -v
```

## 週ごとの候補を決める

- `validate` の `source_commit` は読み込んだ規約の完全なコミット ID。`--base` にその SHA を渡すと、後から同じコミットを使える。追加候補で省略すると手元の `origin/main` を解決する。初回の `P-001` は候補指定を省略しても当時の固定条件で再現できる。
- `condition_fingerprint` は実際の A/B 入力・課題と採点条件から求める。一度評価した候補と指紋が同じなら、無関係なコミットが増えても同条件。週次記録で最後に実施した指紋と照合し、必要な追加反復があるときだけ同条件を再試行する。エージェント・モデル・反復数は別の実行条件として記録する。
- 同じスイートで別の文を試すときは [P-001-short の定義](presets/P-001-short.json) を `presets/<新しいID>.json` として追加する。`id` はファイル名と揃え、`remove` に元の文、`replace` に置換後の文（削除は空文字列）、`hypothesis` に仮説を書く。この2課題が測る範囲は `rules/testing.md`「配置と命名」。異なる規約を検証する場合は、その課題と採点器を先に設計する。
- 追加候補の manifest（v3）はプリセット全体とそのハッシュを保存する。回収・再集計では保存時の定義と SHA を使用する。対象の節で元の文が消えていたり、規約全体に同じ文が複数あったりすると準備は止まる。
- A/B は基準コミットの `AGENTS.md` と、そこから箇条書きで参照する `@rules/.../*.md` の本文を記載順に読み込む。1項目に1ファイルを指定し、説明は空白を挟んで続けられる。解釈できない import は準備時に表示する。
- A/B で同じ独立した採点を使うため、検査器は `evaluator_source_commit` のスキャンと awk に固定する。規約を読み込むコミットと採点条件をそれぞれ記録する。以前の v1/v2 記録も元の条件で再集計できる。

## 結果の読み方

- 1反復で2課題 × 2構成の4試行。課題・反復ごとに A/B の先行順を交替する。 `--repeat N` で同一条件を反復できる。
- 初回の P-001 は入口・全8規約・既存スキャンと付属 awk を固定コミット `d199ad2483ca82c1a9d2b9134460d04a2d89105d` から読む。浅い clone に履歴がない場合はそのコミットを取得する。`manifest.json` にコミット、課題・規約・評価器・配布物のハッシュ、実行条件を記録する。
- 回答はパスと入出力例のデータとして扱う。パスは対象モジュールと照合し、使い捨ての空ファイルで元のテスト規約スキャンを実行する。期待値と境界の網羅は固定した振る舞いから採点する。生成コードの実行や GitHub 操作は発生しない。
- `results.jsonl` の各行にチェック別の結果・失敗理由・計測値を保持する。同じ評価器の版で `report` を実行すると、保存した回答のハッシュ・採点・申告した計測値を照合し、課題別・反復別の結果と B−A の差が得られる。入力・cache read・cache create は別欄で、未取得値は「—」。成功率の分母には要件未達・安全性違反を含める。環境エラーと未実行は別に表示する。
- 全試行の品質判定が成功すれば終了値は0。計測値だけの欠損は「—」と表示する。未実行の試行・品質失敗・環境エラーがあれば終了値は非ゼロとなる。試行外へのパスを回答した場合は安全性違反を記録して停止する。失敗をやり直す実験には新しい出力先を使う。
- この smoke は単発のテスト設計課題。実装・修正ループ・通常セッションの自動読込・フック発火・本番 PR の品質は測定対象外。判定は**保留**とし、本番の規約削除は追加課題、独立した holdout と実運用に近い条件での確認後に判断する。
