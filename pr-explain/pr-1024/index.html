解説時点 77b8e61 · 材料 Issue #1022

PR ごとの解説ページを Pages に出す

実装したセッションが「振る舞い・技術・テスト」の解説を HTML で書き、Actions が「変更の地図」を足して、PR から 1 クリックで読める 4 ページにする。このページ自体が、その仕組みで出した最初の解説。

概要

長いセッションで作られた PR は、diff と Issue を読むだけでは「何の技術を使い、なぜその振る舞いにしたか」が掴みにくい。この PR は、PR ごとに https://dio0550.github.io/design-composer/pr-explain/pr-<番号>/ という解説ページを作り、その読み解きを人間の代わりに先に済ませておく仕組みを足す。

解説は読む目的ごとに 4 ページに分かれる。このページ(入口)は全体像と見てほしい箇所、振る舞いはマージしてよいかを決めるための変更前と変更後、技術は使った技術とコードの読み方、テストは何が守られていて何が守られていないか。

書くのは 2 人。解説の本文は実装したセッションが pr-explain スキル(.claude/skills/pr-explain/SKILL.md)で書く。経緯はセッションの中にしか無いので、ここは AI が書くしかない。変更の地図(変更ファイルの一覧・テスト名の増減・解説の古さ)は git の差分だけで決まるので、Actions(.github/workflows/pr-explain.yml)が機械的に作る。どちらも gh-pages ブランチの pr-explain/pr-<番号>/ にだけ置き、PR ブランチにも main にも入れない。

レビュー特に見てほしい箇所

  • この PR がマージされるまでは、main へのマージのたびに開いている PR の解説が消える。main 側の Storybook のデプロイがまだ pr-explain/ を掃除の対象から外していないため(実際に一度消えた)。振る舞い
  • ページの固定スクリプト(地図の描画・古さの帯・ナビ・行リンク)には自動テストが無い。Playwright で状態ごとに目視しただけ。テストで守れていない振る舞い
  • Pages のデプロイが PR のイベントごとに増える。#109(同時に 1 つしかデプロイできず、待ちが 10 分でタイムアウトする)が再発しないかは観察が要る
  • 解説を書く手間が PR ごとに増える。4 ページのうち該当しないものは書かない決まりにしたが、どこまで書くかの目安(各ページ 5〜10 分で読める長さ)が妥当か

各ページの案内

  • 振る舞い: PR のイベントごとに何が起きるか(開く・push・公開・閉じる・main へのマージ)と、方式の判断・逸脱・見送り
  • 技術: CSP のハッシュ、html.parser での検査、partial clone と sparse-checkout、merge-base とテスト名の集合比較、Actions の認証。後半は読む順のコード解説
  • テスト: 判定表 3 本が守る振る舞いと、test-reviewer が壊して確かめた結果、守れていない振る舞い
