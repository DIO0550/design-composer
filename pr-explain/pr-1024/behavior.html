判断判断

置き場所は gh-pages に直接 push する

採った案
セッションが gh-pages の pr-explain/pr-N/ へ直接 push する。push できることは計画の段階で 1 回置いて確かめた
検討した案
JSON を書いて描画する / Markdown を PR コメントに書く / PR ブランチにコミットする / PR コメントに HTML 断片を貼る / 専用ブランチ経由 / CI で AI に生成させる
理由
AI が書いたものをそのまま読める(JSON は読めない)、HTML、main に溜めない・Files changed に混ぜない、の 3 つを同時に満たすのがこれだけ。専用ブランチは、push で起動するワークフローがそのブランチ側の定義で動くため、HTML しか無いブランチでは何も起動しない

読む目的ごとに 4 ページに分けた

採った案
入口・振る舞い・技術・テストの 4 ページ。枠と検査は共有し、ナビで行き来する
計画にあった案
1 ページに全部の節を並べる
理由
振る舞いはマージ判断のため、技術は後から理解のため、テストは守られている範囲の確認のために読む。1 ページだと長い技術解説に振る舞いが埋もれる(ユーザーの判断。別 PR にはせずこの PR で対応)

セッションが書くのは断片だけにした

採った案
マーカーの間に入る断片だけを書き、build-pr-explain-page.py が検査してテンプレートへ差し込む
計画にあった案
テンプレートを丸ごとコピーして間を書き換え、マーカーの外がテンプレートと一致するかを照合する
理由
同じ枠を 2 か所に持つと、ずれを「検出」することになる。断片だけにすれば、ずれ自体が起きない(solution-reviewer)

解説を書くのはサブエージェントではなく、実装したセッション自身

採った案
実装したセッションが自分で書く
計画にあった案
着手前の会話では「サブエージェントに書かせる」と言っていた
理由
材料に「Issue に書くほどではなかった判断・試して捨てた形」が要り、それはセッションの中にしか無い

防ぐのは事故で、攻撃ではない

採った案
検査(要素・属性・URL・コメント)と CSP の 2 段。CSP は固定スクリプトのハッシュだけを許す
理由
解説は差分のコードを抜粋するので、エスケープし忘れた JSX の onClick= がそのまま属性になる事故が起きうる。差分を書ける人はリポジトリへ書き込める人なので、悪意ある入力は前提にしない
